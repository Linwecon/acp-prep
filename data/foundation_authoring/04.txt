4.1|Agent 定义|一个只回复文字的聊天助手，与能完成任务的 Agent 有什么主要区别？|Agent 能围绕目标选择行动、调用工具并利用结果继续推进。|关键是目标与行动反馈闭环，而不是回答是否很长或是否使用了一个框架。
4.2|组件职责|LLM、Planner、Tool、Memory 分别解决什么问题？|理解生成、规划步骤、执行外部操作、保存或检索状态与经验。|这些是职责划分，实际系统可以把部分职责合并实现。
4.3|工具执行|模型输出一个“查询余额”的工具调用，是否表示数据库已经被查过？|不是，应用还需验证参数、执行工具并返回结果。|模型产生调用提议，真正的外部操作由程序执行。
4.3|工具描述|为什么工具定义需要说明参数名称、类型和用途？|让模型正确选择工具并形成可验证的参数。|模糊工具描述容易导致错误路由；执行端仍要做参数校验。
4.3|调用闭环|把工具结果返回模型的目的是什么？|让模型根据实际执行结果解释、继续行动或结束任务。|没有返回结果就宣称成功，会把计划误当作已完成事实。
4.4|ReAct|用三个动作概括 ReAct 的循环。|思考下一步、执行行动、观察结果，再决定是否继续。|观察是来自工具或环境的反馈，不是模型对结果的想象。
4.4|推理与行动|仅把一个问题拆步思考，与调用工具后再调整计划有什么区别？|前者主要处理已有信息；后者引入环境反馈与外部执行。|复杂表述不自动构成 Agent，工具交互和闭环才改变任务能力。
4.5|MCP 作用|MCP 主要帮助统一哪一类接口问题？|应用接入外部工具、资源和提示模板的协议方式。|它减少重复适配，但不自动完成业务授权或保证工具结果可信。
4.5|协议角色|MCP 的 Host、Client、Server 可以怎样简单区分？|Host 是使用能力的应用；Client 负责连接；Server 提供能力。|区分应用、连接和服务职责，便于定位配置与通信问题。
4.5|三类能力|MCP 中 Tools、Resources、Prompts 分别适合表达什么？|可执行操作、可读取数据、可复用提示模板。|读取资料与执行有副作用的操作应有不同的授权和处理方式。
4.6|固定工作流|流程稳定且步骤必须按顺序执行时，为什么常优先用工作流？|路径更可控，容易测试、审计和处理明确的失败分支。|不需要让模型重新发明每一步，减少不必要的不确定性。
4.6|自主规划|任务路径不确定时，自主规划的价值和代价分别是什么？|价值是灵活选择步骤；代价是更多调用成本与失控风险。|应同时限定工具、预算和停止条件，避免无限探索。
4.6|反思|Agent 执行后检查结果，最重要的是对照什么？|对照明确的成功标准和可观察证据。|仅让模型说“我做得不错”不构成可靠验证。
4.7|多 Agent 分工|多个 Agent 协作时，为什么需要明确职责和交接格式？|防止重复劳动、信息遗漏和互相等待。|增加角色数量不能自动提升结果，协作成本也会增加。
4.7|共享状态|两个 Agent 同时修改同一任务状态，可能出现什么问题？|覆盖对方结果、使用过期状态或重复执行。|需要版本、锁、任务归属或协调规则来控制并发写入。
4.8|短期记忆|短期记忆通常保存什么，与长期记忆有什么区别？|短期保存当前任务上下文；长期保存跨任务可复用信息。|两者的保留期限、检索方式和隐私要求可能不同。
4.8|记忆筛选|为什么不应把每轮完整对话都无限追加到当前上下文？|会增加成本、噪声并触及窗口上限。|保留关键状态、压缩历史和按需检索通常更可控。
4.9|Skill|把“文档审查步骤和标准”做成 Skill，有什么价值？|让成熟操作流程可以被重复使用和维护。|Skill 提供任务指导和资源，不等于修改了模型参数。
4.10|评测方法|规则检查、模型评审和评分量表各适合解决什么？|规则检查可确定条件；模型评审处理语义；量表统一评价维度。|复杂任务通常需要组合，避免只靠一个主观总分。
4.11|运行保障|任务循环为什么需要超时、最大步数和失败出口？|限制失控消耗，并使无法完成的任务可诊断、可接管。|没有停止条件的自动化可能反复执行同一无效步骤。
4.3|参数校验|查询工具只接受员工编号，模型传来了一段 SQL，程序应该怎么做？|拒绝不合契约的参数，返回明确校验错误或要求重新生成。|不能把模型输出直接拼接执行；工具边界由程序落实。
4.3|高影响操作|Agent 找到一笔疑似重复付款后，能直接退款吗？|应按业务授权和审批流程处理，确认后才执行高影响操作。|发现问题、提出行动和获准执行是不同阶段。
4.4|事实反馈|工具返回“订单未找到”，Agent 却答“已取消”，错在哪里？|最终回答没有基于真实观察结果。|应说明未找到订单并检查标识，不能把原计划当成成功状态。
4.5|协议与调用|引入 MCP 后，是否就不再需要模型的工具选择和参数生成？|不是，两者职责不同，应用仍需决定何时调用以及传什么。|MCP 解决接入通信，模型调用机制解决决策表达，两者可以配合。
4.6|混合策略|任务先探索未知资料，再执行固定审批流程，如何组合规划方式？|探索阶段可自主规划，审批阶段转为受约束的固定流程。|不同子任务可用不同控制方式，不必整条链路完全自主。
4.7|减少角色|只有一次简单知识库查询，拆成五个 Agent 有什么潜在问题？|多出通信、延迟和错误传递，却未必增加能力。|先验证单个流程的不足，再决定是否需要多角色分工。
4.8|错误记忆|Agent 把一次错误推测存成长期事实，后续应怎样防止扩散？|标记来源与可信状态，验证后写入，并支持更新和删除。|长期存储会放大错误的持续影响，需要写入治理而不仅是检索。
4.10|轨迹评估|Agent 最后答对了，但调用了未授权接口，应算完全通过吗？|不应，任务结果与执行过程都需要评估。|轨迹检查能发现权限违规、多余调用和不可接受的副作用。
4.11|重试与幂等|支付请求超时后，为什么不能无条件重复提交？|第一次可能已执行，重复提交会造成重复支付。|使用幂等标识并查询状态，再决定是否重试或人工处理。
4.12|完整设计|设计一个报销查询 Agent，列出从提问到结束的关键步骤。|确认身份与需求 → 选择只读工具 → 校验参数 → 查询 → 核对结果 → 回答并记录状态。|同时设置权限、超时与失败出口，不能只设计成功路径。
