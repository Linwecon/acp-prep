6.1|部署目标|把模型从本地脚本变成服务，还需要补充哪些基本能力？|请求处理、资源管理、监控、访问控制和故障处理。|本地能生成一次答案，不等于能持续承接真实并发流量。
6.2|Prefill|推理的 Prefill 阶段主要处理什么？|处理输入上下文并建立后续生成需要的中间状态。|长输入通常增加这一阶段的工作量，并影响首字等待。
6.2|Decode|Decode 阶段为什么通常需要反复执行？|自回归生成要逐步产生后续 Token。|每一步依赖此前上下文，输出长度因此影响总生成时间。
6.3|首字延迟|TTFT 衡量什么？|从请求开始到收到首个输出 Token 的时间。|它与完整响应耗时不同，排队和输入处理都可能影响它。
6.3|吞吐|吞吐量高是否等于每个用户等待时间都短？|不等于，系统总产出与单请求延迟是不同指标。|批处理可能提高总利用率，同时增加部分请求的等待。
6.3|并发|并发请求数与每秒请求数有什么区别？|并发是同时在处理的请求数，每秒请求数是到达或完成速率。|请求耗时不同，同样速率可能对应不同并发压力。
6.6|显存组成|推理显存除了模型权重，通常还要容纳什么？|KV Cache、中间计算张量及运行时开销。|只按权重文件大小选显卡，可能在真实并发时发生显存不足。
6.4|量化|模型量化主要改变什么存储或计算表示？|用较低精度表示权重等数值，减少相应资源需求。|不同量化方案适用范围不同，性能收益也依赖硬件与实现。
6.4|量化边界|把模型从高精度变成低比特，能否保证业务准确率完全不变？|不能，应对目标任务重新评测。|节省显存与潜在误差需要权衡，不能仅看模型能否加载。
6.6|KV Cache|KV Cache 缓存的主要是什么，为什么有助于生成？|缓存已有 Token 的注意力键和值，减少重复计算。|它不是把所有问题的最终答案存起来，也会消耗显存。
6.5|分页管理|PagedAttention 的核心直觉是什么？|用类似分页的方式管理 KV Cache，改善分配与复用。|重点是减少管理浪费和碎片，不是让模型参数变少。
6.5|连续批处理|连续批处理与等整批请求结束后再接下一批有什么区别？|可以在运行过程中让完成请求退出、新请求加入。|长短请求混合时能提高资源利用率，但仍需控制排队和延迟。
6.7,6.8|MaaS|使用模型 API 服务，相比自建通常减少哪类工作？|减少模型底层部署和 GPU 运维工作。|应用仍需负责业务逻辑、权限、调用可靠性和成本管理。
6.9|自建服务|选择自建开源模型时，团队要额外承担什么？|硬件与推理服务部署、容量规划、升级和故障运维。|自建提供控制空间，但不意味着总体成本必然更低。
6.10|云托管|云托管推理服务与直接使用预置模型 API 的区别是什么？|前者可托管自有模型服务，后者通常调用平台已提供的模型。|需要区分“托管部署”与“免部署调用”的运维边界。
6.10|冷启动|Serverless 服务第一次调用慢，可能是什么原因？|实例初始化、依赖加载或模型加载产生冷启动。|应测量初始化与模型推理耗时，不能仅归因为网络。
6.11|高可用|多副本和健康检查分别起什么作用？|多副本提供冗余，健康检查帮助识别不可用实例并调整流量。|有多个实例不代表故障切换会自动正确，需要配套路由策略。
6.11|监控维度|推理服务为什么不能只监控 GPU 利用率？|还要看延迟、错误、队列、费用与业务质量。|高利用率可能意味着效率好，也可能意味着拥塞。
6.11|弹性扩容|自动扩容除了 CPU 或 GPU 利用率，还可以观察什么信号？|队列长度、等待时间、并发和延迟目标等。|扩容有启动时间，应考虑突发流量和容量余量。
6.12|选型约束|部署方案的基本取舍应围绕哪几类约束？|业务质量、延迟吞吐、数据要求、预算和团队运维能力。|没有一个方案在所有约束下都最优。
6.6|权重计算|假设模型有 70 亿参数，每参数 2 字节，仅权重大约多少十进制 GB？|约 14 GB。|70 亿×2 字节=140 亿字节；这是权重估算，不包含 KV Cache 和运行开销。
6.6|长上下文|单用户运行正常，多用户长对话时显存溢出，应优先检查什么？|并发和序列长度引起的 KV Cache 增长，以及资源限制。|权重常驻大小没变，不代表运行时显存不再增长。
6.3|尾延迟|平均响应 1 秒，但少数用户等 20 秒，为什么还应关注 P95/P99？|分位数能揭示慢请求和尾部体验，平均值可能掩盖它们。|上线承诺通常需要兼顾常态与尾部，而不是只报告平均值。
6.5|批量取舍|增大批量后吞吐提高但 TTFT 变差，应怎样决定是否保留？|结合业务延迟目标比较，必要时限制等待或区分流量。|离线批处理和在线交互的优先指标可能不同。
6.4|量化评估|量化后显存下降一半，但专业术语错误增多，应采取什么步骤？|用代表性评测确认退化，比较其他精度或量化配置。|不能把资源收益直接等同于可上线收益。
6.10|冷启动优化|短时请求很少又要求即时响应，降低冷启动与节约成本可能冲突在哪里？|预热或保持实例通常减少等待，却增加闲置成本。|应按真实流量和服务目标计算取舍，不宜一律常驻或一律缩零。
6.11|过载保护|流量超过容量时，无限排队有什么风险？|请求超时、资源耗尽和用户重试可能形成更严重拥塞。|应设队列上限、限流、合理超时和可控降级。
6.11|缓存条件|两个用户问同一句话，能否直接共享缓存答案？|要先核对权限、数据版本和个性化条件是否一致。|相同文字不代表相同授权或事实背景，共享错误会造成泄露或过期回答。
6.12|部署验收|压力测试应该只用短问题和短答案吗？|不应，应包含真实输入长度、输出长度和并发分布。|过于理想的样本会低估长上下文、长输出和突发流量的负载。
6.12|方案串联|为一个交互式答疑服务列出上线前的四项验证。|验证业务质量、典型与尾部延迟、容量与故障恢复、成本和访问控制。|同时准备监控与回滚，避免仅验证一次成功响应就上线。
