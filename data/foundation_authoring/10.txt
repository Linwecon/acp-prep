10.1|平台分层|应用开发、模型 API、训练部署、数据存储，为什么应先分层再选产品？|各层解决不同问题，分层能把需求对应到合适能力。|产品名字多并不意味着必须全部使用，应先明确工作目标。
10.1|MaaS|MaaS 的基本使用方式是什么？|通过服务接口调用平台提供的模型能力。|用户通常不用自己部署模型权重，但仍需管理应用和调用成本。
10.2|百炼定位|百炼平台在大模型应用开发中主要提供什么帮助？|提供模型使用及应用构建相关能力，如知识库、提示配置和流程组织。|具体功能以平台当前支持为准，核心是降低模型应用集成负担。
10.3|DashScope|DashScope 在调用链路中主要位于哪一层？|模型服务接口层，供程序调用支持的模型能力。|它与应用界面、企业数据存储和底层训练任务不是同一职责。
10.4|PAI|需要自行开发、训练和部署模型时，PAI 主要解决什么？|提供机器学习开发、训练任务和推理服务等平台能力。|它服务模型工程流程，不能仅因名字有 AI 就与任意应用工具混同。
10.4|DSW|DSW 更接近交互式开发环境还是生产在线推理服务？|更接近交互式开发环境。|适合探索代码、验证环境和实验；持续对外服务是另一类职责。
10.4|DLC|DLC 与在 Notebook 中手动运行实验相比，更强调什么？|以任务方式组织深度学习训练及相关资源。|开发验证与正式训练作业可以衔接，但用途和运行管理不同。
10.4|EAS|EAS 更适合承接训练后的哪一步？|把模型或算法服务部署为在线推理服务。|训练完成的模型文件需要服务化、资源配置和运维才能持续被调用。
10.7|ModelScope|ModelScope 与已部署的模型 API 服务有什么区别？|它主要是模型与相关资源生态，下载模型不等于获得在线服务。|使用开源权重还需考虑许可、依赖、硬件和部署方式。
10.1|OSS|在知识库问答链路中，OSS 通常适合承担什么角色？|存储文档、图片或模型产物等对象数据。|对象存储保存数据，不会自动完成文本检索、生成或事实核验。
10.1|数据加工|MaxCompute、DataWorks 与模型生成分别关注什么？|前两者偏数据计算和开发治理流程，模型生成负责内容推理与生成。|实际职责可协同，但不能把数据加工平台当作对话模型本身。
10.2|知识库功能|把制度上传到知识库后，为什么仍需要测试问答效果？|解析、切片、召回和生成任一环节都可能有缺陷。|平台封装减少代码，不消除数据质量和评测工作。
10.2|工作流|在低代码工作流中显式配置检索、审核、回复节点有什么价值？|使顺序与分支更可见、可控和可测试。|可视化只是表达方式，仍应检查节点参数和失败路径。
10.3|兼容模式|选择 OpenAI 兼容调用方式时，应先核对什么？|目标模型与所需参数、输出及工具功能是否在兼容范围内。|兼容不是所有服务行为完全一致；不应套用其他平台的模型名。
10.3|原生接口|什么时候有理由考虑平台原生 SDK 或接口？|所需能力或操作在当前兼容接口中没有提供，或原生接口更适配。|应对照具体需求判断，不是认为原生总是更强或兼容总是足够。
10.5|角色匹配|业务人员快速做知识问答原型，与算法团队训练自有模型，平台侧重点应相同吗？|不同，前者偏应用搭建，后者偏开发训练和模型管理。|先看团队职责和交付物，再选工具组合。
10.6|模型选型|选择通义系列模型时，为什么不能只凭名字中的档次词判断？|不同型号、版本的质量、时延、价格和上下文能力需要实测核对。|名称有参考意义，但不是永久不变的性能承诺。
10.6|长上下文|长上下文模型可以直接替代所有知识检索吗？|不能直接这样判断，仍需考虑相关性、更新、权限和成本。|能装下资料不代表能稳定定位所有答案，也不等于资料无需治理。
10.7|开源许可|下载一个可用模型准备商用前，需要额外检查什么？|许可证、使用限制、模型来源及相关组件许可。|可下载不代表任意用途都不受限制。
10.8|费用与额度|余额足够是否意味着调用永远不会被限流？|不是，余额、请求配额和速率限制是不同约束。|应分别监控费用与 RPM、TPM 等实际适用限制。
10.5|快速原型|只需验证员工手册问答，团队没有模型运维能力，怎样起步较合理？|优先评估托管模型及知识库应用能力，先做小规模验证。|先确认业务有效，再考虑是否需要更复杂的训练或自建部署。
10.4|训练链路|团队已在 DSW 中验证训练代码，下一步正式训练并提供 API，可怎样衔接？|可用 DLC 管理训练任务，再用 EAS 等服务化部署产物。|开发、训练、推理各有职责，实际还需配置数据、镜像与权限。
10.3|接口报错|切换到某地域后提示模型不可用，为什么不应立即判断代码逻辑坏了？|可能是地域、模型可用性、账号授权或服务地址不匹配。|排错先核对环境和接口契约，再定位应用逻辑。
10.2|应用与模型|已经创建一个知识库应用，为什么调用基础模型接口不一定得到同样回答？|应用还包含检索、提示词、工具和流程配置。|基础模型能力与完整应用链路不同，不能只比较模型名字。
10.7|私有部署|因数据和定制要求计划私有部署，除模型效果外还需评估什么？|许可、硬件容量、运维能力、数据访问和更新成本。|私有化提供控制空间，但可靠性仍取决于实际工程投入。
10.8|成本控制|为什么应给开发测试和生产调用分开设置访问与预算？|便于隔离风险、归因消耗并控制误用影响。|不能仅看账户总账，环境级观测有助于发现异常调用。
10.8|报价边界|教程写的单价可以直接作为半年后的预算依据吗？|不宜，应按当前型号、版本、地域和计费规则重新核对。|课程数字可用于理解计算，实际采购预算需要有效价格依据。
10.9|低代码边界|低代码平台已经提供发布按钮，是否就不需要测试与监控？|仍需测试、权限配置、质量监控和故障处理。|封装降低搭建成本，不自动承担全部业务质量责任。
10.9|组合方案|制度文档放在 OSS，问答使用托管模型，自有分类模型需要上线，可怎样分工？|OSS 存资料，知识库链路检索，模型 API 生成，自有模型用推理服务提供能力。|这些部件按接口连接，各自完成职责，不需要强行由一个产品包办。
10.9|完整选型|给一项新业务选平台前，应形成哪几项可验证的需求？|输入输出类型、质量标准、数据与权限要求、延迟规模、预算及运维能力。|再做小规模验证和成本估算，比先背产品清单更能支持决策。
