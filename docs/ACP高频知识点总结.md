## 1. 大模型基础

### 1.1 什么是大语言模型（LLM）

> **导读**：大语言模型是在海量文本数据上训练得到的通用智能底座，通过预训练掌握语言规律、知识表达与一定的推理能力，再依据输入提示生成相应输出。
>
> 可粗略类比为一位通读海量文献的学者：给定一个开头（提示词），它便能依据所学语言规律续写下去——行文流畅，但内容并不保证真实，有时会生成看似合理却与事实不符的内容。

**核心概念**：大语言模型（Large Language Model, LLM）是基于深度学习的大规模神经网络，通过在海量文本数据上预训练，习得语言理解和生成能力。

**【直观解读】**：大模型本质上是**概率性的文本生成器**：根据已有上文，按概率预测下一个词，并逐 Token 生成完整回答。它不是数据库，不以"记住答案"的方式工作，而是将训练过程中学到的知识压缩进自身的参数之中。

**高频考点**：

| 知识点 | 说明 |
|--------|------|
| **Token（词元）** | 模型处理文本的最小单位。一个中文字 ≈ 1-2 token，一个英文单词 ≈ 1-3 token。模型的计费和上下文窗口都以 token 为单位 |
| **参数（Parameter）** | 模型内部的"记忆单元"数量。参数越多，模型容量越大，能力越强（如 Qwen2.5 系列从 0.5B 到 72B 参数） |
| **上下文窗口（Context Window）** | 模型一次能"看到"的最大输入长度。超过窗口的内容会被截断。主流模型通常支持 4K-128K token |
| **Transformer 架构** | 当前所有主流大模型的基础架构，核心是**自注意力机制（Self-Attention）**，让每个词都能关注到输入中的所有其他词 |
| **自注意力机制** | 不限制输入序列长度，可灵活处理不同长度的序列。每个位置的输出都会综合考虑所有位置的信息 |

**【深入原理】**：LLM 的本质是**条件概率模型**：给定上文 x₁、x₂…xₜ₋₁，模型计算下一个词的概率分布 P(xₜ | 上文)，训练目标就是让该分布尽量贴近真实文本（最小化交叉熵损失）。所谓"知识"并不以文字形式存放在某个文件中，而是被压缩进数十亿乃至数千亿个**权重参数**中——这正是模型"知道很多却说不清出处"的原因。

**【实战/考试要点】**：
- 计费、窗口、max_tokens 全部按 **token** 计，不是按字数。
- 超过窗口的输入会被**截断**，而不是报错后自动重新处理。
- 记忆结论：**自注意力机制不限制输入序列长度**（附录高频陷阱之一）。

### 1.2 模型能力边界

> **导读**：模型能力强大，但存在三类天然局限：无法获知训练截止日期之后的信息、难以进行精确的数学计算、可能生成与事实不符的内容。认清这些边界，才能判断何时需要借助外部工具进行能力补位。

- **优势**：语言理解、文本生成、知识问答、代码编程、推理分析
- **局限**：
  - **幻觉（Hallucination）**：模型可能生成看似合理但实际错误的内容
  - **知识截止**：模型知识停留在训练数据截止日期之前
  - **数学计算**：纯 LLM 不擅长精确数学计算
  - **实时信息**：无法获取训练数据之外的最新信息

**【直观解读】**：大模型的知识止步于训练数据截止日期，无法获取实时信息；其计算依赖逐 Token 预测，缺乏符号运算机制，难以保证大数乘除的精确性；在上下文信息不足时，它仍可能自信地给出错误答案。

**【深入原理】**：
- **幻觉从哪来**：模型的训练目标是最小化下一个 Token 的预测误差，而非验证事实真伪。当上下文信息不足时，模型只能依据概率续写，生成的内容语言通顺，但事实未必成立。
- **为什么算不好数学**：自回归模型逐 Token 生成输出，缺乏真正的符号运算机制，多位进位、大数乘法等在逐 Token 预测中极易出错。
- **知识截止的根源**：训练结束后参数冻结，推理阶段仅做前向计算、不更新参数，因此模型无法在推理时"学会"新知识——这正是 RAG 与微调等补充手段存在的意义。

**【实战/考试要点】**：
- 需要"新知识/私有知识" → 用 **RAG 检索**或联网搜索补充，而不是调高 temperature。
- 需要"精确计算" → 让模型调用**计算器工具（Function Calling）**，而不是硬让它心算。
- 幻觉无法 100% 消除，只能缓解：引用溯源、人工核验、约束"只依据资料回答"等。

### 1.3 主流模型

> **导读**：考点集中在"通义千问系列如何选型"：**简单任务用 Turbo（响应快、成本低）、高质量任务用 Max（性能最强）、Plus 性能与成本均衡**。

| 模型系列 | 特点 |
|----------|------|
| **通义千问（Qwen）** | 阿里云自研，支持多语言，有 0.5B-72B 多种规格 |
| **Qwen-Plus** | 性能与成本均衡的版本 |
| **Qwen-Max** | 最强性能版本 |
| **Qwen-Turbo** | 速度优先版本 |

**【直观解读】**：Turbo 定位为速度优先的轻量服务（响应快、成本低、能力常规）；Max 定位为性能最强的旗舰服务（成本高、效果最优）；Plus 介于两者之间，兼顾性能与成本。

**【深入原理】**：通义千问分为两条产品线：**开源系列**（如 Qwen2.5，0.5B~72B 参数，可私有化部署、数据不出域）与 **API 商业版**（Turbo / Plus / Max，由 DashScope / 百炼统一提供服务）。商业版对应不同规模与优化目标的模型服务，因此在"速度、能力、价格"三个维度上定位分明。

**【实战/考试要点】**：
- 选型口诀：**快而省 → Turbo；稳而强 → Max；性价比 → Plus**。
- 开源模型的价值是**私有化部署、数据不出域**；商业版的价值是**免运维、按量付费**。
- 考点：简单任务不必上 Max——用 Turbo 更划算（成本控制题）。

### 1.4 模型的训练与生成原理

> **导读**：理解"模型是如何训练的"与"模型是如何生成文字的"，有助于判断哪些问题应归因于训练环节、哪些应归因于推理配置。
>
> 类比：预训练如同通过海量文本泛读掌握语言规律与通识知识，后训练如同针对性指导使模型学会遵循指令，生成阶段则是逐 Token 自回归地续写，每生成一个 Token 后将其拼回输入再预测下一个。

**核心概念**：LLM 采用 **预训练 + 后训练** 两阶段范式，生成时按 **自回归（Auto-regressive）** 方式逐 Token 预测下一个词。

| 知识点 | 说明 |
|--------|------|
| **预训练（Pre-training）** | 在海量无标注文本上训练，目标函数是"预测下一个 Token"，习得语言规律与通用知识 |
| **后训练 / 对齐（Post-training）** | 在预训练基础上用 SFT、RLHF 等方式让模型"遵循指令、符合人类偏好"，是模型听得懂人话的关键 |
| **自回归生成** | 模型一次只生成一个 Token，把已生成内容拼回输入再预测下一个，直到遇到结束符或达到 max_tokens |
| **训练 vs 推理** | 训练阶段更新参数、需要 GPU 集群；推理阶段参数冻结、只做前向计算 |
| **知识截止** | 模型知识停留在训练数据截止日期之前，训练后无法通过推理配置"学会"新知识 |

**【深入原理】**：
- **预训练在做什么**：将文本拆分为 Token 序列，让模型预测第 t 个 Token，用"预测与真实"的差距（交叉熵损失）通过反向传播更新参数。数据、参数与算力规模越大，学到的规律越丰富。
- **后训练为什么必要**：预训练模型只会"续写"，不会"遵循指令"。SFT 使用"指令-回答"样本教会模型回答问题；RLHF 再通过人类偏好反馈使回答更符合价值观。
- **自回归生成流程**：① 将输入与已生成内容拼接 → ② 前向计算得到下一个 Token 的概率分布 → ③ 按解码策略选择 Token → ④ 拼回输入重复执行，直到生成结束符（EOS）或达到 max_tokens。

**【实战/考试要点】**：
- "模型听不懂指令" → 属于后训练/对齐问题；"训练后仍不知道新知识" → 属知识截止（正常现象），应走 RAG。
- 高频题：**训练更新参数 vs 推理冻结参数**——推理阶段不会因多问几遍而"变聪明"。

### 1.5 采样与解码策略

> **导读**：模型每次预测的是下一个 Token 的**概率分布**，从分布中选择具体 Token 的规则即解码策略。策略不同，输出的确定性、多样性与整体风格差异显著。

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **贪婪解码（Greedy）** | 每次只选概率最高的 Token，结果确定，但容易重复、平庸 | 事实问答、代码补全 |
| **随机采样（Sampling）** | 按概率分布随机抽取，配合 temperature/top_p/top_k 控制随机程度 | 创意写作、对话 |
| **束搜索（Beam Search）** | 同时保留多条候选序列，最终选整体概率最高的一条 | 翻译、摘要 |
| **Temperature** | 0 时退化为贪婪解码；值越高概率分布越平缓，输出越发散 | 创作调高、事实类任务调低 |
| **top_p / top_k** | 先截断低概率 Token 再采样，可与 temperature 叠加使用 | 约束采样范围 |

**【直观解读】**：贪婪解码每次选择概率最高的 Token，输出确定但容易重复、缺乏多样性；随机采样按概率分布抽取 Token，输出更具多样性；temperature 控制概率分布的平滑程度——取值越高，低概率 Token 被选中的机会越大，输出越发散；取值越低，输出越集中于高概率 Token。

**【深入原理】**：
- **temperature 的数学本质**：对每个候选词的 logit（模型输出的原始分数）除以 T 再做 softmax：pᵢ = e^(zᵢ/T) / Σ e^(zⱼ/T)。T→0 时概率最高的词趋近于 1（等价于贪婪解码）；T 越大词间概率差越小、输出越发散；T=1 即原始分布。
- **top_p（核采样）**：将候选词按概率从高到低累加，仅从累计概率达到 p 的那批词中采样——**动态**决定候选集大小。
- **top_k**：固定只从概率最高的 k 个词中采样。三者可叠加使用（常见实现先对 logits 做 temperature 缩放，再做 top_k / top_p 截断，最后 softmax 采样）。
- **Beam Search**：每步保留 K 条整体概率最高的部分序列（束），最终从完整序列中挑选整体得分最高的一条，计算量大于贪婪解码。

```chart bars
temperature = 0.2（聚焦头部候选） | 90
temperature = 1.0（原始分布） | 55
temperature = 1.8（分布趋于平坦） | 30
```

> 💡 **判断技巧**："相同输入、输出每次不同" → 采样随机性（属正常现象）；"输出重复、单调" → temperature 过低或贪婪解码；两者都与对话历史、上下文无关。

**【实战/考试要点】**：
- 数值考点：temperature **0.0~2.0**、top_p **0.0~1.0**、top_k 为正整数。
- temperature=0 只能**大幅降低**随机性，**不能绝对保证**输出一致（受并发、模型版本等影响）。
- 事实/代码任务用低 temperature；创意任务用高 temperature + top_p 组合。
- 误区：调高 temperature 不会让模型"更聪明"或"知识更多"，只会让输出更随机。

### 1.6 Transformer 与自注意力机制（深入原理）

> **导读**：Transformer 是 GPT、Qwen 等主流大模型的"地基"。它要解决的核心问题是：在一句话中，每个词应从哪些词获取信息？

**【直观解读】**：自注意力机制可类比为全员参与的圆桌会议：序列中的每个 Token 都会关注所有其他 Token，依据上下文动态评估彼此的相关程度，再综合相关信息更新自身的表示。以"苹果"为例，它与"吃"还是与"手机"更相关，取决于具体语境。

**自注意力可视化**（虚线表示"苹果"对句中其他 Token 的关注）：

```chart attn
苹果
很
便宜
而且
好吃
```

**【深入原理 · 一】自注意力机制（Self-Attention）**（理解链路即可，考试不考手算）：

| 步骤 | 名称 | 说明 |
|------|------|------|
| 1 | Token 化 + 嵌入 | 文本切成 Token，每个 Token 查表得到向量（Embedding） |
| 2 | 位置编码 | 叠加位置信息（如 RoPE 旋转位置编码），让模型感知词的先后顺序 |
| 3 | 生成 Q / K / V | 每个 Token 经三个权重矩阵变换出 Query（查询）、Key（键）、Value（值） |
| 4 | 注意力打分 | 用 Q 与所有 K 做点积得到"相关度分数"，除以 √dₖ 缩放后经 softmax 归一化为权重 |
| 5 | 加权求和 | 用权重对所有 V 加权求和，得到"综合了全文信息"的新表示 |

**Q / K / V 的直观含义**：

| 角色 | 含义 | 类比 |
|------|------|------|
| **Query（查询）** | "我要找什么信息" | 检索时提出的问题 |
| **Key（键）** | "我有什么信息可被找到" | 文档的索引标签 |
| **Value（值）** | "找到之后给我什么内容" | 文档的正文内容 |

> 💡 一句话记法：**Q 拿着问题去问各个 K，命中后用 V 加权汇总**——注意力打分 = 用 Q 与每个 K 计算相关度，加权求和 = 按相关度把 V 汇总起来。

**【深入原理 · 二】从注意力到完整 Transformer 模块**：

单次注意力只能捕捉一种关系，因此需要**多头注意力**——多组 Q/K/V 并行捕捉语法、指代、语义等不同关系，再拼接融合；之后依次接**残差连接**（缓解深层网络梯度消失）、**层归一化**（稳定训练）与**前馈网络**（非线性变换），逐层堆叠形成深层网络。

```chart flow
输入向量
多头自注意力
残差连接
层归一化
前馈网络
残差连接
层归一化
输出
```

**关键结论**：自注意力让每个位置都能直接"看到"任意位置，因此**不限制输入序列长度**——这是它相对 RNN（按顺序逐步传递、长距离信息易丢失）的根本优势。

**【实战/考试要点】**：高频陷阱：**"自注意力机制限制输入序列长度"是错误说法**；限制长度的是"上下文窗口"（工程上限）。多头注意力、残差连接、层归一化属 Transformer 标准组件，认识即可。

### 1.7 Token 与分词（Tokenization）

> **导读**：Token 是模型处理文本的"最小单位"。为什么"一个中文字 ≈ 1-2 token，一个英文单词 ≈ 1-3 token"？因为模型不是按字或词切分，而是按词表切分。

**【直观解读】**：分词将文本切分为词表中的一个或多个 Token：常见词通常对应单个 Token，生僻词或罕见表达则可能被拆分为多个 Token。

**【深入原理】**：主流模型普遍使用 **BPE（Byte Pair Encoding，字节对编码）** 等子词算法构建词表：先统计高频相邻片段，反复合并出现频率最高的"字符对"，形成从整词到单字节的多级 Token。其优势：① 词表规模可控；② 任意文本均可被覆盖（生僻词拆成子词也能表示）；③ 英文常见词多为 1 个 Token，罕见词或中文单字可能拆成多个。

**【实战/考试要点】**：计费与窗口均按 **token 数**计；同样内容因模型词表不同 token 数可能不同。发送长文本前可先用 tokenizer 统计长度，避免超窗被截断。

### 1.8 上下文窗口（Context Window）

> **导读**：上下文窗口限定了模型单次输入所能容纳的最大 Token 数量。窗口容量有限，超出部分会被截断。

**【直观解读】**：上下文窗口是输入与输出**共用**的 Token 预算。例如 8K 窗口下，若输入占用 6K Token，则输出最多剩余 2K Token。

**【深入原理】**：窗口是模型在预训练时设定的**最大序列长度上限**，与注意力计算量直接相关。超过窗口的输入会被截断（丢弃最远部分）或报错，而不会"自动记住"。长文本应用通过**滑动窗口、摘要压缩、检索相关片段**将内容纳入窗口范围；**上下文缓存**可复用重复前缀（如固定系统提示词）的计算结果，降低延迟与成本。

**【实战/考试要点】**：考点：窗口单位是 token，输入与输出总量不能超过窗口。RAG 先检索再拼装，本质就是把"最相关的知识"纳入窗口，而不是将整库文本全部塞入。误区：窗口大 ≠ 效果好，过长的无关上下文会稀释注意力、引入噪声。

### 1.9 参数规模与 Scaling Law（缩放定律）

> **导读**：为什么模型要追求"大"？因为数据、算力、参数同步增长时，模型能力会稳定提升——这就是缩放定律。

**【直观解读】**：缩放定律可用"盖楼"类比：材料（数据）、施工（算力）与楼层（参数）需同步增加，楼才能越盖越高；只加楼层而不加材料，楼就会倾斜。对应到模型：仅扩大参数规模而数据与算力不足，能力提升将受限。

**【深入原理】**：缩放定律（Scaling Law）指出：在合理范围内，模型最终效果随**参数量、训练数据量、计算量**三者的幂律增长而提升，三者需大致同步放大。Qwen2.5 提供 0.5B→72B 多个规格，正是让用户按资源与任务复杂度选择合适的"规模档位"。

**【实战/考试要点】**：模型能力是**参数 × 数据 × 算力**共同作用的结果，**参数多不是唯一因素**。资源有限时选小参数开源模型（可本地部署），追求能力上限时用大参数模型或 API 商业版。误区："参数越大一定越好"——还需看数据质量与训练充分度。

### 1.10 大模型基础常见误区

| 误区 | 正解 |
|------|------|
| "自注意力机制限制输入序列长度" | ❌ 自注意力不限制长度，限制长度的是上下文窗口 |
| "模型输出每次不同 = 代码有 Bug" | ❌ 采样本身具有随机性，属正常现象 |
| "调高 temperature 能让模型更聪明" | ❌ 只会让输出更随机，不会增加知识或能力 |
| "训练后模型还能自动学会新知识" | ❌ 知识截止、参数冻结，需 RAG / 微调补充 |
| "上下文窗口只限制输入、不限制输出" | ❌ 输入 + 输出共用 token 预算 |
| "参数越多模型一定越好" | ❌ 还需数据、算力与训练充分度匹配 |

**考前速记**：

## 2. 提示工程

### 2.1 什么是提示工程

> **导读**：提示工程的核心，是通过更清晰、更结构化的输入方式，引导模型稳定输出符合预期的结果。对同一任务而言，提示词的设计质量往往直接决定回答效果。可以理解为：同一问题，提问方式不同，答案质量差异显著——提示词即"如何向模型提问"的设计。

**核心概念**：提示工程（Prompt Engineering）是通过精心设计输入文本，引导大模型生成期望输出的技术。

**【直观解读】**：提示工程的核心是"把需求表述清楚"。模型能力再强，若需求表达含糊，也难以给出理想结果；提示词设计得当，同一模型可以发挥出完全不同的水平。

**高频考点**：
- 提示词对输出质量有**决定性影响**：同一模型 + 不同提示词 = 不同效果。
- 优化顺序：**先提示词 → 再 RAG → 最后微调**（微调是最后手段）。

### 2.2 提示词设计原则

> **导读**：六大原则是提示词设计的"基本功"，几乎所有场景题都围绕它们出题。

| 原则 | 说明 | 示例 |
|------|------|------|
| **明确角色** | 告诉模型"你是谁" | "你是一名小学科学老师" |
| **明确任务** | 清晰描述要做什么 | "请用 200 字科普保护环境的重要性" |
| **明确受众** | 指定目标读者 | "面向 6-12 岁小学生" |
| **提供示例** | 用样例引导输出格式 | Few-shot：给 2-3 个问答范例 |
| **设定约束** | 限制输出范围 | "只使用小学四年级能理解的词汇" |
| **分步引导** | 复杂任务拆解 | "先分析问题，再给出方案，最后总结" |

**【直观解读】**：一份完整的提示词应明确以下要素：模型扮演的角色、需要完成的任务、面向的受众、期望的输出格式，以及允许的范围与约束。

**【深入原理】**：这些原则的本质是给模型"补足决策信息"。模型生成是概率过程，信息越充分、约束越明确，正确答案的概率分布越集中。其中"角色"激活模型在训练中见过的角色模式，"示例"提供输出格式的锚点，"分步引导"把长任务拆解为多个短步骤，降低中间推理失误的累积概率。

**【实战/考试要点】**：六项原则需组合使用——只写"任务"而不写"角色/受众/约束"是输出跑偏的常见原因；场景题中"生成内容不相关"的第一对策就是补充上下文与约束。

### 2.3 核心技巧

> **导读**：五个核心技巧对应五类高频场景：简单任务、格式任务、推理任务、全局规则、随机性控制。

| 技巧 | 说明 |
|------|------|
| **Zero-shot（零样本）** | 不提供示例，直接提问。适用于简单任务 |
| **Few-shot（少样本）** | 提供 2-5 个示例，模型模仿格式和风格输出 |
| **思维链（Chain-of-Thought, CoT）** | 要求模型展示推理过程，显著提升复杂推理准确率。如加上"让我们一步一步思考" |
| **System Prompt（系统提示词）** | 设定模型全局行为和角色，优先级高于用户提示词 |
| **Temperature（温度参数）** | 控制输出随机性。**值越高越随机/有创意，值越低越确定/保守** |

**【直观解读】**：Zero-shot 指不提供示例直接提问；Few-shot 指先给出 2-5 个示例，再让模型仿照格式与风格作答；CoT 要求模型显式展示推理步骤；System Prompt 用于设定模型全局行为与角色，优先级高于用户提示词；temperature 控制输出随机性。

**【深入原理】**：
- **Few-shot 为什么有效**：示例让模型通过**上下文学习（In-Context Learning）** 对齐任务分布——识别"该输出什么格式、什么口吻"，本质是注意力机制对示例模式的隐式模仿。
- **CoT 为什么能提升推理**：将推理过程显式写出，等于把大问题拆成多步小问题逐步求解，避免"一步到位"的高错误率；对**复杂推理与数学题**提升尤其显著。
- **System Prompt 优先级最高**：系统消息先注入、再拼接用户消息；全局指令（角色、规则、格式）优先于单轮用户指令，但需注意**越狱/提示注入**可能尝试绕过它。

**【实战/考试要点】**：简单任务用 Zero-shot 即可；格式/风格敏感任务用 Few-shot（2~5 个示例）；CoT 适合逻辑推理与数学；System Prompt 放"角色 + 全局规则 + 输出格式"，用户消息放具体任务（角色与任务分离）。

### 2.4 常见问题与对策

> **导读**：模型回答偏离预期，多数情况下源于提示词信息不足。下表给出"问题 → 原因 → 对策"的对应关系，场景题可直接套用。

| 问题 | 原因 | 对策 |
|------|------|------|
| 输出过于学术化 | 未指定受众 | 明确角色和读者年龄层 |
| 生成内容不相关 | 提示词信息不足 | 补充具体上下文和约束条件 |
| 文学翻译失去意境 | 统一提示词无法兼顾多种风格 | **按文本类型拆分提示词**，每类单独定制 |
| 写出了错误的品牌/产品 | 信息不足导致模型自行填充 | 在提示词中明确品牌名称、产品型号 |

**【直观解读】**：模型回答偏离预期，通常不是模型能力问题，而是提示词信息不足——缺少角色、受众、背景与示例时，模型只能依赖猜测补全。

**【深入原理】**：输出不相关的根本原因是**概率分布发散**：信息不足时，正确内容与错误内容的概率接近，模型可能随机落在错误一侧。对策的本质是"收窄概率分布"——补充上下文、设置约束、给出示例，使正确答案的概率显著提升；对知识型内容（品牌、型号、日期）尤其要显式给出，否则模型可能自行编造填充。

**【实战/考试要点】**：场景题套路：看到"回答跑偏 / 过于学术 / 编造品牌"，优先选"补充上下文与约束、明确受众、显式给出事实信息"，而不是"换模型、调高 temperature"。

### 2.5 进阶技巧

> **导读**：进阶技巧面向工程化与 Agent 场景：既要"边推理边行动"，也要"格式可控、版本可管"。

| 技巧 | 说明 |
|------|------|
| **ReAct（推理+行动）** | 思考（Thought）→ 行动（Action，调用工具）→ 观察（Observation）交替进行，适合需要外部信息的复杂任务 |
| **Self-Consistency（自洽性）** | 对同一问题多次采样、取出现次数最多的答案，可显著提升推理类题目准确率 |
| **结构化输出（JSON Mode）** | 要求模型严格按 JSON 格式输出，便于程序解析，是构建 Agent 应用的基础能力 |
| **角色与任务分离** | 系统提示词设定角色与全局规则，用户提示词承载具体任务，二者职责清晰、互不混淆 |
| **提示词版本管理** | 提示词会随调试持续迭代，使用平台（如百炼）的版本管理能力，避免线上行为不可控 |
| **多模态提示** | 图文结合输入（截图+问题）可显著提升文档、表格类任务的准确性 |

**【直观解读】**：ReAct 将推理与行动交替进行；Self-Consistency 对同一问题多次采样并取出现次数最多的答案；JSON Mode 要求模型严格按 JSON 格式输出，便于程序解析。

**【深入原理】**：Self-Consistency 的原理是"多次独立推理的投票结果优于单次猜测"：多次采样相当于多次独立推理，推理链不同但结论一致时可信度显著更高；代价是延迟与成本上升。注意它需要**较高 temperature** 才能采出多样化的推理链——低温度下多次结果趋同，投票失去意义。ReAct 将"推理"与"工具调用"显式交替，使模型可以"查了再想、想了再查"，是 Agent 的核心工作模式之一。

**【实战/考试要点】**：Self-Consistency 提升的是**推理类题目**准确率；JSON Mode 用于程序对接（要求"只输出 JSON，不要多余解释"，配合 Schema 校验）；多模态提示对文档、表格、截图类任务提升明显。

### 2.6 提示词的通用结构

> **导读**：一个"标准提示词"通常由五个模块构成。先记结构，再学技巧，写提示词就不容易遗漏要素。

**推荐结构**：`角色 + 任务 + 上下文 + 示例 + 输出格式与约束`

| 模块 | 作用 | 示例 |
|------|------|------|
| **角色（Role）** | 定义身份与专业视角 | "你是一名资深律师" |
| **任务（Task）** | 一句话说清要做什么 | "审查这份合同的风险条款" |
| **上下文（Context）** | 提供背景材料与事实 | 附上合同正文、相关法条 |
| **示例（Example）** | 给 1~3 个范例对齐输出 | "输出格式如下：…" |
| **约束（Constraint）** | 限制长度/风格/禁止项 | "不超过 300 字，列出 3 条风险" |

**【实战/考试要点】**：结构化提示词便于**程序化组装与版本管理**——企业实践常用模板 + 变量拼接（如 LangChain 的 Prompt Template，支持变量插值），考试会考察这一点。

### 2.7 提示工程方法论与常见误区

**工程化流程**：`明确任务 → 起草提示词 → 小样本测试 → 分析失败案例 → 迭代优化 → 版本固化 → 回归验证`

**【直观解读】**：提示词优化与代码调试类似：用一批测试输入运行，定位失败原因，再有针对性地调整角色设定、补充示例、增加约束，而非盲目试错。

**评估提示词效果**：用**固定测试集**对比不同版本提示词的输出质量（人工打分或 LLM-as-Judge），量化迭代收益；上线后结合线上反馈持续回归。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "提示词越长越好" | ❌ 无关信息会稀释注意力，应只放与任务相关的内容 |
| "所有要求塞进一句话" | ❌ 应分模块组织：角色 / 任务 / 上下文 / 示例 / 约束 |
| "换了模型提示词不用改" | ❌ 不同模型训练分布不同，提示词需按模型微调 |
| "温度越高效果越好" | ❌ 事实类任务应调低 temperature |
| "提示词写一次就定型" | ❌ 应持续迭代并用版本管理控制线上行为 |
| "System Prompt 能完全防住用户指令" | ❌ 存在提示注入 / 越狱风险，仍需安全防护 |

### 2.8 提示词分隔符（Delimiters）

> **导读**：分隔符用显式标记把提示词切成"指令、上下文、示例、待处理内容"等区块，让模型分清"哪些是要求、哪些是数据"，也便于程序模板化组装与解析。

**核心概念**：提示词分隔符是用特殊符号/标签把提示词不同部分显式分隔开来的写法，常见形式如三引号（"""..."""）、XML 标签（<context>...</context>）、Markdown 代码块、分隔线（---）等。

| 项目 | 说明 |
|------|------|
| **作用** | ① 结构化：指令与数据边界清晰；② 防注入：把用户/检索内容当作"数据"而不是"指令"；③ 易解析：程序可按标记提取输出 |
| **常见形式** | 三引号（"""..."""）、XML 标签（<context>...</context>）、Markdown 代码块、分隔线（---）、自定义 token |
| **适用场景** | 注入 RAG 检索片段、给 Few-shot 示例分组、审阅多段文档、多角色对话切分 |
| **易错点** | 前后分隔符不一致；待处理内容里恰好出现相同分隔符（冲突）；只加分隔符却不说明各段含义 |

**简短示例**：

    请依据下面的上下文回答问题。
    <context>
    {检索到的文档内容}
    </context>
    <question>
    {用户问题}
    </question>
    只依据 <context> 内容回答，找不到依据就说"资料中未提及"。

**【实战/考试要点】**：分隔符不是"花架子"，它的核心价值是**把数据与指令隔离**（间接防提示注入）；改错题看到"把用户原文直接拼进提示词且无任何标记"，应改为"用分隔符包裹并声明其角色"。

### 2.9 意图分类：流程、提示词设计与结果处理

> **导读**：意图分类是把用户输入先归入预定义意图，再路由到不同处理分支的前置环节——相当于客服系统的"分诊台"。

**基本流程**：

    定义意图清单 → 设计分类提示词 → 模型输出意图标签 → 置信度判断
    → 命中：进入对应分支 / 低置信度：澄清追问 / 未匹配：兜底意图 / 越界：拒绝或转人工

| 环节 | 要点 |
|------|------|
| **分类提示词设计** | 写清"角色 + 意图清单（每个意图一句话定义 + 1 个示例）+ 输出格式（如 JSON：{"intent":"...","confidence":0.9}）+ 低置信度处理规则" |
| **边界案例** | 一句话含多个意图（取主意图或拆解）；字面相似意图不同（"我要退款" vs "我要退换"）；清单外新意图；含攻击/越权请求 |
| **结果处理** | 置信度低于阈值 → 追问澄清；无匹配 → 走兜底意图或转人工；高风险 → 拒绝并留痕 |

**与相近方法区别**：意图分类是"先分类、再路由"的**前置分流**，与 RAG 检索（找知识）、Function Calling（抽参数执行）解决的问题不同；三者常串联使用：先分类 → 再检索/调工具 → 最后生成。

**【实战/考试要点】**：分类提示词必须含**意图清单 + 输出格式 + 低置信度处理**三要素（缺一即为不完整提示词）；"分类后不做置信度判断直接执行"是常见错误选项。

### 2.10 文档审阅：任务拆解、评价维度与结构化输出

> **导读**：让模型审阅文档，关键是先定"审什么、按什么维度评、输出什么结构"，而不是笼统说"帮我看看这份文档"。

**任务拆解三步**：

1. **定目标**：找风险 / 查合规 / 提质量 / 抓错误——目标决定维度；
2. **定维度**：如合同审阅常用"主体、金额、期限、违约、争议解决、合规"；通用维度有"正确性、完整性、一致性、合规性、可读性、风险等级"；
3. **分批审阅**：长文档先按章节/切片分段，逐段审阅后汇总，避免一次审全篇漏项。

**结构化输出示例**：

    [
      {"位置": "第3条", "原文": "...", "问题": "违约金比例未约定", "严重度": "高", "建议": "补充违约金上限与计算方式"},
      {"位置": "第7条", "原文": "...", "问题": "争议解决方式与正文不一致", "严重度": "中", "建议": "统一为仲裁条款"}
    ]

**【实战/考试要点】**：审阅提示词要同时给"维度定义 + 输出字段 + 严重度分级 + 引用原文定位"；只输出"合格/不合格"二分类通常不能满足业务需求；长文档必须分段，分段后还要注意上下文贯通（跨段条款冲突）。

### 2.11 自动文档修订：按审阅结果改文档

> **导读**：自动修订不是"让模型自由润色"，而是**依据审阅结果、只改该改之处、保留原文并留痕**，避免模型无依据地大改。

**核心原则**：

| 原则 | 说明 |
|------|------|
| **保留原文** | 未在问题清单中的内容一律不动，避免"顺手润色"破坏原意与格式 |
| **标记修改** | 输出"修改前 / 修改后 / 修改理由"三段式或 diff/修订标记，便于人工复核与回退 |
| **避免无依据改写** | 只处理审阅明确指出的问题，禁止编造原文没有的内容（如补一个不存在的条款） |

**基本流程**：审阅输出问题清单 → 把"原文片段 + 对应问题"一并交给模型 → 要求按问题逐条修订并输出三段式 → 人工复核 → 回写文档。

**【实战/考试要点】**：自动修订必须**有依据、留痕、可回退**；"让模型直接重写全文"是高风险错误做法（会丢格式、改语义、引入幻觉）；修改后要回读校验，确认只改了目标问题。

## 3. RAG 检索增强生成

### 3.1 什么是 RAG

> **导读**：大模型的参数知识存在时间边界，也缺乏对企业私有知识的天然访问能力。RAG 通过"先检索、后生成"的方式，将外部知识库与模型相结合，从而提升回答的准确性、时效性与可追溯性。
>
> 可类比为"开卷考试"：模型在作答前先从企业知识手册中检索相关内容，再依据检索结果作答，而非仅凭训练参数中的记忆。

**核心概念**：RAG（Retrieval-Augmented Generation，检索增强生成）将信息检索与大模型结合，先检索再生成，让模型能够基于外部知识回答问题。

**RAG 工作流程**：

```
用户提问 → 文档解析 → 文本切片 → 向量化 → 向量检索 → ReRank重排 → LLM生成回答
```

```chart flow
用户提问
文档解析
文本切片
向量化
向量检索
ReRank 重排
LLM 生成回答
```

**【直观解读】**：RAG 的运作分两步：离线阶段将知识库切分为文本块并向量化建库；在线阶段对用户问题执行检索召回，将命中的相关内容与问题一并交给模型生成回答。

**高频考点**：
- RAG 解决三大问题：**知识过时、私有知识、可追溯性**（回答可附引用来源）。
- 适用场景：知识频繁更新、需要引用出处、企业私有文档问答。
- 与微调的关系：**优先用 RAG**，微调是补充手段（详见 3.6）。

### 3.2 文档解析

> **导读**：知识库中的原始文件（PDF、Word、网页等）无法直接检索，需先解析为检索器与模型均可处理的文本。

| 知识点 | 说明 |
|--------|------|
| **支持格式** | PDF、Word、Markdown、HTML、Keynote 等 |
| **复杂文档处理** | 含表格、流程图的文档，可先转换为 PDF 再用解析工具处理 |
| **Markdown 优于纯文本** | Markdown 保留标题、列表等**结构化信息**，比纯文本更利于语义理解 |
| **自定义 Reader** | 对于特殊格式（如 Keynote），可开发自定义 Reader 进行解析 |

**【直观解读】**：解析器将各类格式的文档转换为文本。解析质量——是否保留标题、表格等结构信息——直接决定后续切片的合理性与检索的准确度。

**【深入原理】**：解析的目标是**保留结构、去除噪声**：标题、层级、表格、列表是重要的语义锚点，保留它们能让切片更合理、向量更准确；扫描件需要 OCR 转文字；复杂排版（多栏、页眉页脚）需要版面分析。常用工具：DashScopeParse（阿里云文档解析服务）、Unstructured、PDFPlumber 等。

**【实战/考试要点】**：考点"文档解析时直接传原始路径" ❌——需先解析为结构化文本再入库；含表格/流程图的文档先转 PDF 再解析；特殊格式（Keynote 等）开发自定义 Reader。

### 3.3 文本切片（Chunking）

> **导读**：切片是将长文档切分为"适合检索的小段"。切分质量直接决定"该找到的能否被找到、找到的上下文是否完整"。

| 知识点 | 说明 |
|--------|------|
| **切片目的** | 将长文档切分成适合检索的小段，每段称为一个 chunk |
| **切片大小** | 需根据场景调整。切片太大会稀释语义，切片太小会丢失上下文 |
| **重叠窗口** | 相邻切片之间保留一定重叠，避免关键信息被切断 |
| **分割策略** | 可按段落、句子、固定长度或语义边界进行分割 |

**【直观解读】**：切片粒度过大，chunk 内语义混杂，检索命中后噪声较多；粒度过小，关键信息可能被切断、上下文不完整。相邻切片之间保留一定重叠，可避免关键内容恰好落在切分边界上。

**【深入原理】**：向量检索的召回对象是**整个 chunk**，因此 chunk 的粒度决定了召回单元的信息完整度。**固定长度切片**实现简单，但可能在句子中间切断；**按段落/标题层级切片**更贴合语义边界（Markdown 结构尤其适合）；**重叠窗口**保证跨界信息在相邻块中至少完整出现一次。切片大小没有万能值，需结合 Embedding 模型的输入上限与下游模型的上下文窗口综合权衡。

**【实战/考试要点】**：高频陷阱：**"切片越大越好" ❌**——太大稀释语义、命中率下降；太小丢失上下文。召回不足时先查切片策略，再考虑查询改写、混合检索、重排（见 3.7 排查顺序）。

**文本分割方法对比**：

| 方法 | 做法 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **固定长度分割** | 按固定 token/字符数等长切分 | 实现简单、可预测 | 会在句子/语义中间切断 | 通用文本的初步切分 |
| **按句分割** | 以句号等标点为边界切分 | 语义单元完整、实现简单 | 长句/段落上下文可能被拆散 | 短文本、FAQ |
| **按段分割** | 按段落/空行切分 | 天然贴合语义边界 | 段落过长或过短时粒度失衡 | Markdown、结构化文档 |
| **递归分割** | 优先按标题→段落→句子逐级下钻，超长再细分 | 兼顾结构与长度 | 需文本有层级结构 | 有标题层级的文档 |
| **语义分割** | 用模型判断语义边界后切分 | 语义最连贯 | 成本高、实现复杂 | 高价值、结构复杂的知识库 |

> 💡 选型口诀：**有标题层级 → 递归/按段；短问答 → 按句；语义要求高 → 语义分割；快速原型 → 固定长度 + 重叠**。无论哪种方法，都建议加**重叠窗口**防止跨界信息被切断。

### 3.4 向量化与 Embedding

> **导读**：计算机无法直接理解自然语言。向量化将文本转换为数值向量，使语义相近的文本在向量空间中彼此靠近。

| 知识点 | 说明 |
|--------|------|
| **Embedding** | 将文本转换为一串数字（高维向量），语义相近的文本向量也相近 |
| **Embedding 模型** | 专门用于文本向量化的模型，如 text-embedding-v3 |
| **向量维度** | 常见有 768、1024、1536 维等，维度越高表达能力越强但也越占资源 |
| **向量数据库** | 用于存储和检索向量的专用数据库，支持高效相似度搜索 |

**【直观解读】**：Embedding 将每个文本块映射为高维空间中的一个向量，语义相近的文本向量距离更近；向量检索的本质，即查找与问题向量最相近的一批文本向量。

**【深入原理】**：
- **Embedding 怎么训练**：采用**对比学习**训练——让"语义相近的文本对"在向量空间中更近、不相关的更远（如阿里云 text-embedding-v3），输出固定维度的向量。
- **相似度怎么算**：**余弦相似度**（看方向夹角，最常用）、**欧氏距离**（看直线距离）、**点积**（兼顾方向与长度）。
- **向量数据库做什么**：存储海量向量并建立索引（如 HNSW、IVF 等近似最近邻算法），支持毫秒级"最近邻查找"，避免暴力两两比较。
- 注意：Embedding 模型与生成模型是两回事——前者将文本转换为向量，后者生成回答。

**【实战/考试要点】**：检索质量差的三大原因：① Embedding 模型不够好 ② 切片策略不当 ③ 文档格式丢失结构信息。相似度首选**余弦相似度**；维度越高表达力越强、资源开销越大。实践流程：离线把每个 chunk 向量化入库；在线把问题向量化后做最近邻检索。

### 3.5 检索与召回

> **导读**：检索阶段解决"哪些文档与问题相关"：先保证"找得够多"（召回），再保证"找得够准"（精排）。

| 知识点 | 说明 |
|--------|------|
| **Top K** | 检索返回的最相关文档数。**增大 Top K 可提高召回率**，但可能引入噪声 |
| **相似度计算** | 常用方法：**余弦相似度**（最常用）、欧氏距离、点积 |
| **召回率 vs 精确率** | 宽松检索 → 高召回率低精确率；严格检索 → 低召回率高精确率 |
| **ReRank（重排）** | 对初步检索结果进行二次精排，过滤低相关度切片。**首轮注重召回，重排注重精确** |
| **检索质量差的原因** | ① Embedding 模型不够好 ② 切片策略不当 ③ 文档格式丢失了结构信息 |

**【直观解读】**：检索遵循"先召回、再精排"的两阶段策略：第一轮以低成本方式召回 Top K 条候选，第二轮用更精细的重排模型（ReRank）对候选重新排序，将高相关片段前置、低相关片段滤除。

**【深入原理】**：
- **Top K 与召回率**：K 越大，候选越多，相关文档"漏网"概率越低（召回率↑），但无关文档也越多（精确率↓、噪声↑），同时消耗更多上下文窗口与 token 成本。
- **ReRank 为什么需要**：向量检索第一轮排序基于"向量距离"这一近似度量，精度有限；ReRank 用更强的**交叉编码器**（将 query 与每个候选文档拼接后一起编码打分）做精确排序，计算量大但只对 Top K 条执行，兼顾质量与成本。
- **设计哲学**：**首轮注重召回（Recall），重排注重精确（Precision）**。

**【实战/考试要点】**：高频陷阱：**"Top K 越小检索越精确" ❌**——太小会漏掉相关文档（召回不足）；**"放宽检索阈值能提高精确率" ❌**——放宽 → 召回率↑、精确率↓。检索到但答错 → 问题在"上下文是否真正进入模型"（拼装/截断），不在检索。

### 3.6 RAG vs 微调

> **导读**：选 RAG 还是微调，是方案设计的第一问。一句话：**要知识 → RAG；要风格/行为 → 微调**。

| 对比维度 | RAG | 微调 |
|----------|-----|------|
| 知识更新 | 更新知识库即可，实时生效 | 需重新训练 |
| 适用场景 | 需要引用外部知识、知识频繁更新 | 需要改变模型行为风格、领域适配 |
| 成本 | 较低 | 较高（需要 GPU 和时间） |
| 可解释性 | 高（可追溯到检索来源） | 低（黑盒） |
| **优先评估** | 在微调前，**应优先尝试提示词优化和 RAG** | 只有提示词+RAG 无法满足需求时才考虑微调 |

**【直观解读】**：知识类需求应优先选择 RAG：知识更新时只需更新知识库即可实时生效，成本低且可溯源；微调用于行为与风格层面的适配，成本高、周期长，应作为补充手段。

**【深入原理】**：二者解决问题的维度不同：RAG 解决**知识获取**（从哪获取事实），微调解决**行为适配**（采用什么风格、什么领域话术）。RAG 不改变模型参数，因此不改变模型行为；微调不注入实时知识，因此不解决知识时效问题。

**【实战/考试要点】**：高频陷阱："微调是解决一切问题的最优方案" ❌——应**先提示词优化 → 再 RAG → 最后微调**。场景题：知识库更新频繁 → 选 RAG；需要固定客服话术/领域口吻 → 考虑微调。RAG 可解释性高（引用可溯源），微调是黑盒。

### 3.7 RAG 进阶技术

> **导读**：进阶技术旨在提升检索质量：问题表述不清晰时先做查询改写；字面与语义不匹配时借助 HyDE 搭桥；既要精确匹配又要语义匹配时采用混合检索。

| 技术 | 说明 |
|------|------|
| **查询改写（Query Rewriting）** | 先让 LLM 把口语化、指代不清的问题改写为适合检索的书面表达，提升召回质量 |
| **HyDE（假设性文档嵌入）** | 先让 LLM 生成一段"假想答案"，再用假想答案做向量检索，提高语义匹配度 |
| **混合检索（Hybrid Search）** | 关键词检索（如 BM25）+ 向量检索融合，兼顾**精确匹配**（错误码、型号、编号）与**语义匹配** |
| **父子分块（Parent-Child Chunking）** | 用小块做检索（精确命中），命中后把所属大块（完整上下文）喂给模型 |
| **元数据过滤** | 按来源、时间、权限、文档类型等元数据先过滤候选集，再做向量排序 |
| **上下文压缩** | 检索结果过多时压缩或截断，只保留与问题相关的片段，控制 Token 成本 |
| **引用溯源（Citation）** | 回答中标注引用来源切片，提升可信度，便于人工核验 |

**【直观解读】**：查询改写将口语化、指代不明的问题改写为适合检索的规范表述后再检索；HyDE 先生成一段假设性答案，再以其进行向量检索；混合检索融合关键词匹配与语义匹配两种方式；父子分块用小粒度文本块完成精确命中，再回溯至父级大块提供完整上下文。

**【深入原理】**：
- **查询改写**：用户常问"它多少钱""这个怎么用"，指代不明、口语化，直接检索匹配度差；先用 LLM 改写为完整书面查询（必要时带上多轮对话上下文）可显著提升召回。
- **HyDE**：把"用问题找文档"变成"用假设性答案找文档"——答案与文档在语义上往往比问题与文档更接近，检索命中率更高，代价是多一次 LLM 生成。
- **混合检索**：BM25 按字面词频匹配，擅长错误码/型号/编号等**精确 token**；向量检索擅长语义相近但字面不同的表达；二者分数加权融合（如 RRF 倒数排名融合）可兼顾两者。
- **父子分块**：小块检索定位精准（不至于整篇大块都"沾边"），但小块上下文可能不足以回答问题，命中后回溯到父块（更大单元）一并喂给模型。

> 💡 召回不足的排查顺序：**切片策略 → 查询改写 → 混合检索 → 重排**，而不是一上来就换模型。

**【实战/考试要点】**：场景题关键词对应：口语化问题 → 查询改写；精确编号/型号 → 混合检索；检索碎片化、上下文不全 → 父子分块；回答冗长成本高 → 上下文压缩；需要审计/可信 → 引用溯源。

**进阶检索技术（二）：句子窗口、自动合并、标题改写、表格增强**

| 技术 | 解决问题 | 一句话原理 |
|------|----------|-----------|
| **句子窗口检索** | 小块命中精准但上下文不足 | 先按"句子"精确检索，命中后再把该句**周围窗口**的相邻句一并取回 |
| **自动合并检索** | 检索碎片化、多个小块同属一段 | 召回多个小块后，把属于同一父文档/相邻区域的块**自动合并**成完整上下文 |
| **标题改写优化** | 文档标题与内容/查询词不匹配 | 检索前用 LLM 把文档标题或查询改写为更易匹配的规范表达 |
| **表格内容增强** | 表格被切碎后检索不到 | 把表格转成保留结构的文本，并生成"表格摘要/问答对"作为补充检索单元 |

**句子窗口检索**：先按句子建立索引，用户问题命中某句后，按窗口大小（如前后各 N 句）把邻句一起返回。**与固定长度切片的区别**：固定长度按字符数切、易切断；句子窗口以句子为最小检索单元、再向外扩窗，兼顾"精确命中 + 上下文完整"。**适用**：PDF 段落较长、需要精确到句且保留邻句语义的问答。**误区**：窗口越大不一定越好，窗口过大会把无关句也带进来、稀释注意力。

**自动合并检索**：召回阶段仍用小块（精确），生成前把"同属一个父文档/相邻区块"的多个小块按顺序合并，还原完整段落。**与父子分块的区别**：父子分块是"小块命中→回取预定义的父块"；自动合并是"多个命中块按来源/位置动态合并"，更适合命中块分散在相邻区域的情况。**适用**：长报告、合同条款跨段引用。**误区**：只召回一个小块就直接回答，缺少合并步骤，导致"只见树木不见森林"。

**标题改写优化**：文档标题若写得泛（如"关于xxx的通知"），用户用具体词检索时匹配度低；先用 LLM 把标题改写成"包含主题、对象、动作"的规范表述，或用 LLM 改写用户查询后再检索。**适用**：标题不规范的历史文档、公文、制度库。**误区**：改写不能编造原文没有的信息，只能做措辞规范化与补全指代。

**表格内容增强**：表格被按行/按单元格切碎后语义丢失，检索难命中。增强手段——① **表格转文本**：转成 Markdown/HTML 保留行列结构；② **结构保留**：切片时按"完整表格"为边界，不把表格切断；③ **表格问答**：为每个表格预生成"这个表回答什么问题"的摘要或问答对，作为额外检索单元；④ **检索问题**：用户问数值/对比类问题时，优先召回表格摘要再定位原表。**适用**：财务报表、规格参数表、对比表。**误区**：把表格当普通文本按固定长度切分，导致行列结构被打散。

**检索方案选择速查**：

| 现象 | 优先尝试 |
|------|----------|
| 命中句子太短、上下文不足 | 句子窗口检索 / 父子分块 |
| 同一段落被切成多个块、回答碎片化 | 自动合并检索 |
| 历史文档标题不规范、检索不到 | 标题改写优化 |
| 表格数据检索不到或答错数值 | 表格转 Markdown + 表格问答增强 |

### 3.8 RAG 评估指标

> **导读**：评估 RAG 要覆盖链路两端：检索端关注"该找的有没有找到、找到的是否都相关"，生成端关注"回答是否忠于资料、是否切题"。

| 指标 | 衡量内容 | 说明 |
|------|----------|------|
| **Context Recall（上下文召回率）** | 相关文档是否被检索到 | 检索条件越宽松，召回率越高 |
| **Context Precision（上下文精确率）** | 检索结果中相关文档的占比 | 检索条件越宽松，精确率越低 |
| **Faithfulness（忠实度）** | 回答是否忠于检索内容 | 防止模型脱离上下文编造（幻觉） |
| **Answer Relevancy（答案相关性）** | 回答是否切题 | 评估答案与用户问题的匹配程度 |

> ⚠️ 高频陷阱：**放宽检索阈值 → 召回率↑、精确率↓**（对应"Context Recall 变高 / Context Precision 变低"）。

**【直观解读】**：四个指标分别回答四个问题：相关文档是否被检索到（Recall）→ 检索结果是否都相关（Precision）→ 回答是否忠于检索内容（Faithfulness）→ 回答是否切题（Relevancy）。

**【深入原理】**：四个指标分属链路两端：Context Recall / Context Precision 评估**检索阶段**（用"问题-相关文档"标注集衡量 Top K 结果）；Faithfulness / Answer Relevancy 评估**生成阶段**（用"问题-回答-参考文档"衡量生成质量）。RAG 的幻觉主要靠 Faithfulness 把关——模型在参考文档中找不到依据却强行作答时，忠实度下降。

**【实战/考试要点】**：高频陷阱组合：放宽检索阈值 → **Context Recall ↑、Context Precision ↓**（必考）。"检索到了但回答错误/编造" → 看 **Faithfulness**，问题出在生成阶段（如上下文未真正进入模型、或未约束"只能依据资料回答"）。

**RAGAS（RAG 专用评估框架）**：

> RAGAS（RAG Assessment）是开源 RAG 评估框架，把 RAG 拆成"检索端 + 生成端"分别打分（与 7.6 的 Ragas 工具对应，考试常把"指标含义"与"需要哪些输入"混在一起考）。

| 指标 | 评价对象 | 所需输入 | 如何解释 |
|------|----------|----------|----------|
| **Context Precision** | 检索端 | 问题 + 召回的上下文列表 + 相关标注 | 召回的上下文中"相关项占比"，高 = 找得准 |
| **Context Recall** | 检索端 | 问题 + 标准答案（ground truth）+ 召回上下文 | 标准答案中"能被召回内容支撑的比例"，高 = 找得全 |
| **Faithfulness** | 生成端 | 问题 + 召回上下文 + 模型回答 | 回答中"可被上下文支撑的比例"，高 = 少编造 |
| **Answer Relevancy** | 生成端 | 问题 + 模型回答 | 回答与问题的相关程度，高 = 不跑题 |
| **Answer Correctness** | 生成端 | 问题 + 标准答案 + 模型回答 | 回答与标准答案的一致程度，高 = 答得对 |

**指标高 ≠ 效果好的情况**：① 标注/标准答案本身质量差，指标被"假满分"抬升；② LLM-as-Judge 打分存在长度偏好、位置偏好，可能系统性虚高；③ 检索指标好但生成答错——链路没打通（上下文未真正进入模型）；④ 单点指标好但整体体验差（如答对了但格式乱、引用错位、成本过高）。**结论：RAGAS 用于"发现问题、横向对比"，不能替代人工抽检与线上效果评估。**

### 3.9 RAG 全链路实战拆解

> **导读**：将 3.2~3.8 串成完整流水线，明确"每一步发生了什么、哪一步最容易出问题"。

**离线建库（一次做好，多次复用）**：

```
文档收集 → 文档解析（保留结构） → 文本切片（含重叠） → 向量化（Embedding）
→ 写入向量数据库（同时存原文 + 元数据 + 向量）
```

**在线问答（每次请求都执行）**：

```
用户提问 →（可选）查询改写 → 问题向量化 → 向量检索 Top K（+元数据过滤）
→ ReRank 精排 → 拼装上下文 → 组装提示词 → LLM 生成 → 引用溯源输出
```

**各环节失败表现速查**：

| 现象 | 大概率原因 | 排查方向 |
|------|-----------|----------|
| 完全检索不到相关文档 | 切片过大/过小、Embedding 质量差 | 切片策略 → 查询改写 |
| 检索到但排序不对 | 相似度算法 / ReRank 缺失 | 混合检索 → 重排 |
| 检索到但回答仍错/编造 | 上下文未进入模型、提示词未约束 | 拼装逻辑 → 忠实度约束 |
| 回答冗长、成本高 | 召回过多、未压缩 | 调小 Top K / 上下文压缩 |
| 权限或时效问题 | 未做元数据过滤 | 元数据过滤 |

**【实战/考试要点】**：场景题定位口诀——**"检索不到 → 查切片与召回链路；检索到了但答错 → 查上下文是否进模型与提示词约束；答非所问 → 查 ReRank 与提示词"**。

### 3.10 RAG 常见误区

| 误区 | 正解 |
|------|------|
| "切片越大越好" | ❌ 太大稀释语义，太小丢上下文，需平衡 |
| "Top K 越小检索越精确" | ❌ 太小召回不足，可能漏掉相关文档 |
| "放宽检索阈值能提高精确率" | ❌ 放宽 → 召回率↑、精确率↓ |
| "RAG 一定能消除幻觉" | ❌ 只能缓解；模型仍可能脱离上下文编造，需 Faithfulness 评估与引用溯源 |
| "知识库更新后无需重建索引" | ❌ 新增/修改文档需重新解析、切片、向量化入库，检索才能命中新内容 |
| "向量检索能完美替代关键词检索" | ❌ 错误码/型号/编号等精确匹配仍需 BM25 等关键词检索（混合检索） |
| "检索结果越多越好" | ❌ 无关上下文会稀释注意力并增加 token 成本，需精排与压缩 |
| "微调能替代 RAG" | ❌ 微调不注入实时知识，知识类需求应优先 RAG |

**RAG 失败案例排查（场景题速查）**：

| 场景 | 判断 | 排查/对策 |
|------|------|-----------|
| 问"合同第 3 条违约金多少"答非所问 | 表格/条款被切碎，召回粒度过细 | 表格转 Markdown、按完整条款为边界切片 |
| 检索片段只给一句话，回答不完整 | 上下文不足 | 句子窗口 / 自动合并 / 父子分块 |
| 文档标题是"通知2024"，用户问"请假流程"检索不到 | 标题语义不匹配 | 标题改写优化 |
| 指标 Context Recall 高但 Faithfulness 低 | 检索找得到、生成没用好 | 检查上下文拼装与"只能依据资料回答"约束 |
| 新增文档后问答仍答旧内容 | 知识库未更新索引 | 重新解析、切片、向量化入库 |

## 4. Agent 智能体

### 4.1 什么是 Agent

> **导读**：如果说大模型负责理解与生成，那么 Agent 更强调感知、规划、调用工具与执行任务的闭环能力，能够将模型的能力从"回答问题"扩展到"完成任务"。

**核心概念**：Agent（智能体）是具有自主感知、规划和执行能力的大模型应用，能够使用工具、制定计划来完成复杂任务。

**【直观解读】**：用户将任务交给 Agent 后，它会自主完成以下动作：拆解任务步骤、检索所需资料、调用相关工具、核验中间结果，直至任务完成——而非仅以对话方式给出答复。

**【深入原理】**：Agent 的本质是"LLM 驱动的闭环执行系统"。普通对话是"一次问答"（输入→输出即结束），Agent 则反复执行「**感知（读入任务与工具结果）→ 规划（决定下一步）→ 行动（调用工具）→ 反思（评估是否达成目标）**」的循环，直到任务完成或达到轮数上限。支撑闭环的三项核心能力：

- **工具调用（Function Calling）**：模型输出结构化的"调用哪个工具、传什么参数"；
- **多步推理**：基于中间结果决定下一步动作，而非一次性给出答案；
- **记忆与上下文管理**：把历史结果与工具返回放回上下文，保证循环可持续。

**高频考点**：

| 考点 | 说明 |
|------|------|
| **Agent vs 普通 LLM 应用** | 普通应用"一问一答"；Agent 自主规划、多步执行，可调用外部工具 |
| **Agent vs RAG** | RAG 解决"知识不够"（查资料）；Agent 解决"事情做不完"（多步骤任务），两者常组合使用 |
| **闭环特征** | 判断是否 Agent 应用的关键：是否包含"规划-行动-观察"循环、是否调用工具 |

### 4.2 单 Agent 架构

> **导读**：单 Agent 将所有组件集成于同一实体：LLM 承担决策，工具负责执行，记忆保存过程信息，三者协同完成一项任务。

| 组件 | 作用 |
|------|------|
| **LLM（大脑）** | 理解任务、生成计划、做出决策 |
| **Planner（规划器）** | 判断何时调用哪个工具/Agent，拆解复杂任务 |
| **Tool（工具）** | Agent 可调用的外部能力（搜索、计算、API、数据库等） |
| **Memory（记忆）** | 存储对话历史和中间结果，支持多轮交互 |

**【直观解读】**：单 Agent 模式下，系统将完整任务交由一个 Agent 处理，由其自主循环执行"决策—行动—记录"，直至任务完成。

**【深入原理】**：各组件如何协作——

- **LLM** 每一轮都基于「系统提示词 + 当前任务 + 记忆 + 工具返回结果」生成下一步动作；
- **Planner** 可以是提示词里的一段规则（"先制定计划再执行"），也可以是独立模块（把任务拆成子任务清单）；
- **Tool** 通过 Function Calling 暴露给模型，每个工具都有一份 JSON-Schema 描述（名称、参数、用途）；
- **Memory** 短期记忆 = 对话历史窗口（受上下文窗口限制），长期记忆 = 外部存储（如向量库）。

**【实战/考试要点】**：

- 组件职责尽量解耦（规划、执行、记忆分离），便于定位问题；
- 工具返回结果必须"喂回"上下文，否则模型不知道上一步结果；
- 给模型"失败出口"：工具超时/报错时应能重试或换方案，而不是直接崩溃。

### 4.3 多 Agent 系统设计原则

> **导读**：多 Agent 系统可类比为多个部门协作：各部门职责清晰、权限独立，由统一调度中心分派任务；若职责或权限设计不当，将出现任务冲突与越权风险。

| 原则 | 说明 |
|------|------|
| **明确职责** | 每个 Agent 有清晰定义的职责边界，不重叠 |
| **独立凭据** | 不同 Agent **不应共用账号凭据**，存在安全隐患 |
| **中央调度** | 设计 Planner Agent 统一判断何时调用哪个 Agent |
| **避免全量注入** | 不要把所有 Agent 的知识一次性写在主 Prompt 中，应按需调用 |

**【直观解读】**：多 Agent 协作的关键在于：职责边界清晰、权限相互独立、由统一调度中心分派任务，否则容易产生职责重叠与越权风险。

**【深入原理】**：多 Agent 的两种典型协作模式——

- **集中式（主从）**：Planner/主管 Agent 统一拆解与调度，Worker Agent 各司其职、把结果交回主管汇总，结构清晰、易控；
- **分布式（对等）**：Agent 之间平级、互相通信传递结果，灵活但更难控制和排错。

通信方式通常有共享内存/消息队列/直接传递结构化结果。设计要点：避免 Agent 之间循环等待（死锁）、控制通信次数（每次通信都有 token 与延迟成本）、权限按 Agent 最小化授予。

**【实战/考试要点】**：考题常把"共用凭据"设为正确选项作为干扰——记住**独立凭据**是硬性安全要求；"主 Prompt 全量注入所有 Agent 知识"也是典型错误选项。

### 4.4 Agent 工具调用（Function Calling）

> **导读**：Function Calling 的机制是：模型并不直接执行工具，而是以结构化格式输出"调用哪个工具、传入哪些参数"，由应用程序负责实际执行。

| 知识点 | 说明 |
|--------|------|
| **工具描述（Schema）** | 用 JSON-Schema 定义工具的参数名称、类型、描述。**Schema 不完整会导致参数提取错误** |
| **参数提取** | Agent 从用户自然语言中提取结构化参数，填入工具调用 |
| **多轮工具调用** | 复杂任务可能需要多次工具调用，Agent 需要根据中间结果决定下一步 |

**【直观解读】**：模型负责输出工具调用意图（工具名与参数），应用程序负责校验并执行工具调用，二者职责分离。

**【深入原理】**：完整流程为「模型输出 `tool_calls` 结构（工具名 + 参数 JSON）→ 应用代码校验并执行工具 → 把执行结果作为新消息追加回上下文 → 模型继续生成」。参数提取的准确性取决于三件事：

1. **Schema 质量**：工具名、参数名、类型、描述、必填项越准确，提取越准；
2. **模型能力**：模型越强，越能理解"哪个信息对应哪个参数"；
3. **上下文清晰度**：用户表述含糊时，Agent 应主动追问澄清，而非自行猜测。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "模型会自己执行工具" | 模型只负责"提议调用"，执行工具的是应用代码 |
| "Schema 随便写写就行" | Schema 不完整/字段名含糊 → 参数提取错误（高频考点） |
| "参数必须一轮提取完" | 参数可分散在多轮对话中，Agent 应逐步收集、缺参时追问 |

### 4.5 常见 Agent 框架

> **导读**：Agent 框架预置了通用组件——循环执行逻辑、工具注册与解析、记忆管理等，开发者只需在此基础上定义工具与编写提示词，无需从零实现。

| 框架 | 说明 |
|------|------|
| **ModelScope-Agent** | 阿里开源 Agent 框架，支持工具调用和多轮对话 |
| **LangChain Agent** | 支持多种 Agent 类型（ReAct、OpenAI Functions 等） |

**【直观解读】**：框架提供 Agent 的通用骨架（执行循环、工具注册、记忆管理），开发者在此基础上填充业务逻辑即可。

**【深入原理】**：主流框架提供的通用抽象——

- **Agent 循环**：内置 ReAct、Plan-and-Execute 等执行模式，无需自行实现执行循环；
- **工具注册与解析**：把 Python 函数自动转换成 JSON-Schema 并注入提示词；
- **记忆模块**：对话历史、摘要记忆、向量记忆的封装；
- **编排能力**：多 Agent 调度、与向量库/模型服务/监控的集成。

选型角度：通用生态选 LangChain；数据/RAG 重度场景选 LlamaIndex；阿里云生态与 ModelScope 模型打通选 ModelScope-Agent。框架只是工具，**核心仍是提示词、工具定义与循环设计**。

### 4.6 ReAct 工作模式

> **导读**：ReAct 将推理与行动交替进行：先基于当前状态推理下一步，再执行行动（如调用工具），随后观察结果并继续推理，如此循环直至任务完成。与一次性完成推理的方式相比，ReAct 能够依据真实反馈动态调整后续步骤。

| 环节 | 说明 |
|------|------|
| **Thought（思考）** | 模型分析当前状态，决定下一步做什么 |
| **Action（行动）** | 调用工具/API，如搜索、计算、查数据库 |
| **Observation（观察）** | 读取工具返回结果，继续思考 |
| **循环终止** | 直到问题解决或达到最大轮数上限 |

**核心**：ReAct 把"推理"与"行动"显式交替，比"一次性回答"更能处理多步、依赖外部信息的任务。

**【直观解读】**：ReAct 以"推理—行动—观察"的循环推进任务，用工具返回的真实反馈指导后续推理，而非仅依赖模型内部知识。

**【深入原理】**：ReAct = **Rea**soning（推理）+ **Act**ion（行动）。以一个任务为例：

```
用户："帮我查明天北京天气，并提醒我要不要带伞。"
Thought：需要天气信息 → 调用天气工具
Action：weather(城市=北京, 日期=明天)
Observation：晴转多云，气温 5~12℃，降水概率 10%
Thought：降水概率低，无需带伞；但温差大，提醒添衣
Answer：直接输出结论
```

机制上，每一轮都会把 Observation 追加回上下文，模型基于**完整轨迹**继续推理。与 CoT（思维链）的区别：CoT 只"想"不"动"（纯推理），ReAct 想一步做一步（推理 + 外部反馈），后者适合需要实时信息的任务。

**【常见误区】**：

- ReAct **不是无限循环**：有最大迭代轮数/超时上限，超限要主动收尾或请求澄清（也防成本失控）；
- Observation 可能含噪声甚至错误信息，模型需要具备判断力，必要时交叉验证；
- 简单任务（一步可答）不需要 ReAct，直接回答更快、更省 token。

### 4.7 Agent 记忆类型

> **导读**：记忆分为短期与长期两类：短期记忆保存当前会话的上下文，长期记忆沉淀跨会话的知识与偏好。记忆容量有限，需要定期整理与压缩。

| 记忆类型 | 说明 |
|----------|------|
| **短期记忆** | 当前会话的对话历史与中间结果，受上下文窗口限制 |
| **长期记忆** | 跨会话持久化，通常用向量库存储历史知识、用户偏好、业务规则 |
| **记忆管理** | 摘要压缩旧对话、按相关性检索注入、定期清理，防止上下文膨胀 |

**【直观解读】**：短期记忆覆盖当前会话的上下文，长期记忆可跨会话保存用户偏好与历史知识，供后续会话按需调用。

**【深入原理】**：三种实现机制——

- **短期记忆**：① 滑动窗口——只保留最近 N 轮；② 摘要压缩——用 LLM 把旧对话浓缩成一段摘要，替换原文以节省 token；
- **长期记忆**：把记忆内容向量化存入向量库，每次按当前问题做相关性检索，只注入最相关的片段；也常配合结构化存储（用户画像、偏好表）使用；
- **记忆管理**：窗口裁剪、摘要、过期清理、隐私过滤（敏感信息不应进入记忆）。

**【实战/考试要点】**：上下文窗口是硬约束，超长记忆必须"选择性注入"而非全量塞入；记忆注入的位置（系统提示词 vs 用户消息）会影响模型行为；"摘要压缩防止上下文膨胀"是高频考点。

### 4.8 MCP（模型上下文协议）

> **导读**：MCP 可类比为统一的接口标准：过去接入数据库、文件系统、内部 API 等每类资源都需单独开发集成，采用 MCP 后可用统一协议接入，且同一套接入可被多个 Agent 复用。

| 知识点 | 说明 |
|--------|------|
| **是什么** | Anthropic 开源的标准化协议，统一 Agent 接入外部工具与数据源的方式 |
| **价值** | 一套工具接入规范可被多个 Agent/应用复用，避免每个 Agent 单独做集成 |
| **与 Function Calling 的关系** | Function Calling 是模型抽取参数、调用工具的能力；MCP 是工具接入的标准化协议，两者互补 |
| **典型场景** | 接入数据库、文件系统、内部 API、搜索服务；敏感操作封装为 MCP 工具并在应用层校验 |

**【直观解读】**：MCP 解决工具的接入标准化问题，Function Calling 解决模型的工具调用能力问题：前者定义接口协议，后者提供调用机制，二者互补。

**【深入原理】**：MCP 采用**主机-客户端-服务器**三层架构：Host（Agent 应用）通过 MCP 客户端连接 MCP 服务器，服务器对外暴露三类原语——

| 原语 | 作用 |
|------|------|
| **Tools（工具）** | 可被调用的操作（执行 SQL、发邮件等） |
| **Resources（资源）** | 可读取的数据（数据库表、文档内容） |
| **Prompts（提示词模板）** | 可复用的提示词/工作流模板 |

价值在于"一次开发、多处复用"，且鉴权、审计可以在服务器侧统一完成，敏感操作集中在应用层校验。

**【常见误区】**：MCP 不解决"模型会不会调用工具"的问题——模型仍需要通过 Function Calling 触发工具；MCP 服务器本身也需要鉴权，不能盲目信任其返回内容（防提示注入）。

### 4.9 Agent 规划策略（Plan-and-Execute 与任务拆解）

> **导读**：完成同一任务可采用不同的规划策略：ReAct 边推理边行动、灵活应变；Plan-and-Execute 先制定完整计划再逐项执行、过程可控。规划策略决定了 Agent 的执行风格。

| 策略 | 特点 | 适用场景 |
|------|------|----------|
| **ReAct** | 思考-行动-观察交替，边做边调整 | 环境动态、需要中间反馈的任务 |
| **Plan-and-Execute** | 先一次性产出完整执行计划，再逐项执行 | 步骤明确、可预先拆解的任务 |
| **分层规划** | 高层规划拆子任务，子任务再用 ReAct 等完成 | 超复杂任务（常见于多 Agent 场景） |

**【直观解读】**：Plan-and-Execute 适合步骤明确、可预先拆解的任务；ReAct 适合环境动态变化、需要依据中间反馈调整的任务。

**【深入原理】**：任务拆解的三条原则——① 子任务尽量独立、可验证（每步完成后能判断"是否成功"）；② 计划必须可执行（"把世界变好"这类不可操作目标无法执行）；③ 计划可被修正（执行中发现计划不当时允许重新规划）。实际工程中常把两者混合：高层用计划驱动，低层用 ReAct 处理不确定步骤。

**【实战/考试要点】**：选择题中"先规划再执行"对应 **Plan-and-Execute**；"边推理边调用工具"对应 **ReAct**，两者是高频区分点。

### 4.10 Agent 与 RAG 的结合及安全要点

> **导读**：将检索器封装为 Agent 的工具后，Agent 可在执行过程中按需自主检索，实现任务执行与知识获取的结合。

**Agent + RAG 结合方式**：

- 把检索器（Retriever）注册为 Agent 工具，Agent 自主决定"何时检索、检索几次"；
- 检索结果作为 Observation 进入循环，帮助 Agent 基于真实资料决策；
- 相比固定 RAG 流程（每次都检索），Agent 化检索更省 token、更贴合任务需求。

**Agent 安全要点**：

| 风险 | 说明与对策 |
|------|-----------|
| **提示注入** | 工具返回的网页/文档可能夹带恶意指令，需过滤、隔离，不直接信任外部内容 |
| **权限放大** | 工具权限按需最小化授予，敏感操作（转账、删除）加人工确认 |
| **循环失控** | 设置最大步数、超时、预算上限，防止无限调用工具导致成本失控 |
| **凭据管理** | 不同 Agent 使用独立凭据（呼应 4.3），防越权访问 |

### 4.11 百炼 Assistant API 构建智能体

> **导读**：百炼 Assistant API 把智能体拆成"配置（Assistant）— 会话（Thread）— 消息（Message）— 执行（Run）"几个对象，用一套对象关系管理多轮、多工具、带知识库的 Agent 应用。**字段名与接口细节以阿里云百炼官方文档为准，本节只讲概念关系与设计思路。**

**对象关系一句话**：

| 对象 | 类比 | 职责 |
|------|------|------|
| **Assistant** | 岗位说明书 | 定义模型、系统指令、可用工具、知识库/文件、生成参数 |
| **Thread** | 一次会话的聊天记录本 | 保存该次会话的消息与执行历史，支持多轮上下文 |
| **Message** | 记录本里的一条消息 | 用户输入或模型输出，挂在 Thread 下 |
| **Run** | 一次"开工" | 在 Thread 上执行一次模型推理，产出消息或工具调用请求 |
| **Tool / Knowledge Base / File** | 工具箱 / 资料库 / 附件 | 供 Assistant 调用的能力与可检索的资料 |

**完整构建思路**：

    创建 Assistant（模型 + 指令 + 工具 + 知识库/文件）
    → 创建 Thread（会话容器）
    → 向 Thread 添加用户 Message
    → 创建 Run（执行推理）
    → 轮询/订阅 Run 状态
       ├─ 需调用工具：模型返回 tool_calls → 应用执行工具 → 提交工具输出继续 Run
       └─ 完成：从 Thread 读取新 Message 作为最终回答

**关键机制**：

- **工具调用**：Run 进入"需要动作"状态时，模型输出要调用的工具与参数；**由应用代码真正执行工具**，再把结果作为工具输出提交回 Run（与 4.4 Function Calling 的"模型提议、程序执行"一致）。
- **状态管理**：Run 有排队、进行中、需动作、完成、失败、过期、取消等状态；应用要处理"失败/过期"（重试或新建 Run）与"需动作"（执行工具后继续）。
- **上下文管理**：Thread 自动累积消息形成多轮上下文；长会话要按需裁剪/摘要，避免窗口膨胀；知识库/文件检索由平台注入相关资料，遵循第 3 章 RAG 思路。
- **异常处理**：工具执行失败时把错误信息作为工具输出返回，让模型知道并调整；限流/超时按指数退避重试；区分"可重试错误"与"需人工处理错误"。
- **安全控制**：工具权限最小化、敏感操作人工确认、知识库按用户/权限隔离、输入输出审核、全量审计留痕（呼应第 8 章）。

**【实战/考试要点】**：判断题核心——**Assistant 是"配置模板"、Thread 是"会话容器"、Run 是"执行过程"**；"模型自己会执行工具"是错误说法；Assistant API 与 RAG/Function Calling 不是互斥关系，而是把它们组织成对象化、可管理、可多轮运行的智能体应用。

> 参考来源：阿里云百炼 Assistant API 官方文档（https://help.aliyun.com/zh/model-studio/ ，字段名与最新能力以官方文档为准）。

### 4.12 Agent 高频考点与常见误区汇总

| 误区 | 正解 |
|------|------|
| "Agent 就是多轮对话" | 多轮对话只是载体，Agent 核心是**规划-行动-观察闭环** |
| "所有 Agent 共用一套凭据更方便" | 存在安全隐患，应独立授权（高频考点） |
| "把所有知识写进主 Prompt" | 应按需检索/调用，避免上下文膨胀与 token 成本 |
| "工具 Schema 不重要" | Schema 决定参数提取正确性，必须准确完整 |
| "ReAct 可以无限循环直到成功" | 有最大迭代轮数/超时上限，超限应收尾或请求澄清 |
| "MCP 会取代 Function Calling" | 两者互补：MCP 是接入协议，Function Calling 是调用能力 |
| "工具报错就是模型不行" | 先查 Schema、工具实现、超时与返回格式，再判断模型能力 |

## 5. 模型微调与训练

### 5.1 什么是微调

> **导读**：通用大模型具备广泛能力，但在专业领域、固定风格或特定任务上，往往还需进一步适配。微调即在预训练模型基础上，通过领域数据继续训练，使模型更贴合目标场景。

**核心概念**：微调（Fine-tuning）是在预训练模型基础上，用领域数据继续训练，使模型适配特定任务。

**【直观解读】**：可将预训练与微调类比为通识教育与岗位培训：预训练阶段模型习得通用语言能力，微调阶段通过领域数据继续训练，使其掌握特定行业的术语、表达习惯与业务规范，从而在目标场景表现更专业。

**【深入原理】**：微调 = 在预训练权重基础上**继续做梯度下降**。训练循环四步：前向传播计算预测 → 计算损失 → 反向传播求梯度 → 优化器更新参数。微调之所以有效：模型在预训练中已习得通用语言能力（底层规律），微调主要调整**输出风格、格式、领域表达**等较上层的行为，学习量小、收敛快。需要明确的一点：微调**不更新模型的知识截止时间**，知识性内容仍受预训练数据限制。

**高频考点**：

| 考点 | 说明 |
|------|------|
| **微调改变什么** | 改变输出行为、风格、格式与领域适配，主要不是"塞新知识" |
| **微调 vs 预训练** | 预训练学通用语言能力（海量无标注数据）；微调适配特定任务（领域有标注数据） |
| **微调 vs 提示词/RAG** | 微调成本最高，是"最后手段"，应先尝试提示词优化与 RAG |

### 5.2 微调前置评估

> **导读**：启动微调前应先评估其必要性：多数场景通过优化提示词或引入知识库即可满足需求，无需调整模型参数。

在正式启动微调前，需**优先评估以下三点**：

| 评估维度 | 说明 |
|----------|------|
| **① 提示词优化** | 是否已通过优化提示词充分挖掘现有模型能力？ |
| **② RAG 方案** | 是否可以用知识库+检索来替代微调？ |
| **③ 数据规模** | 领域数据量是否满足微调的最低要求？ |

> ⚠️ 微调是"最后手段"，只有在提示词优化和 RAG 都无法满足需求时才考虑。

**【直观解读】**：优化顺序应为：先尝试成本最低的提示词优化，再评估 RAG 方案，最后才考虑成本最高、周期最长的微调。

**【深入原理】**：三者本质不同——提示词不改模型、零成本可随时调整；RAG 不改模型、把外部知识注入上下文（可溯源、易更新）；微调改变模型参数（成本高、周期长、存在过拟合与遗忘风险）。因此：**知识更新、引用溯源类需求 → RAG；行为风格、格式规则化需求 → 微调**。

**【考试要点】**：场景题高频判断——"回答错误但能查到资料"选 RAG；"回答风格不像行业专家/格式不统一"选微调；"要求新知识实时生效"选 RAG 而非微调。

### 5.3 微调方法对比

> **导读**：三种主流方法对资源的消耗差异显著：全参微调更新全部参数、效果最优但资源需求最大；LoRA 仅训练少量低秩参数、资源消耗大幅降低且效果接近全参；QLoRA 在 LoRA 基础上叠加量化，进一步降低显存需求，消费级显卡亦可完成微调。

| 方法 | 说明 | 特点 |
|------|------|------|
| **全参微调（Full Fine-tuning）** | 更新模型所有参数 | 效果最好，资源消耗最大 |
| **SFT（监督微调）** | 使用标注过的问答对进行训练 | 最常用的微调方式 |
| **LoRA（低秩适配）** | 只训练少量额外参数，冻结原模型 | **高效低资源**，训练快、显存占用少 |
| **QLoRA** | LoRA + 量化，进一步降低显存需求 | 消费级显卡也可微调大模型 |
| **PEFT（参数高效微调）** | LoRA、Prefix Tuning 等方法的总称 | 只更新少部分参数 |
| **RLHF（人类反馈强化学习）** | 用人类偏好数据训练奖励模型，再优化 LLM | 让模型更符合人类价值观 |
| **DPO（直接偏好优化）** | RLHF 的简化替代方案 | 不需要单独训练奖励模型 |

**【直观解读】**：SFT 使用标注的"指令-回答"样本训练模型遵循指令；RLHF 与 DPO 通过人类偏好数据使输出更符合人类偏好；LoRA 以极低的训练成本达到接近全参微调的效果。

**【深入原理】**：

- **全参微调**：所有权重都更新，梯度、优化器状态（Adam 每个参数还要存两份动量）都占显存，通常需要多卡集群；
- **LoRA**：冻结原权重 W₀，只训练低秩增量 ΔW = B·A（详见 5.7），推理时把 W₀ + ΔW 合并，**推理不增加任何开销**；
- **QLoRA**：把基座模型量化到 4bit（NF4 格式）后冻结，仅对 LoRA 参数做反向传播，配合分页优化器把优化器状态放到 CPU，显存需求大幅下降；
- **RLHF vs DPO**：RLHF 先训练奖励模型再强化学习（复杂、不稳定）；DPO 用"隐式奖励"直接从偏好数据优化（简单、稳定），两者目的一致：让输出更符合人类偏好。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "LoRA 就是没训练模型" | LoRA 训练的是新增的低秩参数，原模型被冻结而已 |
| "全参微调一定比 LoRA 好" | 数据量少时全参反而容易过拟合，LoRA 更稳，常接近全参效果 |
| "QLoRA 量化后必然严重掉点" | 4bit 基座 + 合适 rank 常能逼近 LoRA 效果，具体看任务 |
| "微调后模型知识会变新" | 微调不解决知识时效问题，新知识靠 RAG |

### 5.4 训练过程关键概念

> **导读**：训练以损失函数衡量预测与答案的差距，并通过梯度下降持续更新参数；训练过度会导致过拟合（记住训练集而非学习规律），训练不足则会欠拟合（能力未充分习得）。

| 知识点 | 说明 |
|--------|------|
| **损失函数（Loss）** | 衡量模型预测与正确答案的差距。**训练中 loss 持续下降是正常现象**，表示模型在学习 |
| **过拟合（Overfitting）** | 模型对训练数据"死记硬背"，在新数据上表现差。**训练集表现好但验证集表现差是典型信号** |
| **泛化能力** | 模型在新数据上的表现能力，是微调的核心目标 |
| **训练集/验证集/测试集** | 训练用/调参用/最终评估用，三者必须独立 |
| **数据质量** | 高质量标注数据比海量低质量数据更重要 |
| **学习率** | 控制参数更新步长的超参数，太大不收敛，太小训练慢 |

**【直观解读】**：损失函数（loss）量化模型预测与真实答案的偏差，训练的目标是持续降低该偏差，同时保证模型在新数据上仍表现良好（泛化能力）。

**【深入原理】**：LLM 微调常用**交叉熵损失**——比较模型预测的下一个 token 概率分布与真实 token 的差距，loss 本质是平均负对数似然。**过拟合的机制**：模型容量大而数据少/重复时，会把训练集里的噪声也"背"下来，导致验证集表现变差；对策是数据多样化、增加正则化（如 weight decay、dropout）、控制训练轮数。**泛化**取决于模型学到的是"规律"还是"背诵"。

**【实战/考试要点】**：监控"训练 loss + 验证 loss"两条曲线：训练 loss 降、验证 loss 升 = 过拟合信号；"数据质量优于数量"、"训练/验证/测试集必须独立"都是高频考点。

### 5.5 微调数据准备

> **导读**：数据质量直接决定微调效果：标注错误、内容重复等低质量数据，即使模型能力再强，也难以训练出理想效果。

| 知识点 | 说明 |
|--------|------|
| **SFT 数据格式** | 指令-回答问答对；多轮对话用 messages 结构（system/user/assistant）组织 |
| **数据清洗** | 去重、去噪、过滤错误标注与低质量样本，保证格式统一 |
| **数据规模** | 领域微调通常几千到几万条**高质量**样本即可；样本质量远重要于数量 |
| **数据划分** | 训练集/验证集/测试集必须独立：训练集学习、验证集调参与选 checkpoint、测试集最终评估 |
| **灾难性遗忘（Catastrophic Forgetting）** | 微调新任务可能使模型遗忘原有能力，可通过混合通用数据缓解 |

**【直观解读】**：微调所用的标注数据应保证正确、多样、无重复——样本质量远重要于样本数量。

**【深入原理】**：SFT 数据的 messages 结构三要素——system（角色设定）、user（指令）、assistant（标准答案）；多轮对话要保留完整上下文链条，不能把中间轮拆散。数据质量从四个维度把关：**正确性**（答案无误）、**多样性**（覆盖各种问法与场景）、**一致性**（格式风格统一）、**无重复**（重复低质数据会放大过拟合）。**灾难性遗忘**的本质：新任务梯度覆盖了旧能力权重，缓解手段包括混合通用数据、降低新数据占比、使用 LoRA 等参数高效方法（只动少量参数，扰动更小）。

**【实战/考试要点】**：清洗时检查"指令问 A、答案答 B"的错位样本；测试集严禁泄漏进训练集（否则评估虚高）；"几千到几万条高质量样本即可"是常见考点数值。

### 5.6 训练过程要点

> **导读**：训练过程的超参数（epoch、batch size、学习率等）决定训练时长、收敛速度与最终效果，设置不当将浪费算力资源。

| 知识点 | 说明 |
|--------|------|
| **Epoch（轮数）** | 全部数据完整训练一遍为 1 个 epoch，轮数过多会导致过拟合 |
| **Batch Size** | 每次参数更新使用的样本数，影响收敛速度与显存占用 |
| **学习率调度** | 常用 warmup（预热）+ 余弦退火，防止训练前期震荡 |
| **Checkpoint 选择** | 部署时应选**验证集表现最优**的 checkpoint，而非最后一个（高频考点） |
| **训练监控** | 训练 loss 下降是正常现象；**验证 loss 先降后升是过拟合信号**，应回退到最优轮次 |

**【直观解读】**：epoch 表示全部训练数据完整遍历的次数；batch size 表示每次参数更新使用的样本数；学习率控制每次参数更新的步长。

**【深入原理】**：

- **Epoch**：每 1 epoch = 全量数据过一遍。轮数过多 → 模型记住训练集 → 过拟合；
- **Batch Size**：影响梯度估计精度与显存。batch 越大梯度越稳但显存越高；大批量通常需配套调大学习率；
- **学习率调度**：warmup 让训练前期"小步慢走"稳定梯度（避免一开始大步震荡），再进入余弦退火逐步缩小步长逼近最优；
- **Checkpoint**：训练中每隔 N 步保存一次权重快照；验证集表现最优的 checkpoint 才是"最佳成绩"，最后一个可能是"练过头的成绩"——这是高频考点。

### 5.7 LoRA 深入原理：为什么省显存

> **导读**：LoRA 节省显存的核心逻辑：冻结原模型权重，仅训练少量新增的低秩参数，以接近全参微调的效果换取成本的大幅下降。

**【深入原理】**：

**① 低秩分解（数学原理）**：全参微调需要更新权重增量 ΔW（维度 d×d）；LoRA 把 ΔW 分解为两个小矩阵的乘积：**ΔW = B·A**，其中 A ∈ ℝ^(r×d)、B ∈ ℝ^(d×r)，秩 r（常取 8/16/64）远小于 d（如 4096）。

```chart matrix
W₀ + ΔW（4096×4096） | B（4096×16） | A（16×4096）
```

**② 参数量对比**：全参要训练 d×d 个参数，LoRA 只训练 2×r×d 个。以 d=4096、r=16 为例，LoRA 训练参数量约为全参的 2×16/4096 ≈ **0.8%**——绝大部分参数被冻结，不需要保存它们的梯度。

**③ 显存占用分析**：显存大头来自"梯度 + 优化器状态"（Adam 每个参数还要存 m、v 两份动量）。冻结权重只需前向计算与存储，不产生梯度；只有 LoRA 的小矩阵参与反向传播，显存需求随训练参数量骤降。

**④ 为什么低秩够用**：经验研究发现，模型在下游任务上的权重更新往往集中在**低维子空间**（"内在维度"假说）——真正需要的"改变方向"不多，低秩近似足以表达领域适配所需的变化。

**⑤ 推理零开销**：训练完把 W₀ + B·A 合并回原权重，推理时就是普通模型，**没有额外计算或显存开销**。

**【实战/考试要点】**：r（rank）越大表达能力越强、但训练成本越高；alpha 控制增量缩放；推理合并后与普通模型等价——"LoRA 推理不增加开销"是高频判断点。

### 5.8 微调超参数速查与常见误区

> **导读**：超参数需要在训练前合理设置，考试常以"调整哪个参数解决什么问题"的形式考查。

| 超参数 | 作用 | 常见经验方向 |
|--------|------|--------------|
| **learning_rate** | 每次参数更新的步长 | 太大不收敛、太小训练慢；LoRA 常用 1e-4~2e-4 量级（经验范围，视模型与框架调整） |
| **rank (r)** | LoRA 低秩矩阵的秩 | 简单任务 8/16 起步，复杂任务可加大 |
| **alpha (lora_alpha)** | LoRA 增量缩放系数 | 常设为 r 的 1~2 倍 |
| **batch_size** | 每次更新的样本数 | 显存允许时可加大，加快收敛 |
| **epochs** | 训练轮数 | 小数据量 2~5 轮即可，过多过拟合 |
| **warmup_steps** | 预热步数 | 训练前期稳定梯度，防震荡 |
| **max_seq_len** | 样本最大长度 | 超长样本会被截断，注意数据长度分布 |

> ⚠️ 以上数值为业界常见经验范围，不同模型、框架与数据规模下需实测调整，考试一般只考"大小方向"而非精确数值。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "微调数据越多越好" | 高质量、多样性远比数量重要，重复低质数据反而有害 |
| "训练 loss 不降就是没练够" | 先排查学习率是否过大/过小、数据是否干净、格式是否对齐 |
| "部署用最后一个 checkpoint" | 应选**验证集表现最优**的 checkpoint |
| "验证 loss 先降后升还能继续练" | 是过拟合信号，应回退到最优轮次 |
| "微调后知识截止就自动更新了" | 微调不解决知识时效，新知识靠 RAG |
| "LoRA 效果一定不如全参" | 数据少时 LoRA 更稳，常接近甚至优于全参微调 |

### 5.9 微调完整流程（SOP）

> **导读**：将微调组织为一条完整流水线：先判断是否需要微调，再准备数据、选择方法、训练、选择最优版本、小流量验证，最后上线。

```
需求分析 → 确认"提示词/RAG 是否够用" → 收集领域数据 → 数据清洗（去重/去噪/格式校验）
→ 划分训练/验证/测试集 → 选择方法（全参 / LoRA / QLoRA）→ 设定超参数
→ 训练并监控双 loss → 选择验证集最优 checkpoint → 评测（测试集 + 人工抽查）
→ 小流量对比验证 → 上线部署
```

| 阶段 | 关键动作 |
|------|----------|
| **需求分析** | 明确要改变什么（风格/格式/行为），排除"塞知识"类伪需求 |
| **数据准备** | 清洗、去重、错位样本修复、messages 格式校验 |
| **方法选型** | 资源紧张/数据少 → LoRA/QLoRA；追求上限且有资源 → 全参 |
| **训练监控** | 盯训练 loss 与验证 loss 双曲线，防过拟合 |
| **版本选择** | 验证集最优 checkpoint，而非最后一个 |
| **验证上线** | 测试集评估 + 人工抽查 + 小流量灰度，再全量 |

### 5.10 微调失败排查与考试速记

**失败排查速查**：

| 现象 | 可能原因 | 对策 |
|------|----------|------|
| loss 不降或震荡 | 学习率过大/过小、数据噪声、格式错位 | 调学习率、清洗数据、校验 messages 格式 |
| 验证 loss 先降后升 | 过拟合 | 回退最优 checkpoint、加正则/数据多样性 |
| 微调后旧能力明显变差 | 灾难性遗忘 | 混合通用数据、用 LoRA 减少扰动 |
| 输出格式不稳定 | SFT 样本格式不统一、模板不一致 | 统一 messages 格式与回答模板 |
| 测试集分数虚高 | 测试集泄漏进训练集 | 重新划分独立测试集 |

**考试速记**：

- 优化顺序：**先提示词 → 再 RAG → 最后微调**（微调是最后手段）。
- 微调改变**行为/风格/格式**，不解决**知识时效**——新知识走 RAG。
- 部署用**验证集最优 checkpoint**，不是最后一个。
- 数据**质量 > 数量**，几千到几万条高质量样本通常够用（经验值，视任务而定）。

## 6. 模型部署与推理优化

### 6.1 什么是模型部署

> **导读**：模型训练完成后，还需经过部署与服务化，才能真正对外提供稳定能力。部署环节不仅关系到调用方式，也直接影响系统延迟、吞吐、成本与可维护性。

**核心概念**：模型部署是将训练好的模型上线服务化的过程，涉及推理框架、资源调度、性能优化等。

**【直观解读】**：训练解决"模型能力"问题，部署解决"服务能力"问题：需要平衡响应延迟、吞吐量、显存占用与成本，并保证在并发高峰下系统稳定运行。

**【深入原理】**：推理 = 参数冻结的**纯前向计算**，其时间开销分为两段——

- **Prefill（预填充）**：一次性处理全部输入 token，计算密集，决定 **TTFT（首 token 延迟）**；
- **Decode（解码）**：逐个生成 token，每步只算一个新 token，但需反复读取历史 KV Cache，**显存带宽密集**，决定生成速度。

因此部署优化的两大方向：**缩短首 token 延迟 + 提高每秒生成 token 数（吞吐）**，同时控制显存占用与成本。

**高频考点**：

| 考点 | 说明 |
|------|------|
| **训练 vs 推理** | 训练更新参数、需反向传播、要 GPU 集群；推理参数冻结、只前向计算 |
| **推理两阶段** | Prefill 计算密集、Decode 带宽密集，优化手段各有侧重 |
| **部署目标** | 平衡延迟（RT）、吞吐（QPS）、显存与成本四者 |

### 6.2 模型量化

> **导读**：量化以少量精度损失换取显存占用与推理延迟的大幅下降：将模型参数由高精度压缩至低精度后，模型体积显著减小、推理速度提升，而精度损失通常有限（低比特下损失更明显）。

| 知识点 | 说明 |
|--------|------|
| **什么是量化** | 将模型参数从高精度（如 FP32/FP16）压缩到低精度（如 INT8/INT4），**降低显存占用和推理延迟** |
| **INT8 量化** | 8 位整数量化，精度损失小，速度提升明显 |
| **INT4 量化** | 4 位整数量化，进一步压缩，但精度损失较大 |
| **GPTQ** | 一种训练后量化方法，需要少量校准数据 |
| **AWQ** | 激活感知权重量化，比 GPTQ 更快、更适合低比特量化 |
| **量化 vs 原始模型** | 量化后精度有轻微损失，但推理速度大幅提升，适用于资源受限场景 |

**【直观解读】**：量化将模型参数由高精度浮点数近似为低精度整数表示，从而降低显存占用与计算开销。

**【深入原理】**：数值表示上，FP32 用 32 位浮点（符号+指数+尾数），INT8 用 8 位整数。量化的核心公式：**q = round(x / scale) + zero_point**（scale 为缩放系数，zero_point 为偏移），反量化时 x ≈ (q − zero_point) × scale。**显存对比**：FP32→INT8 参数缩小 4 倍，→INT4 缩小 8 倍。

```chart bars
FP32 全精度（32 bit） | 32
FP16 半精度（16 bit） | 16
INT8 量化（8 bit） | 8
INT4 量化（4 bit） | 4
```实现路线分两类：

- **PTQ（训练后量化）**：直接量化训练好的模型，只需少量校准数据即可，成本低——GPTQ 与 AWQ 都属于此类（GPTQ 基于二阶信息逐层最小化量化误差；AWQ 依据激活值显著性保护重要权重通道，低比特下更稳）；
- **QAT（量化感知训练）**：训练时就模拟量化误差让模型适应，精度更高但成本更高。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "量化必然大幅掉点" | INT8 通常损失很小，INT4 损失略大，具体看方法与任务 |
| "量化只省显存不加速" | 显存带宽下降通常带来加速，但需推理框架算子支持 |
| "量化后模型权重变回浮点" | 量化后权重以低精度存储与计算，反量化只是数学还原，不是恢复原值 |

### 6.3 推理框架

> **导读**：推理框架决定了模型的执行效率：选择适配的框架可显著提升推理速度、降低资源消耗，并提高并发处理能力。

| 框架 | 特点 |
|------|------|
| **vLLM** | 高性能推理框架，支持 PagedAttention、连续批处理 |
| **TGI（Text Generation Inference）** | HuggingFace 出品，支持张量并行、量化 |
| **DashScope** | 阿里云模型服务，提供 API 调用，免运维 |

**【直观解读】**：vLLM 的优势在于显存利用高效、吞吐量高；TGI 的优势在于生态完善、接入便捷；DashScope 的优势在于平台托管、无需自运维。

**【深入原理】**：

- **vLLM**：两大核心——PagedAttention（分页管理 KV Cache，消除显存碎片，详见 6.6）与连续批处理（请求动态进出 batch，GPU 不空转），是当前高吞吐推理的主流选择；
- **TGI**：HuggingFace 出品，内置张量并行、量化、流式输出，与 Transformers 生态无缝衔接；
- **DashScope / 百炼**：阿里云托管模型服务，用户只需提供 API Key 与请求体，底层集群、扩缩容、安全由平台负责。

**【选型要点】**：托管 API（省事、免运维、按量付费）vs 自部署框架（可控、可深度优化、数据不出域）——涉及数据合规的私有化场景选自部署，波动型业务选托管。

### 6.4 部署关键指标

> **导读**：衡量服务可用性的核心指标包括：吞吐量（QPS）、响应时间（RT）、并发处理能力与限流策略。

| 指标 | 说明 |
|------|------|
| **QPS（每秒查询数）** | 衡量系统吞吐量 |
| **RT（响应时间）** | 单次请求的延迟 |
| **并发** | 同时处理的请求数。**超出并发限制会返回错误** |
| **限流** | 服务端对请求频率的限制，保护系统稳定性 |
| **弹性伸缩** | 根据流量自动增减实例数量 |

**【直观解读】**：QPS 衡量系统单位时间内处理的请求数量，RT 衡量单次请求的延迟，二者通常相互制约。

**【深入原理】**：工程上吞吐与延迟满足近似关系：**QPS ≈ 并发数 / 平均 RT**（Little 定律思想）——RT 升高会挤压 QPS，因此压测必须同时观察两个指标。延迟细分为 **TTFT**（首 token 延迟，影响用户感知的"开口快慢"）与**总生成时长**；流量超过处理能力时请求会排队，超时或返回错误码（如 429），需要限流、重试、降级配合。

**【实战/考试要点】**：只报 QPS 高而 RT 已劣化是常见陷阱；"超出并发限制会返回错误"是高频考点；监控应同时关注 GPU 利用率与 KV Cache 占用。

### 6.5 MaaS（模型即服务）

> **导读**：MaaS（Model as a Service）即"模型即服务"。企业无需自行维护底层算力和推理环境，只需通过标准化 API 即可调用模型能力，快速完成集成与上线。

**核心概念**：MaaS（Model as a Service）将大模型封装成云服务，用户通过 API 调用，无需关心底层基础设施。

- **优势**：免运维、弹性伸缩、按量付费、快速接入
- **典型产品**：阿里云百炼平台、DashScope

**【直观解读】**：可类比为按需用水用电：通过 API 即可按需调用模型能力，无需自行建设与维护 GPU 集群等底层基础设施。

**【深入原理】**：MaaS 背后由平台统一管理：GPU 集群调度、弹性扩缩容、负载均衡、安全隔离、版本管理、监控告警。使用者只需关注"请求怎么发、结果怎么用"。与自部署的对比——

| 对比维度 | MaaS 托管 | 自部署 |
|----------|-----------|--------|
| 成本模型 | 按调用量付费，波动型友好 | 按 GPU 资源包年/包月，恒定型更划算 |
| 控制力 | 低（平台配置） | 高（深度定制、优化） |
| 数据合规 | 数据出域需评估 | 数据不出域，适合私有化 |
| 运维负担 | 免运维 | 需自建监控、扩缩容 |

### 6.6 推理加速技术

> **导读**：推理加速的常用手段包括：缓存历史计算结果（KV Cache）、按需分页管理显存（PagedAttention）、动态组批处理（连续批处理）以及小模型草稿加速（投机解码）。

| 技术 | 说明 |
|------|------|
| **KV Cache** | 缓存历史 Token 的 Key/Value，避免每步重复计算，是加速生成的基础 |
| **PagedAttention** | vLLM 的分页式注意力管理，减少显存碎片，提高吞吐 |
| **连续批处理（Continuous Batching）** | 动态组批、先完成的请求先返回，提升 GPU 利用率 |
| **投机解码（Speculative Decoding）** | 小模型快速草稿 + 大模型验证，无损加速生成 |
| **并行策略** | 张量并行（切分权重到多卡）、流水线并行（按层切分），支撑超大模型部署 |

**【直观解读】**：KV Cache 缓存历史 Token 的 Key/Value 计算结果，避免重复计算；PagedAttention 将 KV Cache 按需分块管理，减少显存碎片与浪费；连续批处理允许完成的请求随时退出并返回结果，提升 GPU 利用率。

**【深入原理】**（逐个拆解）：

- **KV Cache**：自注意力每一步都要让新 token 与**所有历史 token** 计算注意力。将历史 token 的 K/V 缓存下来后，每步只需计算新 token 的 Q·K，避免历史重复计算。代价是显存随序列长度线性增长——长上下文下 KV Cache 常超过权重本身的显存（详见 6.8）；
- **PagedAttention**：传统推理按"最大可能长度"预分配连续显存，造成碎片与浪费；PagedAttention 类比操作系统**分页**，把 KV Cache 切成固定大小块、按需分配，用页表映射，消除碎片、支持多请求共享，从而大幅提升吞吐；
- **连续批处理**：静态批处理必须等整批生成完才能换新请求（慢的拖累快的）；连续批处理允许新请求随时加入、完成的请求随时退出并返回，GPU 全程满载；
- **投机解码**：小"草稿模型"快速生成 K 个候选 token，大模型一次性验证（一次前向可验证 K 个位置），全部正确则一次产出 K 个 token；接受率越高加速越明显，且**输出分布与原始模型一致（无损）**；
- **并行策略**：张量并行把单层权重切到多卡（每步需通信，适合单卡放不下的大模型）；流水线并行按层分段、卡间只传激活值（通信量小）；数据并行则各卡各跑一批样本。

### 6.7 部署形态与运维

> **导读**：部署形态的选择取决于业务特征：波动型业务适合按量付费的 Serverless 形态，核心业务适合资源稳定的独占实例，同时需配套监控告警与应急预案。

| 部署形态 | 说明 |
|------|------|
| **Serverless（按量付费）** | 无流量时不占用资源，按调用量计费，适合波动型业务 |
| **独占实例** | 独享 GPU 资源、性能稳定，可自定义并发与配置，适合核心业务 |
| **弹性伸缩** | 按 QPS/并发自动扩缩容，兼顾成本与稳定性 |
| **运维监控** | 关注 QPS、RT（响应时间）、TTFT（首 Token 延迟）、错误率、Token 消耗、GPU 利用率 |
| **限流与降级** | 超过并发上限会返回错误（如 429），需设计重试与降级策略 |

**【直观解读】**：Serverless 按调用量计费、无流量时不占用资源；独占实例独享 GPU 资源、性能稳定；弹性伸缩根据流量自动增减实例数量，兼顾成本与稳定性。

**【深入原理】**：Serverless 存在**冷启动**问题——无流量时实例被回收，请求到来需重新拉起，首个请求可能变慢，适合可容忍偶发抖动的业务；独占实例资源恒定、延迟稳定、可自定义并发上限，适合核心链路。运维上以 **QPS、RT、TTFT、错误率、Token 消耗、GPU 利用率**为核心监控项，配合告警与自动扩缩容策略；超并发返回 429 时应设计**指数退避重试 + 降级**（如返回缓存结果或提示稍后再试）。

### 6.8 KV Cache 显存怎么算（一张账）

> **导读**：KV Cache 是推理阶段的"显存大户"——模型权重只占一份，但 KV Cache 随"序列长度 × 并发数"线性膨胀，长上下文 + 高并发时它才是显存大头。

**【深入原理】**：每层、每个 token 的 KV Cache 大小为 **2（K 和 V 两份）× 注意力头数 × 每头维度 × 每值字节数**；整体显存 ≈ 上式 × 层数 × 序列长度 × 批大小。由此可得两个工程结论：

- 序列长度翻倍 → KV Cache 显存翻倍；
- 并发数翻倍 → KV Cache 显存翻倍。

这就是"长上下文 + 高并发"的真实成本所在（用符号公式理解即可，考试不考具体数值）。

**缓解手段**：

| 手段 | 原理 |
|------|------|
| **GQA（分组查询注意力）** | 多个查询头共享一组 KV 头，KV Cache 成倍缩小 |
| **KV Cache 量化** | 对缓存做低精度存储，省显存、略损精度 |
| **PagedAttention 分页** | 按需分配、消除碎片与预分配浪费 |
| **上下文缓存（前缀复用）** | 相同前缀（如系统提示词、知识库）的 KV 结果复用，降低重复计算与延迟 |

### 6.9 推理优化常见误区

| 误区 | 正解 |
|------|------|
| "量化后推理一定变慢" | 通常因显存带宽下降而变快，但要看算子是否支持低比特 |
| "vLLM 只对长文本有效" | PagedAttention 对所有长度都减少碎片，只是短文本收益有限 |
| "并发越高吞吐越高" | 超并发导致排队、RT 劣化甚至报错，需压测确定最优并发阈值 |
| "TTFT 就是总延迟" | TTFT 是首 token 延迟，总延迟 = TTFT + 后续生成耗时 |
| "Serverless 没有冷启动" | 无流量实例被回收，冷启动可能拖慢首个请求 |
| "KV Cache 只占一点点显存" | 长上下文 + 高并发下 KV Cache 常是显存占用大头 |
| "并行策略越多越好" | 张量并行每步需卡间通信，过度切分反而因通信开销变慢 |

### 6.10 ECS 部署推理服务基本方案

> **导读**：ECS（云服务器）是"自己搭服务器"的部署形态，适合需要**数据不出域、深度定制、稳定流量**的场景；代价是要自己承担 GPU 选型、推理框架、网络、监控与运维。

**基本架构**：

```chart flow
客户端请求
网关/负载均衡（Nginx/SLB）
推理服务（vLLM / TGI）
GPU 实例（权重 + KV Cache）
监控告警 + 日志
```

**部署要点**：

| 环节 | 说明 |
|------|------|
| **实例选型** | 按模型参数规模选 GPU 显存（权重 + KV Cache + 运行时余量），量化可降低显存门槛 |
| **推理框架** | vLLM/TGI 提供 PagedAttention、连续批处理、流式输出（见 6.3、6.6） |
| **网关与加密** | 前面挂 Nginx/SLB 做反向代理、HTTPS 终止、限流与负载均衡 |
| **弹性** | 手动扩缩容或配合弹性伸缩组；GPU 实例弹性成本较高，需提前规划 |
| **监控** | QPS、RT、TTFT、错误率、GPU 利用率、显存占用（见 6.4） |

**适用与不适用**：稳定流量、数据合规要求高、需深度优化 → 选 ECS 自建；无 GPU 运维团队、强波动流量、只求快速上线 → 优先托管/Serverless（见 6.12）。

### 6.11 函数计算 FC 部署 AI 助手

> **导读**：函数计算（Function Compute, FC）是事件驱动的 Serverless 计算服务——写完函数代码即可运行，平台负责弹性与运维，适合**轻量 AI 助手、WebHook、定时任务、流量尖峰**场景。

| 知识点 | 说明 |
|--------|------|
| **特点** | 事件驱动、免运维、按调用量计费、自动弹性伸缩 |
| **适用场景** | 轻量 API 网关/WebHook、定时任务、图片/文本处理、流量波动大的小助手、快速原型 |
| **冷启动** | 无流量时实例被回收，请求到来需重新拉起，首个请求变慢；可用**预留实例/预热**缓解，代价是持续占用资源 |
| **弹性伸缩** | 按并发/QPS 自动扩缩容，无需手动管服务器 |
| **限制** | 有函数超时时间、内存/临时磁盘、代码包/镜像大小、并发上限等限制；长时推理或大模型加载需评估是否适配（GPU 实例能力以官方文档为准） |

**FC 快速发布 AI 助手流程**：

    编写函数（接收 HTTP 请求 → 组织 messages → 调模型 API → 返回结果）
    → 配置环境变量（API Key、模型名）
    → 部署函数 + 配置 HTTP 触发器（域名）
    → 观察日志/监控，按需调并发与超时

**【实战/考试要点】**：FC 的"免运维 + 弹性"是优点，但**冷启动与执行时长限制**是它的边界；"把 70B 大模型裸跑在普通 FC 上"属于选型错误，大模型私有部署应看 ECS/PAI-EAS（GPU）方案。

### 6.12 部署方案对比：vLLM / ECS / FC / PAI-EAS / 百炼

> **导读**：这五种方案不是"互相替代"的并列选项，而是**不同抽象层级、不同控制力与运维责任的取舍**：从"全托管、最快上线"到"全自建、最强控制"逐级过渡。

| 方案 | 定位 | 典型场景 | 优势 | 代价/限制 |
|------|------|----------|------|-----------|
| **百炼 / DashScope API** | 全托管 MaaS，调 API 即可 | 快速接入、波动流量、无运维团队 | 免运维、按量付费、弹性 | 数据出域需评估、深度定制受限 |
| **FC（函数计算）** | Serverless 函数，轻量服务编排 | AI 助手 API、WebHook、定时任务 | 免运维、自动弹性、低成本起步 | 冷启动、执行时长/资源限制 |
| **ECS + vLLM** | 自建 GPU 推理服务 | 数据不出域、高吞吐、深度定制 | 可控性强、可深度优化 | 自运维、GPU 成本高、弹性弱 |
| **PAI-EAS** | 企业级托管推理平台 | 私有模型上线、弹性伸缩、灰度发布 | 托管 + 弹性 + 企业级运维 | 学习成本、需在 PAI 体系内管理 |

**决策依据（按顺序问五个问题）**：

1. **数据能否出域？** 不能 → 排除百炼托管，选 ECS/EAS 私有部署；
2. **流量形态如何？** 强波动/低频 → FC 或托管；稳定高吞吐 → ECS+vLLM / EAS；
3. **对延迟与吞吐的要求？** 极致吞吐 → vLLM 深度调优；常规要求 → 托管/FC 即可；
4. **有无 GPU 运维能力？** 无 → 优先托管/Serverless；有 → 自建可控；
5. **成本模型？** 波动型按量付费划算；恒定型包月 GPU 更划算（需实测对比）。

### 6.13 云上部署微调模型基本方案

> **导读**：微调产出的模型要上线服务，通常先"固化权重"，再选 EAS/ECS 等 GPU 形态部署，最后灰度验证。

**基本流程**：

    微调产物（LoRA 增量 / 全参权重）→ LoRA 合并为完整权重（如适用）
    → 打包模型文件/镜像，上传 OSS/镜像仓库
    → 部署到 EAS 或 ECS+vLLM（GPU 实例）
    → 配置模型路径、并发、弹性、监控
    → 灰度/AB 验证 → 全量上线（保留回滚版本）

| 要点 | 说明 |
|------|------|
| **LoRA 合并** | 训练出的 LoRA 增量通常需与基座合并为完整权重后部署；也可按框架支持热加载适配器（以官方文档为准） |
| **部署形态** | 私有模型首选 PAI-EAS（托管弹性）；自建可选 ECS+vLLM |
| **版本管理** | 保留多个模型版本，支持回滚；灰度对比后再全量 |
| **监控回滚** | 上线后盯 QPS/RT/错误率与业务指标，异常时回滚到旧版本 |

### 6.14 部署选型场景题

| 场景 | 选型 | 原因 |
|------|------|------|
| 创业团队 3 天上线一个 AI 助手，无 GPU 运维 | 百炼 / FC | 免运维、快速上线 |
| 企业私有知识问答，数据严禁出域，流量稳定 | ECS + vLLM 或 PAI-EAS | 数据不出域、可控可优化 |
| 晚间批量跑评测，白天几乎无流量 | FC 或托管按量 | 按调用计费、弹性匹配波动 |
| 私有微调模型上线，需弹性伸缩与灰度 | PAI-EAS | 企业级托管 + 弹性 + 灰度 |
| 追求极致吞吐与显存利用率 | ECS + vLLM | PagedAttention、连续批处理深度调优 |

**【实战/考试要点】**：选型题先看三个词——**数据出域、流量形态、运维能力**；"ECS/FC/PAI/百炼可以互相替代"是错误认知，它们对应不同控制力层级。

## 7. 模型评估

### 7.1 为什么需要评估

> **导读**：评估的目的不是简单打分，而是用可量化的方法判断模型是否满足业务目标，并据此发现短板、定位问题、指导后续优化。

**核心概念**：模型评估是通过定量指标和定性分析，衡量模型在特定任务上表现的系统方法。

**高频考点**：

- **评估的五大用途**：发现短板、定位问题、指导优化、防止回归（改坏了没有）、辅助选型（换不换模型）
- **评估的本质**：把"主观质量感受"翻译成"可测量、可复现的指标"——没有评估，就没有优化的依据

**【直观解读】**：评估可以理解为一次标准化的"考试"：先确定考核维度（指标），构建评测题目（评测集），统一阅卷规则（固定评测配置），这样才能对分数进行横向比较，并据此定位薄弱环节。

**【深入原理】**：为什么不能仅凭主观感受判断模型好坏？

- 大模型输出具有**概率性**：同一输入多次输出可能不同，仅凭一两次对话无法得出统计结论，必须用"一批样本 + 统一配置"进行评估。
- 业务目标 ≠ 模型指标：业务关注的是"用户满意度、转化率"，而模型产出的是 token 序列，中间需要经过**任务定义 → 指标设计 → 评测集**的转译。
- 评估需**控制变量**：固定评测集版本、推理参数（temperature/seed）与模型版本，否则分数差异无法归因。

**【实战/考试要点】**：先评测、再优化，而非凭主观感觉调整；评测集须冻结版本，否则历史分数不可比；指标须匹配任务类型（摘要用 ROUGE、翻译用 BLEU、分类用 Accuracy/F1、语言模型看 PPL）。

### 7.2 自动化评估指标

> **导读**：自动评估指标如同"机器阅卷"：基于参考答案与数学公式计算得分，速度快、可复现，但判定规则相对简单，可能出现误判。

| 指标 | 适用场景 | 说明 |
|------|----------|------|
| **BLEU** | 机器翻译 | 比较生成文本与参考文本的 n-gram 重叠度，侧重**精确率** |
| **ROUGE** | 文本摘要 | 基于最长公共子序列（LCS），衡量召回率。核心维度：**召回率、精确率、F1 分数** |
| **Perplexity（困惑度）** | 语言模型 | 衡量模型对文本的"惊讶程度"，越低越好 |
| **准确率（Accuracy）** | 分类任务 | 正确预测数 / 总数 |
| **F1 分数** | 分类任务 | 精确率和召回率的调和平均，综合考量 |

**【直观解读】**：BLEU 衡量生成文本与参考答案在字面上的重合程度，标准偏严；ROUGE 衡量参考答案中的要点是否被覆盖，标准偏宽；困惑度反映模型对文本的熟悉程度，数值越低表示把握越强。

**【深入原理】**：

- **BLEU 怎么算**：先计算 n-gram 精确率 pₙ（生成文本中出现在参考译文中的 n-gram 占比），对 1~4 gram 取几何平均，再乘**简洁惩罚 BP**（brevity penalty），防止生成过短译文来取巧：BLEU = BP × exp(Σ wₙ·log pₙ)。生成越短，BP 越小，分数越低。
- **ROUGE 怎么算**：ROUGE-N 基于 n-gram 重叠，**默认侧重召回率**（参考内容被覆盖多少）；ROUGE-L 基于**最长公共子序列（LCS）**，不要求内容连续，衡量结构相似度。三个维度：召回率 = 参考内容被覆盖的比例，精确率 = 生成内容中有效信息的比例，F1 = 2PR/(P+R) 是二者的调和平均。
- **困惑度含义**：PPL = exp(每个 token 平均负对数似然)。直观理解：PPL 近似表示模型在每个位置平均需要从多少个等概率候选词中做出选择（PPL=10 约等于在 10 个候选中猜 1 个），**越低越好**。但需注意：PPL 低 ≠ 回答正确，它衡量的是概率预测的把握程度，而非事实正确性。
- **F1 为什么用调和平均**：调和平均对精确率与召回率的失衡更敏感——当两者差距较大时，F1 会被明显拉低，从而避免只优化单一指标。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "BLEU 高 = 翻译质量好" | BLEU 只认字面重合，同义改写、表达差异会误伤，短译文还有 BP 惩罚 |
| "ROUGE 能衡量语义等价" | 同义改写会让 ROUGE 偏低，它衡量字面/结构覆盖 |
| "PPL 低 = 模型更聪明" | PPL 只反映概率预测能力，事实性错误照样可以 PPL 很低 |
| "只看 Accuracy 就够了" | 类别不平衡时 Accuracy 失真，要看 P/R/F1 和混淆矩阵 |

### 7.3 评估注意事项

> **导读**：自动化评分速度快，但结果可能系统性偏高；LLM-as-Judge 较为灵活，但评分模型自身也存在偏好，需先校准评分标准与阈值。

| 知识点 | 说明 |
|--------|------|
| **自动化评分 vs 人工评测** | 自动化评分偏高是常见问题，需人工校准 |
| **LLM-as-Judge** | 用一个大模型给另一个大模型的输出打分。**需调整评分提示词和阈值，避免系统性偏差** |
| **专业领域评测** | 医疗、法律等专业场景**必须由领域专家参与评测**，仅靠自动化指标不够 |
| **评测样本集** | 应覆盖各类题型和难度，分布要合理 |
| **评测与优化闭环** | 评测 → 找到短板 → 针对性优化 → 再评测 |

**【直观解读】**：自动化评分容易给与参考答案字面接近的输出较高分数；LLM-as-Judge 由另一模型参与评分，但评分模型自身存在偏好（如倾向长答案、倾向先出现的答案），需事先明确评分标准并校准。

**【深入原理】**：

- **自动化评分为什么偏高**：n-gram 类指标偏向与参考答案**字面重合**的输出；基于模型的自动评分常见**长度偏差**（更长的输出得分更高）、**位置偏差**（先出现的答案更受青睐）、**自我偏好**（评分模型偏爱与自己风格一致的输出）。
- **LLM-as-Judge 校准方法**：① 评分提示词明确维度、量表、输出格式（如只输出 JSON 分数）② 交换候选顺序多次打分取平均（抵消位置偏差）③ 提供参考答案和评分样例（few-shot）④ 多个 Judge 投票 ⑤ 定期用人工标注校准阈值。
- **专业领域为什么必须人工**：医疗、法律等领域中"看似合理实则错误"的代价极高，领域专家能判断事实性与合规性，通用规则与通用模型均无法胜任。

**【实战/考试要点】**：自动指标用于批量初筛，人工评测用于精准把关；评测集需**分层设计**（简单/中等/困难、短/长文本、正常/对抗样本），若仅包含简单题目，分数会虚高。

### 7.4 常见公开评测基准

> **导读**：公开基准如同"统一模拟考试"，可用于横向比较模型；但模拟考试不能等同于企业真实业务场景，不能仅以此为依据做出选型决策。

| 基准 | 评测内容 |
|------|----------|
| **MMLU** | 多学科知识理解（英文） |
| **C-Eval** | 中文知识能力评测 |
| **GSM8K** | 小学数学推理（检验推理与计算能力） |
| **HumanEval** | 代码生成正确性 |
| **CMMLU / CMATH** | 中文综合能力 / 中文数学 |

> ⚠️ 公开基准分数高 ≠ 业务表现好：基准反映通用能力，业务场景必须用**自有评测集 + 领域专家**验证。

**【直观解读】**：MMLU 考察英文知识面，C-Eval 考察中文知识面，GSM8K 考察数学推理，HumanEval 考察代码生成。基准分数高说明通用能力扎实，但通用能力强不等于业务场景表现好。

**【深入原理】**：

- **MMLU**：涵盖 STEM、人文、社科等 57 个学科的多选题，检验知识广度，是英文模型的主流基准。
- **GSM8K**：包含约 8.5K 道小学数学应用题，需要**多步推理**，用于检验模型在多步推理与计算中的准确性。
- **HumanEval**：164 道手写 Python 编程题，用 **pass@k** 计分——生成 k 个候选程序，只要有 1 个通过全部单元测试即算通过；k 越大，越体现"多试几次能对"的能力。
- **为什么还要看中文基准**：英文基准的训练数据分布与中文差异大，中文场景应同时参考 C-Eval、CMMLU、CMATH。

**【常见误区】**：公开基准存在"刷分"风险（评测题泄露进训练数据）、与业务题型不一致、语言分布不匹配等问题——**公开基准仅用于选型初筛，业务决策必须使用自建评测集**。

### 7.5 评测落地流程

> **导读**：评测流程本质上是"评测 → 优化 → 再评测"的循环：优化某一能力的同时不能影响其他能力，因此每次改动后都需用同一套评测集回归验证，上线前再通过小流量 AB 测试检验真实效果。

```
明确评测目标 → 构建评测集（覆盖各类题型/难度） → 确定指标 → 运行评测
→ 分析短板 → 针对性优化（提示词/RAG/微调） → 回归评测 → 上线灰度/AB 验证
```

| 知识点 | 说明 |
|--------|------|
| **回归评测** | 每次优化后跑同一套评测集，防止"修好 A、弄坏 B" |
| **AB 测试** | 新旧版本分流对比线上真实效果 |
| **人工抽查** | 自动化评分后按比例人工复核，校准系统性偏差 |

**【直观解读】**：流程可概括为：明确目标 → 构建评测集 → 运行评测 → 分析短板 → 针对性优化 → 回归评测 → 小流量 AB 验证，每个环节都有明确的执行动作。

**【深入原理】**：

- **回归评测的前提是评测集一致**：评测集版本、评测脚本、推理参数（temperature、seed、模型版本）均需冻结，分数变化才能归因于本次改动。
- **AB 测试要点**：线上真实流量按比例分流（如新版本 10%、旧版本 90%），对比业务指标；**同一用户尽量固定到同一版本**（避免会话内体验割裂），样本量需充足（差异才具有统计显著性），观察期需覆盖不同流量特征。
- **优化优先级**：提示词 → RAG → 微调（与第 5 章一致），每步之后均应回归评测，不应跳过中间步骤直接采用高成本方案。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| 用训练数据当评测集 | 数据泄漏，分数虚高，无参考价值 |
| 每次优化都换评测集 | 分数不可比，无法判断是否回归 |
| 只看平均分 | 应细分维度（简单/难题、长短文本、类别）找短板 |
| 只跑一次不回归 | 无法发现"修好 A、弄坏 B" |

### 7.6 常用评测工具与平台

> **导读**：评测工作不必从零开发，社区与云平台已提供成熟的评测工具，合理选用可大幅节省时间。

| 工具/平台 | 说明 |
|-----------|------|
| **Ragas** | 开源 RAG 评估框架，内置 Context Recall/Precision、Faithfulness、Answer Relevancy 等指标（与第 3 章 RAG 评估指标对应） |
| **DeepEval** | 开源 LLM 评估框架，支持把评测用例组织成"单元测试"式断言 |
| **OpenAI Evals** | OpenAI 开源的评估框架，适合自建评测集与回归评测 |
| **LangSmith** | LangChain 生态的链路观测与评测平台，可记录调用 trace 并对输出打分 |
| **阿里云百炼评测** | 平台内置评测能力，支持自动化与人工评测，可评估模型、知识库、RAG 应用等 |

**【直观解读】**：Ragas 专注于 RAG 应用的相关性与忠实度评估；DeepEval 将评测用例组织为单元测试式断言，便于持续回归；百炼在云端提供评测集管理与自动打分能力。

**【实战/考试要点】**：工具可以替换，**评测集、指标与流程才是核心**——应先明确"评测什么、如何计分"，再选择工具；评估体系应固化为可复用的评测集，才能支撑长期迭代优化。

### 7.7 评估高频场景与速记

**场景判断速查**：

| 场景 | 选什么指标/方法 |
|------|-----------------|
| 机器翻译质量 | BLEU（字面重合 + 简洁惩罚） |
| 文本摘要是否覆盖要点 | ROUGE（召回为主） |
| 类别不平衡的分类 | F1 / 混淆矩阵，不要只看 Accuracy |
| 语言模型概率预测能力 | Perplexity（越低越好，但不等于"更聪明"） |
| RAG 检索与生成质量 | RAGAS：Context Recall/Precision + Faithfulness + Answer Relevancy（见 3.8） |
| 医疗/法律等专业场景 | 领域专家人工评测，自动指标只做初筛 |

**考前速记**：

- 公开基准（MMLU/C-Eval/GSM8K/HumanEval）只用于**选型初筛**，业务决策用**自有评测集**。
- 每次优化后跑**同一套冻结评测集**做回归，防止"修好 A、弄坏 B"。
- LLM-as-Judge 要防**长度偏好、位置偏好、自我偏好**，靠交换顺序/多 Judge 投票/人工校准缓解。
- 数据泄漏（测试集进训练集）会导致**分数虚高**，是评估大忌。

## 8. AI 安全与合规

### 8.1 为什么需要安全机制

> **导读**：随着模型能力增强，内容生成、数据泄露、越狱攻击和权限滥用等风险也随之增加。安全与合规不是附加项，而是大模型落地过程中的基础要求。

**核心概念**：AI 安全包括内容安全、数据安全、模型安全和访问控制等多个维度。

**高频考点**：

- **安全的四个维度**：内容安全（模型"说什么"）、数据安全（数据"怎么管"）、模型安全（模型"怎么防攻击"）、访问控制（谁"能用什么"）
- **核心思路：纵深防御（Defense in Depth）**：输入侧 → 模型侧 → 输出侧 → 应用侧 → 审计侧，层层设防、互为兜底

**【直观解读】**：安全机制用于约束模型能力的合理使用：模型能力越强，越需要防止其被误用或滥用；安全不是上线后的补救措施，而是在系统设计阶段就应纳入的基础要求。

**【深入原理】**：为什么安全不能只靠模型本身？

- **对齐（Alignment）只约束模型，约束不了输入**：安全对齐让模型"学会拒绝"，但用户输入、检索文档、网页内容都是模型无法预先防备的，必须在应用链路加防护。
- **攻防是持续对抗**：攻击者不断发明新绕法（角色扮演、编码混淆、间接注入），安全措施必须可升级、可监控、可响应，不是"配一次就完事"。
- **单一防线必然被击穿**：只靠输出审核防不住工具被滥用，只靠输入过滤防不住间接注入，所以要多层布防。

**【实战/考试要点】**：区分"安全"还是"质量"问题是高频考点——**生成不相关内容/说错数字 = 质量缺陷；被诱导输出违法内容、越权访问数据 = 安全问题**。

### 8.2 内容安全风险

> **导读**：内容安全风险指模型可能输出不合规内容：一类源于模型自身（违法信息、偏见），另一类源于外部攻击（越狱、提示注入）。

| 风险类型 | 说明 |
|----------|------|
| **违法信息** | 生成涉及暴力、色情、诈骗等违法内容 |
| **虚假信息** | 生成看似合理但事实错误的内容（幻觉） |
| **偏见与歧视** | 模型训练数据中的偏见被放大 |
| **越狱攻击（Jailbreak）** | 用户通过特殊提示词绕过安全限制 |
| **提示注入（Prompt Injection）** | 在用户输入中嵌入恶意指令劫持模型行为 |

> ⚠️ "生成不相关内容"不属于内容安全风险，属于质量/相关性缺陷。

**【直观解读】**：违法信息与虚假信息属于模型自身的能力或数据问题；越狱与提示注入属于外部攻击问题。输出跑题或表述错误属于质量缺陷，不构成安全事故。

**【深入原理】**：

- **虚假信息（幻觉）的根源**：大模型本质上是概率续写模型，对没有把握的内容会生成语法通顺、逻辑自洽但事实存疑的表述，人工较难察觉。
- **偏见从哪来**：训练数据本身存在分布偏差（某些群体样本少、刻板印象表达多），模型学到的统计规律因此带有偏见，并在推理时被放大——这是**数据问题**，并非模型有意为之。
- **越狱为什么能得逞**：安全对齐训练通常只覆盖"直接提问"这类常见模式；攻击者通过**角色扮演、虚构场景、语言转换、编码混淆**等手段，将有害请求包装成"无害的创作任务"，绕过对齐层（详见 8.6）。

**【常见误区】**：① "模型说错一个数字 = 安全问题" → 属事实性/质量问题；② "幻觉 = 模型在撒谎" → 是概率生成的自然缺陷，模型并不存在主观意图；③ "偏见只能靠审核解决" → 根本治理靠数据清洗与对齐，审核仅是兜底手段。

### 8.3 安全防护措施

> **导读**：防护措施可概括为双向把关：输入侧检查是否存在恶意指令，输出侧检查是否存在违规内容，同时通过行为护栏约束模型的输出边界。

| 措施 | 说明 |
|------|------|
| **内容审核** | 对输入和输出进行自动审核过滤 |
| **Guardrail（护栏）** | 设定模型行为边界，拦截不安全请求 |
| **非法查询识别** | 识别并拒绝回答非法/违规查询 |
| **插件安全设计** | 不安全的插件设计可能导致数据泄露或权限滥用 |
| **API Key 安全管理** | 将 API Key 配置在**环境变量**中，而非硬编码在代码里。可避免泄漏到版本库或被日志打印 |

**【直观解读】**：内容审核负责对输入与输出进行自动检查；Guardrail 通过预设规则约束模型的行为边界；API Key 必须存放于环境变量或密钥管理服务中，不能写入代码或配置文件。

**【深入原理】**：

- **内容审核怎么做**：通常是"规则 + 模型"结合——关键词/正则先粗筛，再用审核模型（文本、图片、语音分类）细判，可对接阿里云内容安全等服务；**输入、输出双向审核**缺一不可（输入防注入，输出防违规）。
- **Guardrail 的本质**：将"模型不应执行的行为"从依赖模型自律转为应用层强制约束——如敏感话题黑名单、输出格式约束、工具调用白名单、敏感操作二次确认。
- **插件/工具安全**：插件获得的能力 = 攻击者可利用的能力。工具权限越大，提示注入的破坏越大，所以要**权限最小化 + 关键操作人工确认**。
- **API Key 泄漏路径**：硬编码后提交 Git 被自动化爬虫扫描；打印进日志；写进前端页面被浏览器用户看到。正确做法：环境变量/配置中心/KMS 托管、定期轮换、最小权限、异常调用监控。

**【实战/考试要点】**：高频考点一句话——**API Key 放环境变量、输入输出双向审核、敏感操作人工确认、权限最小化**。

**内容安全合规检查手段**：

| 手段 | 说明 | 特点 |
|------|------|------|
| **输入检测** | 请求进入模型前检测恶意指令、注入、越狱话术 | 防患于未然，拦截非法查询 |
| **输出检测** | 生成后审核输出是否含违规/敏感内容 | 兜底，防止违规内容流出 |
| **敏感内容识别** | 对违法、色情、暴力、政治敏感等分类识别 | 需与审核模型/规则结合 |
| **规则审核** | 关键词/正则黑白名单 | 快、成本低，但易被变形绕过 |
| **模型审核** | 用审核模型或 LLM 分类判断内容风险 | 更准，但需调阈值、有成本 |
| **人工审核** | 高风险内容交人工复核 | 准确，但成本高、不可全量 |
| **审计留痕** | 记录审核决策、调用与访问日志 | 可追溯、支撑合规检查 |

**组合原则**：**规则粗筛 → 模型细判 → 人工兜底 → 全程留痕**；输入、输出两端都要检，只检一端会漏掉间接注入或违规输出。

### 8.4 数据安全

> **导读**：数据安全要求数据在传输、存储与使用三个环节均不泄露：传输需加密（HTTPS/TLS）、存储需加密、访问需鉴权控制、全过程需记录审计日志。

| 知识点 | 说明 |
|--------|------|
| **数据脱敏** | 训练/推理前对敏感信息进行脱敏处理 |
| **访问控制** | 通过 RAM/ACL 控制数据和模型的访问权限 |
| **传输加密** | 数据传输使用 HTTPS/TLS 加密 |
| **审计日志** | 记录所有 API 调用和数据访问行为，便于追溯 |

**【直观解读】**：脱敏是在使用前对敏感信息进行遮蔽或替换；访问控制用于明确不同主体对数据的权限范围；审计日志完整记录访问行为，便于事后追溯与追责。

**【深入原理】**：

- **脱敏（去标识化）**：对姓名、证件号、手机号、地址等敏感字段做替换/掩码/泛化，用于训练、评测和测试数据；RAG 场景中，企业知识库的敏感文档也要在进入检索链路前做权限标记。
- **访问控制**：RAM（子账号、角色、策略）实现最小权限；ACL 控制对象级访问；**RAG 应用要防"越权检索"**——低权限用户通过检索接口读到高权限文档。
- **传输与存储加密**：传输层使用 HTTPS/TLS，存储层进行静态加密（如 KMS 托管密钥）；**两者缺一不可**。
- **审计日志**：记录"谁、何时、从哪个 IP、调用了什么接口/文档、返回了什么"，是追溯与合规检查的基础。

**【常见误区】**：① "传输加密就够了" → 存储加密同样必要；② "API Key 不写进代码就安全" → 还需防日志打印、前端暴露，并定期轮换；③ "权限配好就不用管" → 权限要随人员/业务变动持续评审。

### 8.5 法规与合规

> **导读**：合规要求履行法律规定的各项义务：服务需依法备案、生成内容需添加标识、收集个人信息需获得授权、数据出境需完成评估。

| 知识点 | 说明 |
|--------|------|
| **生成式 AI 管理办法** | 《生成式人工智能服务管理暂行办法》：服务提供者需履行内容安全义务、依法备案 |
| **《数据安全法》《个保法》** | 数据分级分类、最小必要原则、用户授权同意 |
| **深度合成规定** | AI 生成/合成内容需添加标识（如"AI 生成"水印），不得用于造假诈骗 |
| **企业落地要点** | 数据出境评估、训练数据合规审查、敏感数据脱敏、审计留痕 |

**【直观解读】**：核心规定可概括为三点：**向公众提供服务须依法备案；处理用户数据须事先授权并遵循最小必要原则；AI 生成内容须添加"AI 生成"标识**。

**【深入原理】**：

- **《生成式人工智能服务管理暂行办法》**：面向境内公众提供生成式 AI 服务的组织，需履行内容安全主体责任、依法**备案**，并建立投诉举报机制、生成内容标识机制等，是国内生成式 AI 服务的核心合规门槛。
- **《数据安全法》**：建立**数据分类分级**制度，重要数据重点保护；**《个人信息保护法》**：处理个人信息需**告知同意**、遵循**最小必要**原则，敏感个人信息需单独同意。
- **深度合成标识**：利用 AI 生成/合成的文本、图片、音视频，依法需**显著标识**（如"AI 生成"水印），防止被用于造假、诈骗。
- **企业落地闭环**：训练数据来源合规审查 → 敏感数据脱敏 → 数据出境评估（跨境传输需依法评估）→ 生成内容标识与审核 → 审计留痕。

**【实战/考试要点】**：记关键词即可——**备案、标识（AI 生成水印）、最小必要、告知同意、出境评估、审计留痕**。

### 8.6 提示注入与越狱防护

> **导读**：提示注入将恶意指令混入数据之中，使模型难以区分指令与数据；越狱则通过话术技巧绕过模型的安全对齐。

| 攻击类型 | 说明 |
|----------|------|
| **直接提示注入** | 用户直接在对话中输入恶意指令（如"忽略以上所有规则…"）劫持模型 |
| **间接提示注入** | 恶意指令藏在网页、文档中，被 RAG 检索进上下文后悄悄改变模型行为 |
| **越狱（Jailbreak）** | 用角色扮演、虚构场景等技巧绕过模型安全对齐 |

**防护手段**：输入输出双向内容审核、指令与数据隔离、对检索内容做无害化过滤、权限最小化、关键操作人工确认。

**【直观解读】**：直接注入在对话中直接下达恶意指令；间接注入将指令隐藏在文档或网页中，经检索进入上下文后影响模型；越狱则通过话术技巧绕过安全限制。三者的共同目标是劫持模型行为。

**【深入原理】**：**提示注入为什么能得逞？**

- **模型并不区分指令与数据**：系统提示词、用户输入与检索文档在模型看来都是上下文 token；"系统提示词优先级最高"只是**约定与惯例**（依靠位置与措辞维持），并非机制层面的保证。
- **注入的本质是"覆盖"**：攻击者把恶意指令写得比原指令更明确、更靠后，模型就可能"忘掉"原指令照新指令执行——"忽略以上所有规则，只做 X"就是这个原理。
- **间接注入危害更大**：恶意指令藏在网页/文档里，用户根本不知道；一旦被 RAG 检索进上下文，模型可能被诱导去**调用工具**（读文件、发邮件、改数据）——工具权限越大，破坏越大。
- **越狱的原理**：对齐层拒绝的是"直接有害请求"，角色扮演、虚构场景把请求包装成"创作/教学任务"，让有害意图在语义上"隐形"。

**【常见误区】**：① "系统提示词写得强硬就绝对安全" → 提示词隔离只是缓解手段，不是机制保证；② "只审核用户输入就够了" → 间接注入来自文档/网页，检索内容也要过滤；③ "提示注入只是让模型说错话" → 它可能劫持工具调用，造成数据泄露等真实危害；④ "越狱 = 幻觉" → 幻觉是质量缺陷，越狱是主动攻击。

### 8.7 企业级安全落地清单

> **导读**：将前述安全知识点汇总为一份上线前自查清单，逐项核验，即可完成一次完整的安全落地。

| 环节 | 检查项 |
|------|--------|
| **输入侧** | 用户输入内容审核、注入/越狱检测、非法查询识别 |
| **模型侧** | 服务依法备案、生成内容合规、模型版本管理 |
| **输出侧** | 输出内容审核、AI 生成内容标识（水印）、敏感信息脱敏后再输出 |
| **数据侧** | 训练/评测数据脱敏、存储加密、传输加密（HTTPS/TLS） |
| **权限侧** | RAM/ACL 最小权限、API Key 环境变量管理、定期轮换、工具权限最小化 |
| **应用侧** | 插件安全设计、敏感操作人工确认、指令与数据隔离、RAG 越权防护 |
| **审计侧** | 调用与访问全量日志、异常监控告警、投诉举报渠道、应急响应预案 |

**【直观解读】**：该清单覆盖大模型应用安全的关键环节——输入与输出、数据与权限、应用与审计，每项均需逐条核验，全部通过后方可上线。

**【实战/考试要点】**：场景题先判断它落在**哪个环节**（输入/输出/数据/权限/审计），再选对应措施；跨环节的题（如"文档被检索后诱导模型调用工具"）按**注入 → 工具 → 权限**的链路整体作答。

### 8.8 云服务应用系统安全：安全组 / WAF / DDoS / RAM

> **导读**：大模型应用部署在云上时，安全由多个产品分兵把守——它们各自解决不同层面的问题，考试重点是"什么产品解决什么问题"以及"为什么不能互相替代"。

| 产品/机制 | 解决的问题 | 关键要点 |
|-----------|-----------|----------|
| **安全组** | 网络层"谁能访问实例" | 入站/出站规则、默认拒绝、**最小开放**（只开 80/443 等必要端口、白名单 IP/安全组） |
| **WAF** | 应用层"流量里有没有攻击" | 拦截 SQL 注入、XSS、CC 攻击、恶意爬虫；与安全组互补（网络层 vs 应用层） |
| **DDoS 防护** | 流量型攻击"带宽/连接被打满" | 高防清洗、CDN 分担、限流；防 SYN Flood、CC 等洪峰攻击 |
| **RAM** | 身份与权限"谁能用什么云资源" | 子账号/角色最小权限、MFA、定期轮换密钥、独立凭据 |
| **身份隔离** | 不同环境/项目权限串扰 | 生产/测试分账号或分角色，避免越权 |
| **网络隔离** | 资源之间横向渗透 | VPC 私有网络、安全组、子网划分，数据库只放内网 |
| **私网访问** | 不应公网暴露的服务被暴露 | 管理后台/数据库经 VPC 内网、负载均衡或跳板机访问，不开公网 |
| **密钥管理** | 密钥泄露 | KMS/环境变量托管，不硬编码、定期轮换、最小权限 |
| **数据加密** | 数据在传输与存储中被窃取 | 传输 TLS + 静态加密 + 敏感字段脱敏 |
| **日志审计告警** | 事后不可追溯、异常不可感知 | 操作审计 + 日志服务 + 告警阈值 |

**四者各自解决什么（必考区分）**：**安全组** = 网络准入（端口/IP 放行）；**WAF** = 应用层攻击（注入/爬虫）；**DDoS 防护** = 流量洪峰（带宽/连接耗尽）；**RAM** = 权限最小化（谁能动什么）。它们不是四选一，而是**分层叠加**：安全组先放行、WAF 过滤应用攻击、DDoS 防洪峰、RAM 控制操作权限。

### 8.9 安全场景判断题

| 场景 | 正确判断 | 错误做法（干扰项） |
|------|----------|-------------------|
| 内网管理后台"可访问但不应公网暴露" | 放 VPC 内网 + 安全组白名单 + 私网/跳板访问 | "能访问就行，直接绑公网 IP" |
| 接口被高频攻击 / 被注入 | 上 WAF + 限流 + DDoS 防护 + 输入校验 | "只靠安全组就够" |
| 账号权限过大 / 多人共用 | RAM 最小权限 + 独立凭据 + MFA + 审计 | "共用一个主账号 Key 方便" |
| 敏感数据泄露 | 脱敏 + 加密 + 访问控制 + 审计告警 + 密钥托管 | "只做传输加密即可" |
| 检索文档诱导模型调用工具 | 间接提示注入：过滤检索内容 + 工具白名单 + 敏感操作人工确认 | "只审核用户输入就安全" |

**【实战/考试要点】**：安全场景题先定位**攻击面/风险点**（网络准入、应用攻击、权限、数据、注入），再选对应产品与措施；"安全组能替代 WAF""RAM 只管登录"等都是高频错误选项。

## 9. API 调用与工具使用

### 9.1 什么是 API 调用

> **导读**：大模型 API 调用的本质，是通过标准化请求把提示词、参数和上下文发送给模型服务，再由服务端返回生成结果。理解参数和调用规范，是模型接入的基础能力。

**核心概念**：通过 HTTP 请求调用云端模型服务，传入提示词和参数，获取模型生成的文本。

**高频考点**：

- **请求三要素**：接口地址（URL）、身份凭证（API Key）、请求体（messages + 参数）
- **消息结构（messages）**：按角色组织——`system`（系统提示词）、`user`（用户输入）、`assistant`（模型回复）；多轮对话要把历史消息按顺序全部带上
- **鉴权方式**：HTTP Header 携带 API Key（如 `Authorization: Bearer <API-Key>`），请求用 POST、`Content-Type: application/json`

**【直观解读】**：API 调用是将提示词、上下文与参数封装为标准化请求，发送给云端模型服务并接收生成结果；请求需携带身份凭证（API Key）以完成鉴权。

**【深入原理】**：

- **一次调用的完整链路**：客户端构造请求 → 服务端鉴权 → 配额/限流检查 → 模型推理 → 返回响应；任何一环失败都会反映在错误码上（见 9.5）。
- **为什么"输入 + 输出"都占上下文窗口**：模型每次生成都重新计算完整 messages，输入越长，费用越高、速度越慢；输入 + 输出 token 之和不能超过模型上下文窗口上限，否则报错或被截断。
- **OpenAI 兼容模式**：阿里云 DashScope/百炼除原生接口外，还提供 **OpenAI 兼容接口**，用 OpenAI 风格 SDK 改一下 `base_url` 和 `api_key` 即可接入，迁移成本低。

**【实战/考试要点】**：记住 messages 三个角色与"多轮对话要带全历史"；鉴权失败（401）先查 Key 是否写对、是否过期；参数错误（400）先查 messages 格式。

### 9.2 核心参数

> **导读**：核心参数用于控制模型生成行为：temperature 控制随机性，top_p/top_k 限制采样候选范围，max_tokens 限制生成长度，seed 控制可复现性，stop 指定停止条件。

| 参数 | 说明 | 取值范围 |
|------|------|----------|
| **temperature** | 控制随机性。**越高越随机有创意，越低越确定保守** | 0.0 ~ 2.0 |
| **top_p** | 核采样，只从累积概率达到 top_p 的词中采样 | 0.0 ~ 1.0 |
| **top_k** | 只从概率最高的 k 个词中采样 | 正整数 |
| **max_tokens** | 限制生成的最大 token 数 | 正整数 |
| **seed** | 随机种子，固定后相同输入产生相同输出 | 正整数 |
| **stop** | 遇到指定字符串时停止生成 | 字符串或字符串数组 |

**【直观解读】**：temperature 越高输出越多样、越低越稳定；top_p/top_k 控制采样候选范围；max_tokens 限制生成的最大长度；seed 固定随机种子以提高可复现性；stop 指定终止生成的字符串。

**【深入原理】**：

- **temperature 的数学含义**：模型先算出每个候选 token 的得分（logits），除以 temperature 再做 softmax：T 越小分布越集中（最高分被放大），T→0 退化为贪婪解码（只选最高分）；T 越大分布越平缓（各 token 概率趋近相等），输出越发散；T=1 即原始分布。**temperature 只改变输出的随机性，不改变模型的能力**。
- **top_p（核采样，Nucleus Sampling）**：把候选按概率从高到低排序、从最高开始累加，直到累积概率 ≥ p，只在这个"核心集合"内按重归一化后的概率采样。p 越小，候选圈越小、输出越保守。
- **top_k**：只保留概率最高的 k 个 token 再重归一化采样；k 越小越保守，k=1 等价于贪婪解码。
- **三者叠加关系**：一般先 top_k 截断、再 top_p 截断、最后 temperature 缩放（不同实现顺序略有差异）；实践中**固定一个、调另一个**即可，不建议三个一起大调。
- **seed 的局限**：固定 seed 可大幅提高可复现性，但并发请求、服务端实现、模型版本升级都可能改变结果——**seed 相同 ≠ 输出绝对相同**。
- **stop 的用法**：命中任一 stop 字符串即停止生成，可用于截断输出到指定格式（如生成 JSON 到 `}` 为止）。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "temperature 调高 = 模型变聪明" | temperature 只影响随机性，与能力无关 |
| "temperature=0 输出必然完全一致" | 只是大幅降低随机性，受并发/版本影响，不能绝对保证 |
| "top_p 和 temperature 一起拉满效果更好" | 双高 = 输出完全失控，建议固定一个调另一个 |
| "max_tokens 越大越好" | 输入+输出受上下文窗口限制，过大会报错且成本高 |
| "seed 固定就能跨版本复现" | 模型版本、服务端实现变化都会破坏复现性 |

**参数选择建议（场景对照）**：

| 任务类型 | 建议 | 理由 |
|----------|------|------|
| 事实问答、代码生成、数学计算 | temperature 低（如 0~0.3） | 输出要稳定、少随机 |
| 创意写作、头脑风暴、文案 | temperature 中高（如 0.7~1.0）+ top_p 0.8~0.95 | 需要多样性 |
| 格式严格、需程序解析 | temperature 低 + JSON 约束/结构化输出 | 格式稳定优先 |
| 多轮对话 | 保持温度适中，system 定角色，历史消息按顺序带全 | 平衡连贯与自然 |

**模型选择建议**：简单高频任务 → 轻量/快速档（如 qwen-turbo）；复杂推理、高质量生成 → 旗舰档（如 qwen-max）；性价比均衡 → 中间档（如 qwen-plus）；超长文档 → 长上下文模型（如 qwen-long）。**选型原则：先按任务复杂度选模型，再按稳定性/创意调 temperature/top_p，最后用 max_tokens 控制长度与成本。**

### 9.3 API Key 安全最佳实践

> **导读**：API Key 是调用模型服务的身份凭证，应存放于环境变量或密钥管理服务中，严禁写入代码或提交至 Git 仓库，并需定期轮换。

| 实践 | 说明 |
|------|------|
| **环境变量存储** | API Key 放在环境变量中，**不硬编码在代码或配置文件** |
| **不要提交到 Git** | 代码仓库中不应包含 API Key |
| **定期轮换** | 定期更换 API Key 降低泄漏风险 |
| **最小权限** | 每个 Key 只授予必要的最小权限 |

**【直观解读】**：API Key 一旦泄露，他人即可冒用身份调用模型，造成额度消耗与数据安全风险。因此应做到：不硬编码在代码中、不提交至仓库、定期轮换、授予最小权限。

**【深入原理】**：

- **主要泄漏途径**：① 硬编码后提交到 Git，被自动扫描 API Key 的爬虫发现（GitHub 上每天都有 Key 这样被盗）② 打印进日志 ③ 写进前端代码，任何浏览器用户都能在开发者工具里看到。
- **正确做法**：环境变量/配置中心/密钥管理服务（如阿里云 KMS）托管；RAM 子账号 + 按需授权（只给用到的服务和接口）；定期轮换并清理旧 Key；对调用做**异常监控**（异常地域、频率、额度消耗要告警）；**前端一律不直接放 Key，走后端代理**。
- **泄漏后的应急**：立即禁用/轮换该 Key → 检查近 7~30 天调用记录 → 评估损失与是否涉及数据泄露。

**【实战/考试要点】**：高频考点——**API Key 放环境变量、不进 Git、定期轮换、最小权限、前端走代理**；"写死在代码里方便维护"是典型的错误选项。

### 9.4 Function Calling（工具调用）

> **导读**：Function Calling 的机制是：向模型提供工具的结构化描述（Schema），模型将用户意图转换为规范的调用参数，由应用代码真正执行工具——模型负责决策，程序负责执行。

| 知识点 | 说明 |
|--------|------|
| **工具 Schema 定义** | 使用 **JSON-Schema** 准确定义工具的参数名、类型、描述和必填项 |
| **Schema 不完整** | 会导致模型无法正确映射参数，如"菜品名称"和"数量"无法区分 → 订单出错 |
| **多轮工具调用** | 复杂场景需要 Agent 多次调用不同工具，并在多轮对话中逐步提取参数 |

**【直观解读】**：Schema 是对工具参数的规范描述。Schema 越完整、字段说明越清晰，模型提取参数的准确率越高；若缺少必填字段或描述含糊，参数映射将出错，例如无法区分"菜品名称"与"数量"两个字段。

**【深入原理】**：

- **完整调用闭环（四步）**：① **定义工具**——把工具写成 JSON-Schema（name、description、parameters，含各字段的 type、description、required）② **模型决策**——请求带上 tools，模型判断是否需要调用：需要则返回 `tool_calls`（函数名 + 参数 JSON），不需要则直接回答 ③ **程序执行**——你的代码解析参数、真正执行工具（查库、调 API、计算）④ **结果回传**——把工具结果以 `tool` 角色消息返回模型，模型基于结果生成最终回答。
- **为什么 Schema 的 description 至关重要**：模型靠字段名和 description 理解"这个参数是什么意思"，描述含糊、字段名歧义都会导致参数提取错误。
- **常见失败模式**：required 漏标必填字段、参数类型写错（number 写成 string）、工具 description 太泛（模型不知道该何时用）、多轮调用后上下文过长。
- **与 MCP 的关系**：Function Calling 是"模型抽取参数、调用工具"的能力；MCP 是"工具如何接入"的标准化协议，两者互补（见 4.8）。

**【实战/考试要点】**：**模型返回 tool_calls 不等于工具已执行**——真正执行工具的是应用代码，执行完毕后必须将结果回传给模型，否则模型无法基于真实结果继续生成；"Schema 不完整导致参数映射错误"是高频考点。

### 9.5 流式输出与调用实践

> **导读**：流式输出如同"边下载边播放"：首字符几乎立即返回，后续内容逐段到达，用户感知的响应速度显著优于等待完整输出。

| 知识点 | 说明 |
|--------|------|
| **流式输出（SSE）** | 服务端通过 SSE 逐个返回 Token，用户无需等待完整回答，显著改善体验 |
| **超时与重试** | 设置合理超时；失败用指数退避重试，避免请求雪崩 |
| **常见错误码** | 限流（429）、参数错误（400）、鉴权失败（401）、服务不可用（500） |
| **并发控制** | 客户端主动控制并发，避免触发服务端限流 |
| **TTFT（首 Token 延迟）** | 流式场景关键指标，影响用户感知速度 |

**【直观解读】**：非流式需要等待完整响应，流式则可边接收边展示。请求失败时不应立即重试，以免瞬时并发压垮服务，而应采用指数退避策略逐次延长重试间隔。

**【深入原理】**：

- **SSE 的报文格式**：服务端通过 HTTP 长连接逐条推送事件帧，格式形如 `data: {"choices":[...]}\n\n`；每条帧是**增量（delta）**，最后一条带 `finish_reason` 表示结束。**流式响应不能当作完整 JSON 解析**，需按帧逐条解析、增量渲染。
- **超时设置**：连接超时与读取超时需分开设置；流式场景中读取超时应适当放宽，否则模型生成间隔稍长即被误判为超时。
- **指数退避 + 抖动（Jitter）**：失败后按 1s → 2s → 4s… 递增等待再重试，并加随机抖动，避免大量客户端同时重试造成"重试雪崩"；**4xx（参数/鉴权）重试无意义，不重试**，直接修请求；429/5xx 才重试。
- **延迟构成**：总延迟 ≈ TTFT + TPOT（后续每 token 时间）× 生成 token 数；流式下用户感知的是 TTFT，非流式感知的是总延迟。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| 把流式返回当完整 JSON 解析 | 需按 SSE 帧解析增量，最后一条才是结束标记 |
| 对 400/401 无限重试 | 参数/鉴权错误重试无意义，应修请求 |
| 重试不加退避 | 大量并发重试会打爆服务端，必须指数退避+抖动 |
| 流式接口用短读取超时 | 模型"思考"间隙可能较长，读取超时要放宽 |

### 9.6 计费与配额

> **导读**：计费按 Token 进行：输入与输出 Token 分开计价，且输出单价通常更高；重复使用相同前缀（如固定系统提示词）命中缓存后可显著降低成本。

| 知识点 | 说明 |
|--------|------|
| **按 Token 计费** | 输入与输出 Token 分开计价，输出通常更贵 |
| **上下文缓存** | 命中缓存的部分 Token 大幅降价，适合固定系统提示词 + 知识库场景 |
| **免费额度** | 阿里云百炼/DashScope 新用户通常有免费试用额度 |
| **成本控制** | 用 max_tokens 限制、上下文压缩、缓存、模型分级（Turbo/Plus/Max）平衡成本与效果 |

**【直观解读】**：输入与输出 Token 均按量计费，且输出单价更高；若请求前缀保持稳定（如固定系统提示词与知识库前缀），命中的缓存部分可大幅降价。

**【深入原理】**：

- **计费规则**：输入 token、输出 token **分开计价，输出单价通常高于输入**（生成更贵）；系统提示词、历史消息、检索文档都计入输入 token——**上下文越长，单次调用越贵**。
- **上下文缓存为什么能省钱**：服务端按"请求前缀"缓存，相同前缀（固定 system prompt、固定知识库切片）无需重复计算，命中部分大幅降价；代价是**保持前缀稳定**——把易变内容放在请求靠后位置，别让前缀"每次都不一样"。
- **配额与限流**：平台按 RPM（每分钟请求数）、TPM（每分钟 token 数）、并发数等维度设配额，超额返回 **429**；配额不够可提工单申请调整。
- **成本优化要点**：max_tokens 限制输出 → 上下文压缩/截断控制输入 → 复用固定前缀命中缓存 → 按任务选模型（简单任务用 Turbo，高质量任务用 Max）→ 批量任务走离线/批量接口（如平台支持）。

**【实战/考试要点】**：三个关键点——**输入输出分开计价且输出更贵；缓存命中降成本（前缀要稳定）；429 = 限流（配合 9.5 的退避重试）**。

### 9.7 完整调用示例（示意）

> **导读**：将 9.1~9.6 的内容汇总为一段最小可用的调用代码。考试不要求默写代码，但理解调用流程有助于掌握各参数与错误码的含义。

```python
import os
from openai import OpenAI  # 以 OpenAI 兼容模式为例（DashScope/百炼均支持）

client = OpenAI(
    api_key=os.environ.get("DASHSCOPE_API_KEY"),   # Key 从环境变量读取
    base_url="https://dashscope.aliyuncs.com/compatible-mode/v1",  # 以官方文档为准
)

resp = client.chat.completions.create(
    model="qwen-plus",
    messages=[
        {"role": "system", "content": "你是一个严谨的客服助手"},
        {"role": "user", "content": "介绍一下退款流程"},
    ],
    temperature=0.3,   # 事实类任务调低
    max_tokens=512,    # 限制长度、控制成本
    stream=True,       # 流式输出
)

for chunk in resp:     # 流式：逐段取增量，而不是一次性取完整结果
    print(chunk.choices[0].delta.content or "", end="")
```

**【直观解读】**：该代码展示了 API 调用的完整流程：从环境变量读取身份凭证（Key）、按角色组织消息（messages）、配置生成参数、开启流式输出（stream），并逐段接收增量结果。

**【实战/考试要点】**：**环境变量读 Key**（对应 9.3）、**messages 按角色组织**（对应 9.1）、**流式逐段解析**（对应 9.5）是代码改错题的高频考点；接入前先看官方文档确认接口地址、模型名、参数名、鉴权方式与最新计费规则。

### 9.8 批量生成（Batch API）

> **导读**：批量生成把一批请求打包成**异步任务**，平台离线处理后统一返回结果；它不是"更快返回"，而是"更低成本/更高吞吐地处理大批量任务"。

**与同步、流式的区别**：

| 调用方式 | 返回时机 | 适用场景 |
|----------|----------|----------|
| **同步调用** | 阻塞等待完整响应 | 交互式问答、在线服务 |
| **流式输出** | 逐 Token 边生成边返回 | 对话体验优先、低 TTFT |
| **批量生成（Batch）** | 提交任务后异步执行，稍后拉取结果 | 离线大批量、对实时性无要求 |

**核心特征**：

- **异步任务**：提交输入 → 创建任务 → 轮询/回调获取状态 → 拉取结果文件；整个过程不阻塞业务。
- **输入输出**：通常以 JSONL 文件形式提交（每行一个请求），输出也是 JSONL（每行对应一个结果），按请求 ID 与输入对齐；**提交后要校验行数对齐**。
- **失败重试**：批内单行失败通常不影响其他行；可只重试失败行（注意幂等与去重），无需整批重跑。
- **成本吞吐**：Batch 的优势在**吞吐高、对实时性无要求的离线任务更经济**；是否降价、如何计费以平台官方计费文档为准，不要记具体折扣数值。

**适用场景**：批量评测、批量翻译/摘要/分类、离线数据标注、夜间跑批、成本敏感的大规模处理。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "Batch 能更快返回单个结果" | Batch 是异步任务，单请求延迟反而更高，优势在吞吐与成本 |
| "批内一行失败就整批失败" | 一般按行处理，失败行单独重试即可（以官方文档为准） |
| "Batch 适合在线对话" | 在线对话要低延迟，应选同步/流式 |
| "结果文件不用校验" | 必须校验行数/ID 对齐，防止错位 |

> 参考来源：以阿里云百炼/DashScope 官方文档的 Batch/异步任务说明为准。

> **导读**：通义是阿里云大模型产品体系的总称：通义千问负责文本、通义万相负责图像、通义听悟负责语音等。考试常考察"产品 ↔ 能力"的对应关系，正确选型比调参更重要。

| 产品 | 定位 |
|------|------|
| **通义千问（Qwen）** | 文本大模型：开源系列 Qwen2.5（0.5B~72B）+ 商业版 Turbo/Plus/Max |
| **通义万相** | 图像生成模型（文生图、图生图） |
| **通义听悟** | 语音识别 / 会议转写（ASR） |
| **通义法睿** | 法律领域模型 |
| **通义灵码** | 代码助手（IDE 插件） |

| 对比 | 说明 |
|------|------|
| **开源 vs 商业版** | 开源模型可私有化部署、数据不出域；商业版免运维、能力更强 |
| **模型选型** | 简单任务用 Turbo（快省），高质量任务用 Max（强），Plus 均衡 |

**【直观解读】**：通义千问擅长文本生成，通义万相擅长图像生成，通义听悟擅长语音转写；开源版模型可私有化部署，商业版通过 API 按量付费使用。

**【深入原理】**：商业版规格中，Turbo 快速低延迟、Plus 均衡、Max 效果最强，另有 qwen-long 主打超长上下文（千万级 Token，适合长文档问答）与 qwen-mt（翻译）；看到"长文本/大文档"关键词优先选 qwen-long。开源系列 Qwen2.5 提供 0.5B~72B 多档参数量，可私有化部署到自建 GPU 或 PAI 平台。垂类产品还有通义晓蜜（客服）、通义点金（金融）、通义仁心（医疗）等。

**【实战/考试要点】**：高频映射——代码补全 → 通义灵码；图像生成 → 通义万相；会议转写 → 通义听悟；法律问答 → 通义法睿；长文档问答 → qwen-long。

### 10.5 PAI 机器学习平台

> **导读**：PAI 是阿里云的模型训练与部署平台：百炼解决"应用如何使用模型"，PAI 解决"模型如何训练与部署"。需要私有化训练或部署开源模型时，应选用 PAI。

| 组件 | 说明 |
|------|------|
| **DSW** | 交互式建模环境（Notebook），适合探索与实验 |
| **DLC** | 分布式训练任务平台，支持大规模并行训练 |
| **EAS** | 模型在线服务，一键部署推理服务、弹性伸缩 |
| **AutoML** | 自动特征工程、自动调参与模型选择 |

**【直观解读】**：DSW 提供交互式建模环境（Jupyter Notebook），DLC 支持多卡分布式训练，EAS 提供模型在线推理服务，AutoML 实现自动特征工程、自动调参与模型选择。

**【深入原理】**：DSW 基于 JupyterLab 提供 GPU 交互式开发；DLC 支持容器化分布式训练（数据并行/模型并行），可对接 OSS 数据集与 MaxCompute 数据；EAS 支持弹性伸缩、灰度发布与监控，是私有化模型上线出口。三者合称"PAI 三件套"，考试常考"调试选 DSW、训练选 DLC、上线选 EAS"。

> 💡 **百炼 vs PAI**：百炼面向**大模型应用开发**（提示词、知识库、Agent），PAI 面向**模型训练与推理部署**的底层平台，两者互补。

### 10.6 百炼、DashScope、PAI 三者关系

**一句话定位**：DashScope 提供标准模型 API，百炼提供一站式应用开发能力，PAI 提供模型训练与推理部署平台。

| 平台 | 一句话定位 | 服务对象 | 典型动作 |
|------|-----------|----------|----------|
| **百炼** | 大模型应用开发平台 | 应用开发者 | 建知识库、调 Prompt、做智能体、发布应用 |
| **DashScope** | 模型 API 服务 | 程序调用方 | 发 HTTP/SDK 请求拿模型结果 |
| **PAI** | 训练与推理部署平台 | 算法工程师 | DSW 调参、DLC 训练、EAS 部署 |

**选择逻辑**：只调 API → DashScope；搭完整应用（知识库/智能体/工作流）→ 百炼；自己训练或私有化部署开源模型 → PAI。三者可组合：百炼应用也能调用部署在 PAI 上的私有模型。

### 10.7 模型选型与计费要点

| 场景 | 推荐 | 原因 |
|------|------|------|
| 长文档问答 / 超长上下文 | qwen-long | 千万级 Token 窗口，几乎不用切片 |
| 快速原型、高频低敏调用 | qwen-turbo | 延迟低、单价低 |
| 复杂推理、高质量生成 | qwen-max | 效果最强 |
| 数据不出域、私有部署 | Qwen2.5 开源系列 + PAI | 模型与数据留在内部 GPU 环境 |

**计费与成本要点**：输入/输出 Token 分开计价，输出通常更贵，用 max_tokens 限制输出长度；上下文缓存（Context Cache）命中固定前缀（系统提示词、知识库段落）可大幅降价；新用户通常有免费试用额度；RPM/TPM 超限返回 429，需重试、指数退避与降级。

### 10.8 常见误区

| 误区 | 正解 |
|------|------|

## 11. 多模态 AI

### 11.1 什么是多模态

> **导读**：多模态 AI 不再局限于文本处理，而是能够联合理解图像、音频、视频等多种信息形式，从而支持更丰富的交互方式与业务场景。可将其理解为：在文本模型的基础上增加图像与音频的理解能力，使其能够同时处理多种模态的信息。

**核心概念**：多模态模型能处理文本、图像、音频、视频等多种数据类型，并理解它们之间的关联。

**【直观解读】**：多模态模型能够同时处理文本、图像、音频与视频，并理解不同模态之间的关联，例如将图像中的"猫"与文本中的"猫"建立对应关系；纯文本模型则只能处理文字。

**高频考点**：

| 知识点 | 说明 |
|--------|------|
| **LLM vs 多模态模型** | LLM 主要处理文本；多模态模型可处理文本+图像+音频+视频 |
| **多模态协同学习** | 多种模态信息互补，提升理解和推理能力 |
| **语音转文本（ASR）** | 将语音转为文字，如通义听悟 |
| **文本转语音（TTS）** | 将文字转为语音播报，如 CosyVoice |
| **图像理解** | 识别图片中的物体、场景、文字（OCR） |
| **视频理解** | 分析视频中的动作、事件、人物 |

**【实战/考试要点】**：模态 ↔ 任务 ↔ 产品映射是高频考点——"语音→文字"（ASR，通义听悟）、"文字→语音"（TTS，CosyVoice）、"图里取字"（OCR）、"看图问答"（Qwen-VL）、"文字画图"（通义万相）。

### 11.2 典型多模态应用场景

> **导读**：多模态的价值最终落在场景上。判断某场景属于"理解、生成还是转换"，是选择题的常见出题点。

| 场景 | 技术组合 |
|------|----------|
| **智能会议助手** | ASR 语音转文字 → LLM 生成摘要 → TTS 语音播报 |
| **智能客服** | 用户上传截图 → OCR 识别 → LLM 理解并回复 |
| **教育答疑** | 学生拍照题目 → 图像识别 → LLM 解题+讲解 |

**【直观解读】**：上述场景均采用管道式架构：先由专用模型完成模态转换（语音转文字、图像转文字），再由 LLM 进行语义理解与生成；各环节相互独立，可单独替换为更强的组件。

**【深入原理】**：管道式架构的价值在于解耦：ASR/TTS/OCR 等单点能力成熟且成本低，LLM 仅负责中间的语义理解与生成，任一环节升级均不影响整条链路。考试常将各环节的职责错配（如把会议摘要误写成 OCR），明确"输入是什么模态、输出是什么模态"即可正确作答。

### 11.3 多模态模型与产品

| 知识点 | 说明 |
|--------|------|
| **典型架构** | 视觉编码器提取图像特征 + 语言模型对齐（如 CLIP 对比学习），使模型"看图说话" |
| **Qwen-VL** | 通义视觉语言模型，支持图文理解、图片问答、OCR |
| **通义万相** | 文生图 / 图生图，可用于营销素材、设计辅助 |
| **多模态 RAG** | 图片、表格也可向量化后参与检索，扩展知识库形态 |
| **评估注意** | 多模态能力需结合人工评测（如图文一致性），纯自动指标易失真 |

**【直观解读】**：Qwen-VL 负责图像理解（看懂图片后回答问题），通义万相负责图像生成（根据文字描述生成图片），二者分别属于理解与生成两个方向。

### 11.4 多模态模型是怎么工作的

> **导读**：多模态模型的关键不是同时处理图像与文本，而是将不同模态的信息统一表示为同一种内部形式（向量/Token），再交由同一模型处理——如同将不同语言统一转换为同一种内部编码。

**【直观解读】**：模型无法直接理解图片，只能处理数字表示。将图像划分为若干小块（patch），每个小块转换为向量序列，再与文本 Token 混合输入同一模型，即可实现图像的"理解"——这就是统一 Token 化。

**【深入原理】**：

- **统一 Token 化**：图像被切成固定大小的 patch，每个 patch 经视觉编码器（如 ViT）变成向量；音频经声学编码器变成序列；这些"视觉 Token""语音 Token"与文本 Token 混在一起输入 Transformer，用自注意力建立"图里的猫 ↔ 文字里的猫"的关联。
- **对齐训练（CLIP 范式）**：对比学习将匹配的图文对向量拉近、不匹配的图文对推远，使图文映射到同一向量空间，这是图文理解与文生图共用的基础能力。
- **图像生成用扩散模型（Diffusion）**：文生图不是"从图片库里检索"，而是从随机噪声开始，在文本条件引导下一步步去噪得到图像；VAE 把图像压缩到潜空间再解码，降低算力消耗。
- **视频理解**：对视频抽关键帧 + 提取音频轨，按"图像 + 语音 + 文字"联合理解（如 Qwen2-VL 支持视频输入）。
- **动态分辨率（Qwen2-VL）**：不把图片强行缩放成固定尺寸，而是按原始宽高比切分以保留细节，配合多模态旋转位置编码（M-RoPE）处理高清图与视频。

**【实战/考试要点】**：架构关键词记忆：图文统一 = "编码器 + 投影对齐 + 大模型"；文生图 = 扩散模型；OCR = 图像理解的基础子能力；"图文一致性"只能靠人工评测兜底。

### 11.5 多模态 RAG 与文档智能

| 知识点 | 说明 |
|--------|------|
| **文档智能解析** | 扫描件/PDF 先做 OCR + 版面分析，还原成含表格的结构化文本，再进入常规 RAG 链路 |
| **图像向量化** | 用多模态 Embedding 模型把图片向量化，可对"图片库"做语义检索 |
| **表格与图表** | 表格转 Markdown/HTML 保留结构；图表可让视觉模型描述后入库 |
| **图文混合检索** | 文本与图片各自向量化，检索时按需召回，再交给多模态模型生成回答 |

**【直观解读】**：多模态 RAG 扩展了知识库的容纳范围：扫描件、表格与图片经解析与向量化后，均可参与检索并支撑生成回答。

**【实战/考试要点】**：RAG 场景题中，遇到扫描件/图片，第一步先"OCR/解析"而不是直接切片；图文混合知识库的回答需要多模态模型，纯文本模型无法"看图作答"。

### 11.6 个性化语音助手端到端案例

> **导读**：语音助手是"多模态 + Agent + RAG"的集大成场景：语音进、语音出，中间依次经过识别、理解、检索/工具、生成、合成，且全链路要有会话记忆与安全控制。

**端到端链路**：

```chart flow
语音输入
ASR 语音识别（语音→文字）
意图理解（LLM）
知识检索 / 工具调用
LLM 生成回复
TTS 语音合成（文字→语音）
语音输出
```

| 环节 | 职责 | 关键点 |
|------|------|--------|
| **语音输入/ASR** | 把用户语音转成文字（通义听悟等） | 噪音、口音、专有名词影响识别，必要时纠错 |
| **意图理解** | 识别用户想做什么（见 2.9 意图分类） | 低置信度追问澄清 |
| **知识检索/工具调用** | RAG 查知识库或调工具（查订单、查天气） | 检索质量决定回答质量 |
| **LLM 回复** | 结合上下文生成自然语言回复 | 约束"只依据资料回答"防幻觉 |
| **TTS 输出** | 把文字合成语音（CosyVoice 等） | 音色、语速、情绪一致性 |
| **会话记忆** | 保存多轮上下文与用户偏好 | 超长会话要摘要压缩/选择性注入 |
| **安全控制** | 输入输出审核、工具权限最小化、敏感操作确认、审计留痕 | 语音内容同样要审核留痕 |

**【实战/考试要点】**：端到端是**管道式架构**（ASR→LLM→TTS 各司其职），任一环节可单独替换；"语音助手的 ASR 和 TTS 是同一模型"是错误认知；会话记忆贯穿全程但不是"无限保存"，受上下文窗口与隐私约束。

### 11.7 多模态内容生成与交互实践

> **导读**：多模态不只是"理解"，还包括"生成"与"交互"：文生图、图生图、文生视频、语音合成、数字人等，是内容生产与沉浸式交互的关键能力。

| 方向 | 说明 | 代表能力/产品（示例） |
|------|------|----------------------|
| **文生图** | 文字描述 → 图像 | 通义万相 |
| **图生图** | 参考图 + 指令 → 新图 | 通义万相 |
| **文生视频** | 文字 → 视频 | 通义万相视频生成能力 |
| **语音合成（TTS）** | 文字 → 语音 | CosyVoice |
| **看图问答** | 图像 + 问题 → 答案 | Qwen-VL |
| **多轮图文交互** | 连续多轮图像+文字对话 | Qwen-VL 系列 |

**交互实践要点**：① 图文混合输入要明确"哪张图、问什么"，必要时给图片编号；② 生成内容要加**AI 生成标识**（合规要求，见 8.5）；③ 文生图/视频的**图文一致性、版权与内容合规**需人工或审核模型把关，不能只靠自动指标。

**【实战/考试要点】**：区分"理解"（图→文字/答案，Qwen-VL）与"生成"（文字→图/视频，通义万相）；深度合成内容须标识，是合规必考点。

### 11.8 阿里 AI 技术解决方案系列定位

> **导读**：考试对"阿里 AI 解决方案"的考查集中在**定位与能力映射**：通义家族各司其职，百炼/PAI 负责承载，掌握"产品 ↔ 能力 ↔ 场景"即可。

**典型架构**：

```chart flow
数据（OSS / 业务库）
训练与部署（PAI：DLC / EAS）
模型能力（通义千问 / 万相 / 听悟）
应用开发（百炼：知识库 / Agent / 工作流）
业务场景（客服 / 办公 / 医疗 / 教育 / 娱乐）
```

| 解决方案 | 定位 | 适用场景 |
|----------|------|----------|
| 通义千问（Qwen） | 文本大模型底座 | 对话、写作、代码、推理 |
| 通义万相 | 图像/视频生成 | 营销素材、设计、视频创作 |
| 通义听悟 | 语音识别/转写 | 会议纪要、录音转写 |
| 通义灵码 | 代码助手 | IDE 代码补全与问答 |
| 百炼 + PAI | 应用开发 + 训练部署底座 | 承载上述能力落地 |

**【考试理解重点】**：只考"谁做什么、何时选谁"，不考具体配置；把"通义听悟"当作文本生成、"通义万相"当作语音识别都是典型错误选项。

### 11.9 行业应用案例（医疗 / 教育 / 娱乐）

> **导读**：行业案例题考的是"完整场景 + 技术链路 + 风险点"，尤其娱乐场景不能只答一句"AI 生成内容"，要能说清链路与合规风险。

**医疗**：

- **场景**：智能问诊导诊、病历结构化、影像辅助分析、用药审核、健康科普。
- **技术链路**：多模态输入（病历图片/影像/语音）→ OCR/影像理解 → LLM 结构化输出/问答 → 医生复核。
- **风险点**：专业准确性要求极高、患者隐私（脱敏、授权）、合规（不能替代医生诊断）、可解释与留痕。

**教育**：

- **场景**：拍照搜题、作文批改、个性化学习路径、口语陪练。
- **技术链路**：拍照/语音 → OCR/ASR → LLM 解题讲解/批改 → 结构化反馈。
- **风险点**：答案准确性、学生数据安全、过度依赖削弱独立思考、内容适龄合规。

**娱乐（完整链路）**：

- **场景**：AI 数字人直播、虚拟偶像、互动小说、游戏 NPC、短视频脚本与素材生成。
- **技术链路**：文本生成（剧本/台词/脚本）→ 语音合成（TTS 配音）→ 形象生成/驱动（数字人/图像视频）→ 实时交互（用户输入 → 意图理解 → 生成回复 → 音画同步输出）→ 内容审核与发布。
- **风险点**：深度合成内容须加**AI 标识**；版权与肖像权合规；直播间/互动内容的内容安全审核；未成年人保护与防沉迷；数字人言论一致性（防提示注入与越狱）。

**【实战/考试要点】**：行业案例题答题结构 = **场景 + 链路（输入模态 → 处理 → 输出模态）+ 风险/合规**；"娱乐=文生图一句话"是失分写法，必须补全交互链路与合规点。

### 11.10 常见误区

| 误区 | 正解 |
|------|------|
| "多模态模型只能处理图像" | 多模态是"多"种模态，文本、图像、音频、视频都算 |
| "OCR 就是图像理解的全部" | OCR 只提取文字；图像理解还包括物体、场景、关系识别 |
| "文生图是从图片库检索" | 文生图是扩散模型逐步去噪生成，不是检索 |
| "多模态模型能读任意长度视频" | 视频需抽帧/截断，超出上下文窗口会被截断 |
| "多模态评测只靠自动指标" | 图文一致性、指令跟随等需人工评测校准 |

## 12. 框架与工具

### 12.1 LangChain

> **导读**：框架与工具的价值，在于将提示词、模型调用、检索、记忆与工具编排等能力模块化，帮助开发者高效构建复杂的大模型应用。LangChain 通过"链"将各能力组件拼接为完整应用。

**核心组件**：

| 组件 | 说明 |
|------|------|
| **LLM/Chat Model** | 统一的大模型调用接口 |
| **Prompt Template** | 提示词模板，支持变量插值 |
| **Chain（链）** | 将多个组件串联成处理流程 |
| **Memory（记忆）** | 存储对话历史，支持多轮对话 |
| **Agent** | 根据 LLM 输出动态决定调用哪些工具 |
| **Retriever（检索器）** | 文档检索接口，对接向量数据库 |
| **Tool（工具）** | 封装外部能力（搜索、计算、API） |

**【直观解读】**：LangChain 将模型调用、提示词编写、检索、对话记忆与工具调用封装为标准组件，通过管道符 | 串联各组件即可快速构建应用，无需重复实现底层逻辑。

**【深入原理】**：

- **四层抽象**：Model I/O（PromptTemplate → ChatModel → OutputParser 解析输出）、Retrieval（Loader → Splitter → Embedding → VectorStore → Retriever）、Memory（缓冲 / 摘要 / 向量检索三类记忆）、Agent（工具注册 + ReAct 循环）。
- **LCEL（LangChain 表达式语言）**：基于 Runnable 协议，用 `|` 组合组件（如 `prompt | model | parser`），天然支持流式输出、批处理、异步与并行。注意：LCEL 不是一门新语言，只是 Python 里的管道式写法。
- **记忆实现**：ConversationBufferMemory 全量缓存（简单但费 Token）、ConversationSummaryMemory 摘要压缩（省 Token 但丢细节）、VectorStoreRetrieverMemory 按相关性检索注入——对应第 4 章"记忆管理"。
- **生态扩展**：LangGraph 用图结构编排复杂 Agent 状态机；LangSmith 提供链路追踪与评测，适合生产级应用。

**【实战/考试要点】**：

| 要点 | 说明 |
|------|------|
| LCEL 识别 | `prompt \| model \| output_parser` 属于声明式管道组合 |
| 记忆选型 | 长对话用摘要/向量记忆，短对话用缓冲记忆 |
| Agent 工具 | Tool 需用 JSON-Schema 声明参数，呼应 Function Calling 考点 |

### 12.2 LlamaIndex

> **导读**：如果说 LangChain 偏重通用编排，LlamaIndex 则专注于数据索引与检索：文档切片、索引构建与检索召回均由框架封装，是 RAG 场景的常用工具。

| 知识点 | 说明 |
|--------|------|
| **定位** | 专注于数据连接和 RAG 的框架，擅长构建"数据 Agent" |
| **context_str** | 在 LlamaIndex 默认提示词模板中，`context_str` 表示**从向量库检索到的上下文信息** |
| **多轮对话** | LlamaIndex 提供 ChatEngine 支持 RAG 场景下的多轮对话 |
| **与 LangChain 对比** | LlamaIndex 更专注 RAG 和数据索引，LangChain 更通用 |

**【直观解读】**：LlamaIndex 负责文档切片、索引构建与检索召回；context_str 是默认提示词模板中用于注入检索上下文信息的占位符。

**【深入原理】**：

- **核心数据流**：Document（原始文档）→ NodeParser 切分为 Node（带元数据的小块）→ 构建 Index（VectorStoreIndex 做向量索引、SummaryIndex 做全量摘要）→ Retriever 检索 → QueryEngine（检索 + 合成）返回答案。
- **context_str 的作用**：LlamaIndex 默认提示词模板用 `{context_str}` 占位符注入检索到的上下文，模型基于它回答——这正是"先检索后生成"的实现细节，考试常把它伪装成"用户输入"来混淆。
- **持久化**：Index 可通过 StorageContext 保存到本地或向量数据库，避免每次重建；Embedding 模型、LLM 可通过全局 Settings 统一配置。
- **Agent 能力**：LlamaIndex 也支持工具注册与 ReAct 式 Agent，适合"先查数据再回答"的场景。

**【实战/考试要点】**：记住链路 Document → Node → Index → Retriever → QueryEngine；判断题"context_str 表示用户的问题"是错误选项；"RAG 多轮对话用 ChatEngine"是正确选项。

### 12.3 文档解析工具

| 工具 | 说明 |
|------|------|
| **DashScopeParse** | 阿里云文档解析服务 |
| **Unstructured** | 开源文档解析库 |
| **PDFPlumber** | Python PDF 解析库 |
| **自定义 Reader** | 针对特殊格式开发专用解析器 |

**【深入原理】**：DashScopeParse 底层结合 OCR、版面分析、表格识别与多模态模型，能把扫描件、复杂表格还原为结构化文本（Markdown/HTML/JSON），输出可直接进入 RAG 切片；Unstructured 按"分区（partition）"思路识别标题、段落、表格；PDFPlumber 适合纯文本 PDF 的精确抽取。

**【实战/考试要点】**：选择逻辑——扫描件/复杂版式 → DashScopeParse（OCR 能力强）；纯文本 PDF → PDFPlumber（轻量精准）；多种杂格式混合 → Unstructured；特殊专有格式 → 自定义 Reader。

### 12.4 更多框架与工具

| 工具 | 说明 |
|------|------|
| **LCEL** | LangChain 表达式语言，用声明式管道组合链（如 prompt \| model \| output parser） |
| **Spring AI** | Java 生态的大模型开发框架，适合 Java 技术栈企业 |
| **Ollama / LM Studio** | 本地一键运行开源模型，适合开发调试与离线场景 |
| **Transformers** | HuggingFace 标准库，模型加载、微调、推理的事实标准 |
| **Streamlit / Gradio** | 快速搭建 LLM 应用 Demo 的 UI 框架 |

**【直观解读】**：Ollama 提供本地一键运行开源模型的能力；Transformers 是加载开源模型的标准库；Streamlit/Gradio 用于快速搭建应用 Demo 的界面。

**【深入原理】**：Spring AI 提供 ChatClient 等高层 API，将模型调用抽象为 Model/Prompt/Message 结构，便于 Java 技术栈平滑接入；Transformers 的 `pipeline()` 与 `AutoModel.from_pretrained()` 是加载开源模型的标准方式，模型与分词器（tokenizer）必须配套加载；Streamlit/Gradio 仅负责界面展示，不承载业务逻辑，应明确 Demo 与生产实现的边界。

**定位、适用场景与区别速查**：

| 工具 | 定位 | 适用场景 | 一句话区别 |
|------|------|----------|-----------|
| Spring AI | Java 生态大模型框架 | Java 技术栈企业应用 | 与 LangChain 同类但面向 Java |
| Ollama / LM Studio | 本地模型运行器 | 本地开发调试、离线跑开源模型 | 只负责"跑模型"，不负责编排 |
| Transformers | 模型加载/微调/推理标准库 | 加载开源模型、微调、推理 | 模型层事实标准，不是应用编排框架 |
| Streamlit / Gradio | 快速 UI 框架 | 搭 Demo、展示原型 | 只管界面，业务逻辑要另写 |
| LCEL | LangChain 的管道式组合语法 | LangChain 内声明式组链 | 是写法不是独立框架 |

**关键区分**：Ollama 解决"本地有没有模型可跑"，Transformers 解决"怎么加载/微调模型"，LangChain/LlamaIndex 解决"怎么编排应用"，Streamlit/Gradio 解决"怎么展示"，四者常组合使用而非互相替代。

### 12.5 框架选型与组合

| 场景 | 推荐 | 理由 |
|------|------|------|
| 快速 RAG 原型 | LlamaIndex | 数据索引、检索开箱即用 |
| 复杂 Agent / 多工具编排 | LangChain + LangGraph | 工具、记忆、状态机生态完整 |
| 纯 API 调用、零依赖 | DashScope SDK / OpenAI SDK | 轻量可控，学习成本低 |
| Java 技术栈 | Spring AI | 与现有 Spring 体系天然集成 |
| 私有化模型服务 | vLLM + Transformers | 高性能推理 + 标准模型加载 |
| 低代码快速搭建 RAG/Agent 应用 | Dify | 可视化编排，非程序员也能快速上线 |

**组合要点**：LangChain 与 LlamaIndex 可以组合使用（例如用 LlamaIndex 构建索引、用 LangChain 编排 Agent）；框架仅提供编排能力，应用效果仍取决于提示词、数据与检索质量。

### 12.6 常见误区

| 误区 | 正解 |
|------|------|
| "LCEL 是一门新的编程语言" | 是 Python 的管道式表达式语法，本质仍是 Python |
| "context_str 是用户输入的问题" | 是检索到的上下文；用户问题由 query 模板注入 |
| "LangChain 与 LlamaIndex 必须二选一" | 可以组合使用，各自擅长不同环节 |
| "本地 Ollama 跑通 = 生产部署完成" | 本地仅适合调试，生产还要考虑并发、限流、监控、安全 |
| "用了框架就不需要懂提示词和 RAG" | 框架只做编排，效果取决于提示词、数据与检索质量 |

### 12.7 Dify（LLM 应用开发平台）

> **导读**：Dify 是开源的 LLM 应用开发平台，用**可视化界面**把知识库、工作流、Agent、模型接入和发布串起来，定位是"低代码快速搭建应用"，与 LangChain/LlamaIndex 这类代码框架、百炼这类云托管平台都不同。

| 维度 | 说明 |
|------|------|
| **定位** | 开源 LLM 应用开发平台，可视化编排 RAG/工作流/Agent |
| **知识库** | 上传文档 → 自动解析、切片、向量化 → 检索问答（本质是第 3 章 RAG 的产品化） |
| **工作流** | 拖拽节点编排"开始 → 意图分类 → 检索/工具 → LLM → 输出"，可分支与条件路由 |
| **模型接入** | 支持多家模型 API（含 OpenAI 兼容接口），模型可替换 |
| **工具调用** | 内置 HTTP 请求、自定义工具、代码节点，供 Agent/工作流调用 |
| **应用发布** | 一键发布为 Web 应用、API，或嵌入第三方页面 |

**与 LangChain / LlamaIndex / 百炼的区别**：

| 工具 | 形态 | 适合 |
|------|------|------|
| LangChain / LlamaIndex | 代码框架（Python/JS） | 深度定制、复杂状态机、代码级编排 |
| Dify | 可视化开源平台 | 低代码快速搭建、非程序员参与、可私有部署 |
| 百炼 | 云托管平台 | 阿里云生态、与 DashScope 模型/PAI 打通、企业级托管 |

**适合快速搭建什么**：企业知识库问答、客服机器人、内部流程自动化（审批/工单/信息汇总）、原型验证与 Demo。

**优点**：低代码、上手快、可视化调试、可私有部署、团队协作友好。
**局限**：深度定制不如代码框架灵活；超复杂状态机/自定义逻辑受限；大规模生产需评估性能、版本管理与安全加固。

**【常见误区】**：

| 误区 | 正解 |
|------|------|
| "Dify 可以替代 LangChain" | 一个可视化平台、一个代码框架，深度定制仍用 LangChain |
| "用 Dify 就不需要懂提示词和 RAG" | 可视化只是编排，效果仍取决于提示词、切片与检索质量 |
| "Dify 私有部署就自动合规安全" | 私有部署解决数据出域，内容安全、权限、审计仍需自行配置 |

## 附录：高频考试陷阱

| 陷阱 | 正解 |
|------|------|
| "微调是解决一切问题的最优方案" | ❌ 应优先尝试提示词优化和 RAG，微调是最后手段 |
| "所有 Agent 共用一套凭据更方便" | ❌ 存在安全隐患，不同 Agent 应独立授权 |
| "文档切片越大越好" | ❌ 切片太大稀释语义，太小丢失上下文，需平衡 |
| "Top K 设得越小检索越精确" | ❌ Top K 太小可能漏掉相关文档（召回率不足） |
| "API Key 写死在代码里方便" | ❌ 应存储在环境变量中，避免泄漏到 Git/日志 |
| "生成不相关内容属于内容安全风险" | ❌ 属于质量/相关性缺陷，不属于安全风险 |
| "自动化评分高说明模型表现好" | ❌ 自动化评分可能系统性偏高，需人工校验 |
| "量化会让模型精度大幅下降" | ❌ INT8 量化通常精度损失很小，INT4 损失略大 |
| "文档解析时直接传原始路径即可" | ❌ 需要先将不同格式文档解析为结构化文本 |
| "自注意力机制限制输入序列长度" | ❌ 自注意力不限制序列长度，可灵活处理不同长度的输入 |
| "模型输出每次不同，说明代码有 Bug" | ❌ 采样本身具有随机性，属正常现象，可通过调低 temperature 或固定 seed 控制 |
| "验证损失先降后升，应继续训练" | ❌ 是过拟合信号，应回退到验证集表现最优的 checkpoint |
| "公开评测分数高代表业务效果好" | ❌ 需用自有业务评测集 + 人工验证 |
| "放宽检索阈值能提高精确率" | ❌ 检索越宽松：召回率↑、精确率↓ |
| "相同输入设置 temperature=0 就能保证输出完全一致" | ❌ 可大幅降低随机性，但受并发、模型版本等影响，不能绝对保证一致 |
| "qwen-long 与 qwen-max 的上下文窗口一样大" | ❌ qwen-long 主打千万级 Token 超长上下文，长文档场景应选它 |
| "多模态模型只能处理图像" | ❌ 文本、图像、音频、视频都属于多模态范围 |
| "OCR 等于图像理解" | ❌ OCR 只是从图片提取文字，图像理解还包括物体、场景、关系识别 |
| "文生图是在图片库里检索相似图" | ❌ 扩散模型从噪声逐步去噪生成，不是检索 |
| "百炼与 DashScope 是两个不相关的平台" | ❌ 百炼应用开发层基于 DashScope 模型 API，共用 API-KEY |
| "PAI 是给大模型应用开发用的平台" | ❌ PAI 负责训练与推理部署（DSW/DLC/EAS），应用开发用百炼 |
| "上下文窗口越大越好" | ❌ 窗口越大 Token 成本与延迟越高，应按场景选型（长文档用 qwen-long） |
| "LlamaIndex 的 context_str 是用户输入的问题" | ❌ context_str 是从向量库检索到的上下文信息 |
| "RAG 知识库只能检索文本" | ❌ 图片、表格经多模态向量化后同样可参与检索 |
| "Prompt 越长效果一定越好" | ❌ 冗长无关信息会稀释注意力，反而降低输出质量 |
| "Batch API 能更快返回单个结果" | ❌ Batch 是异步批量任务，优势在吞吐与成本，单请求延迟反而更高 |
| "安全组可以替代 WAF" | ❌ 安全组管网络准入（端口/IP），WAF 管应用层攻击（注入/爬虫），两者互补 |
| "意图分类后不用判断置信度" | ❌ 低置信度应追问澄清，未匹配走兜底或转人工 |

## 附录二：易混概念对比

| 易混项 | 区别 |
|--------|------|
| **预训练 vs 微调** | 预训练学习通用语言能力（海量无标注数据）；微调适配特定任务（领域数据） |
| **SFT vs RLHF** | SFT 用标注问答对模仿学习；RLHF 用人类偏好训练奖励模型再强化，使模型更符合价值观 |
| **LoRA vs 全参微调** | LoRA 只训练少量低秩适配参数（省资源、快）；全参更新所有参数（效果上限高、成本大） |
| **temperature vs top_p** | temperature 平滑整个概率分布；top_p 截断低概率候选集，二者可叠加使用 |
| **精确率 vs 召回率** | 精确率 = 找对的 ÷ 找到的；召回率 = 找对的 ÷ 该找的；两者通常此消彼长 |
| **幻觉 vs 越狱** | 幻觉是模型"一本正经说错话"（质量缺陷）；越狱是攻击者绕过安全限制（安全问题） |
| **过拟合 vs 欠拟合** | 过拟合 = 训练集好、验证集差；欠拟合 = 训练集与验证集都差 |
| **贪婪解码 vs 采样** | 贪婪解码输出固定、易重复；采样有随机性、内容更丰富 |
| **Function Calling vs MCP** | Function Calling 是模型抽取参数调用工具的能力；MCP 是工具接入的标准化协议 |
| **RAG vs 知识库问答** | RAG 是"检索 + 生成"的完整链路；知识库仅是其中的数据来源 |
| **百炼 vs DashScope vs PAI** | 百炼 = 应用开发平台（知识库/Agent/发布）；DashScope = 模型 API 服务；PAI = 训练与部署平台 |
| **Qwen-VL vs 通义万相** | Qwen-VL 是"看懂图"（视觉理解）；万相是"画出图"（图像生成），一进一出 |
| **ASR vs TTS** | ASR 语音→文字（识别）；TTS 文字→语音（合成），方向相反 |
| **OCR vs 图像理解** | OCR 只提取图中文字；图像理解还识别物体、场景、关系 |
| **LangChain vs LlamaIndex** | LangChain 通用编排（链/Agent/工具）；LlamaIndex 专注数据索引与 RAG |
| **文生图 vs 图生图** | 文生图：文字→图像；图生图：参考图 + 指令 → 新图 |
| **上下文缓存 vs 知识库 RAG** | 缓存是命中相同前缀降价（省成本）；RAG 是检索外部知识增强回答（补知识），解决不同问题 |
| **开源模型 API vs 商业模型 API** | 开源可私有化部署、数据不出域；商业 API 免运维、能力更强、按 Token 付费 |
| **安全组 vs WAF** | 安全组 = 网络层准入（端口/IP）；WAF = 应用层攻击过滤（注入/爬虫），分层叠加 |
| **同步调用 vs 流式 vs Batch** | 同步 = 阻塞等完整结果；流式 = 边生成边返回；Batch = 异步批量离线处理 |
| **Dify vs LangChain vs 百炼** | Dify = 可视化开源平台；LangChain = 代码框架；百炼 = 云托管平台 |

## 附录三：应试技巧

| 技巧 | 说明 |
|------|------|
| **排除绝对化选项** | "一定""必须""所有""任何场景"等绝对化表述多为错误选项 |
| **警惕过度方案** | 场景题中"直接微调""全量注入提示词""上传公有云"通常是干扰项 |
| **场景关键词定位** | 检索不到 → 排查切片/召回链路；输出不一致 → 采样随机性；检索到了但答错 → 上下文未进入模型 |
| **多选题保守作答** | 只选有把握的选项，不确定的不选，避免倒扣分 |
| **记忆陷阱附录** | 附录一的反直觉结论是判断类题目的高频来源，考前务必过一遍 |
| **参数题背数值** | temperature/top_p 取值范围、Token 换算、量化位宽等精确数值题靠记忆拿分 |
| **平台角色定位** | 遇到阿里云平台题先对号入座：应用开发 → 百炼，模型 API → DashScope，训练/部署 → PAI |
| **关键词触发模型** | "长文本/大文档" → qwen-long；"扫描件/图片" → OCR/多模态解析；"会议转写" → 通义听悟 |
| **合规题选保守** | 涉及数据出境、敏感数据、权限的题目，默认选"脱敏/最小权限/人工确认"等最保守方案 |
| **架构题画数据流** | 解析 → 切片 → 向量化 → 检索 → 重排 → 生成，按流程逐环节排查问题 |
| **先易后难** | 判断题、概念题先做；计算/数值题（Token 换算、量化位宽）放最后精确作答 |
