## 7. 模型评估

### 7.1 为什么需要评估

> **导读**：评估的目的不是简单“打分”，而是用可量化的方法判断模型是否满足业务目标，并据此发现短板、定位问题、指导后续优化。

**核心概念**：模型评估是通过定量指标和定性分析，衡量模型在特定任务上表现的系统方法。

**高频考点**：

- **评估的五大用途**：发现短板、定位问题、指导优化、防止回归（改坏了没有）、辅助选型（换不换模型）
- **评估的本质**：把“主观质量感受”翻译成“可测量、可复现的指标”——没有评估，就没有优化的依据

**【白话版】**：评估就像给学生“出卷考试”：先定好考什么（指标）、出好卷子（评测集）、统一阅卷规则（固定配置），分数才能横向比较，也才知道该补哪块短板。

**【深入原理】**：为什么不能“凭感觉”判断模型好坏？

- 大模型输出是**概率性的**，同一次输入多次输出可能不同，必须用“一批样本 + 统一配置”做统计评估并**控制变量**（冻结评测集版本、推理参数、模型版本），否则分数差异无法归因；业务要的是“用户满意度、转化率”，而模型产出的是 token 序列，中间必须靠**任务定义 → 指标设计 → 评测集**转译。

**【实战/考试要点】**：先评测再优化（而不是“感觉不对就调”）；评测集要冻结版本（改了之后历史分数不可比）；指标要匹配任务（摘要用 ROUGE、翻译用 BLEU、分类用 Accuracy/F1、语言模型看 PPL）。

### 7.2 自动化评估指标

> **导读**：自动评估指标就像“机器阅卷”：靠“参考答案 + 数学公式”打分，速度快、可复现，但阅卷规则简单，容易“看走眼”。

| 指标 | 适用场景 | 说明 |
|------|----------|------|
| **BLEU** | 机器翻译 | 比较生成文本与参考文本的 n-gram 重叠度，侧重**精确率** |
| **ROUGE** | 文本摘要 | 基于最长公共子序列（LCS），衡量召回率。核心维度：**召回率、精确率、F1 分数** |
| **Perplexity（困惑度）** | 语言模型 | 衡量模型对文本的“惊讶程度”，越低越好 |
| **准确率（Accuracy）** | 分类任务 | 正确预测数 / 总数 |
| **F1 分数** | 分类任务 | 精确率和召回率的调和平均，综合考量 |

**【白话版】**：BLEU 考“用词像不像参考答案”（偏严格）；ROUGE 考“参考答案该说的说全了没”（偏宽松）；困惑度考“模型对这段话熟不熟”——越不惊讶（越低）越见多识广。

**【深入原理】**：

- **BLEU 怎么算**：先算 n-gram 精确率 pₙ（生成文本中出现在参考译文里的 n-gram 占比），对 1~4 gram 取几何平均，再乘**简洁惩罚 BP**（brevity penalty）防止“只翻译半句”：BLEU = BP × exp(Σ wₙ·log pₙ)，生成越短 BP 越小、分数被惩罚。
- **ROUGE 怎么算**：ROUGE-N 基于 n-gram 重叠，**默认侧重召回率**（参考内容被覆盖多少）；ROUGE-L 基于**最长公共子序列（LCS）**，不要求内容连续。三个维度：召回率 = 参考内容被覆盖的比例，精确率 = 生成内容中有效信息的比例，F1 = 2PR/(P+R) 是二者的调和平均，比算术平均更“惩罚偏科”。
- **困惑度含义**：PPL = exp(每个 token 平均负对数似然)，约等于“模型在每个位置平均要从多少个等概率候选词里做选择”（PPL=10 ≈ 平均 10 个候选里猜 1 个），**越低越好**。注意：PPL 低 ≠ 回答正确，它衡量“概率预测的把握”而非“事实正确”。

**【常见误区】**：① “BLEU 高 = 翻译质量好” → 只认字面重合，同义改写会误伤，短译文还有 BP 惩罚；② “ROUGE 能衡量语义等价” → 同义改写会让 ROUGE 偏低；③ “PPL 低 = 模型更聪明” → PPL 只反映概率预测，事实错误照样 PPL 很低；④ “只看 Accuracy” → 类别不平衡时失真，要看 P/R/F1。

### 7.3 评估注意事项

> **导读**：机器打分快但容易“虚高”；让模型给模型打分（LLM-as-Judge）灵活，但“阅卷老师”也有自己的偏好，要先调教好。

| 知识点 | 说明 |
|--------|------|
| **自动化评分 vs 人工评测** | 自动化评分偏高是常见问题，需人工校准 |
| **LLM-as-Judge** | 用一个大模型给另一个大模型的输出打分。**需调整评分提示词和阈值，避免系统性偏差** |
| **专业领域评测** | 医疗、法律等专业场景**必须由领域专家参与评测**，仅靠自动化指标不够 |
| **评测样本集** | 应覆盖各类题型和难度，分布要合理 |
| **评测与优化闭环** | 评测 → 找到短板 → 针对性优化 → 再评测 |

**【白话版】**：自动评分像“机器阅卷”，容易给“长得像答案”的输出打高分；LLM-as-Judge 像“请另一位老师阅卷”，这位老师也有脾气（偏爱长答案、偏爱先看到的答案），要先约好评分标准再打分。

**【深入原理】**：

- **自动化评分为什么偏高**：n-gram 类指标偏爱与参考答案**字面重合**的输出；基于模型的自动评分常见**长度偏差**（更长得分更高）、**位置偏差**（先出现的答案更受青睐）、**自我偏好**（打分模型偏爱与自己风格一致的输出）。
- **LLM-as-Judge 校准方法**：① 评分提示词明确维度、量表和输出格式（如只输出 JSON 分数）② 交换候选顺序多次打分取平均（抵消位置偏差）③ 提供参考答案与评分样例 ④ 多 Judge 投票 ⑤ 定期用人工标注校准阈值。

**【实战/考试要点】**：自动指标负责“批量粗筛”，人工负责“精准把关”；评测集要**分层设计**（简单/中等/困难、短/长文本、正常/对抗样本），全考简单题会让分数虚高。

### 7.4 常见公开评测基准

> **导读**：公开基准就像“全国统一模拟考”，分数可横向对比模型；但模拟考 ≠ 你公司的真实业务考试，不能只盯着它。

| 基准 | 评测内容 |
|------|----------|
| **MMLU** | 多学科知识理解（英文） |
| **C-Eval** | 中文知识能力评测 |
| **GSM8K** | 小学数学推理（检验推理与计算能力） |
| **HumanEval** | 代码生成正确性 |
| **CMMLU / CMATH** | 中文综合能力 / 中文数学 |

> ⚠️ 公开基准分数高 ≠ 业务表现好：基准反映通用能力，业务场景必须用**自有评测集 + 领域专家**验证。

**【白话版】**：MMLU 考英文知识面、C-Eval 考中文知识面、GSM8K 考数学推理、HumanEval 考写代码——考得好说明底子好，但“底子好”不等于“你公司的活干得好”。

**【深入原理】**：

- **MMLU**：涵盖 STEM、人文、社科等 57 个学科的多选题，检验知识广度，是英文模型的主流基准。
- **GSM8K**：约 8.5K 道小学数学应用题，需要**多步推理**，专门检验“模型会不会一本正经算错”。
- **HumanEval**：164 道手写 Python 编程题，用 **pass@k** 计分——生成 k 个候选，只要有 1 个通过全部单元测试即算通过。

**【常见误区】**：公开基准可能被“刷分”（评测题泄露进训练数据）、与业务题型不一致、语言分布不匹配（中文场景还应参考 C-Eval、CMMLU、CMATH）——**公开基准用于选型粗筛，业务决策必须用自建评测集**。

### 7.5 评测落地流程

> **导读**：整个流程就是“考试 → 改错 → 重考”的循环：每次改完都用同一套卷子重考（回归评测），上线前再小范围真刀真枪试一次（AB 测试），防止“补了数学、丢了语文”。

```
明确评测目标 → 构建评测集（覆盖各类题型/难度） → 确定指标 → 运行评测
→ 分析短板 → 针对性优化（提示词/RAG/微调） → 回归评测 → 上线灰度/AB 验证
```

| 知识点 | 说明 |
|--------|------|
| **回归评测** | 每次优化后跑同一套评测集，防止“修好 A、弄坏 B” |
| **AB 测试** | 新旧版本分流对比线上真实效果 |
| **人工抽查** | 自动化评分后按比例人工复核，校准系统性偏差 |

**【白话版】**：先定标准（目标）→ 出卷（评测集）→ 考试（跑评测）→ 看错题（分析短板）→ 补课（优化）→ 重考（回归）→ 小范围试运行（AB 测试），每一步都有明确动作。

**【深入原理】**：

- **回归评测的前提是“同一套卷子”**：评测集版本、评测脚本、推理参数（temperature、seed、模型版本）都要冻结，分数变化才能归因于“这次改动”。
- **AB 测试要点**：线上真实流量按比例分流（如新版本 10%），对比业务指标；**同一用户尽量固定到同一版本**（避免会话内体验割裂），样本量要足够（差异才有统计显著性），观察期要覆盖不同流量特征。

**【常见误区】**：① 用训练数据当评测集 → 数据泄漏、分数虚高；② 每次优化都换评测集 → 分数不可比；③ 只看平均分 → 掩盖类别短板；④ 只跑一次不回归 → 发现不了“修好 A、弄坏 B”。

### 7.6 常用评测工具与平台

> **导读**：评测不一定要从零写代码，社区和云平台已有“现成的阅卷系统”，会选用能省下大量时间。

| 工具/平台 | 说明 |
|-----------|------|
| **Ragas** | 开源 RAG 评估框架，内置 Context Recall/Precision、Faithfulness、Answer Relevancy 等指标（与第 3 章 RAG 评估指标对应） |
| **DeepEval** | 开源 LLM 评估框架，支持把评测用例组织成“单元测试”式断言 |
| **OpenAI Evals** | OpenAI 开源的评估框架，适合自建评测集与回归评测 |
| **LangSmith** | LangChain 生态的链路观测与评测平台，可记录调用 trace 并对输出打分 |
| **阿里云百炼评测** | 平台内置评测能力，支持自动化与人工评测 |

**【白话版】**：Ragas 专治 RAG 应用的“跑题、乱编”；DeepEval 把评测写成单元测试方便持续回归；百炼则在云端帮你组织评测集和打分。

**【实战/考试要点】**：工具可以换，**评测集、指标与流程才是核心**——先想清楚“考什么、怎么算分”再选工具，评估体系要能沉淀为“同一套卷子反复用”。

## 8. AI 安全与合规

### 8.1 为什么需要安全机制

> **导读**：随着模型能力增强，内容生成、数据泄露、越狱攻击和权限滥用等风险也随之增加。安全与合规不是附加项，而是大模型落地过程中的基础要求。

**核心概念**：AI 安全包括内容安全、数据安全、模型安全和访问控制等多个维度。

**高频考点**：

- **安全的四个维度**：内容安全（模型“说什么”）、数据安全（数据“怎么管”）、模型安全（模型“怎么防攻击”）、访问控制（谁“能用什么”）
- **核心思路：纵深防御（Defense in Depth）**：输入侧 → 模型侧 → 输出侧 → 应用侧 → 审计侧，层层设防、互为兜底

**【白话版】**：安全机制就像给模型装“刹车、保险丝和行车记录仪”：能力越强，越要防止它被误用；安全不是上线后的补丁，而是从一开始就要设计好的“安全带”。

**【深入原理】**：为什么安全不能只靠模型本身？

- **对齐（Alignment）只约束模型，约束不了输入**：安全对齐让模型“学会拒绝”，但用户输入、检索文档、网页内容都是模型无法预先防备的，必须在应用链路加防护；攻击者还会不断发明新绕法（角色扮演、编码混淆、间接注入），单一防线必然被击穿，所以安全措施必须**可升级、可监控、可响应，多层布防**。

**【实战/考试要点】**：区分“安全”还是“质量”问题是高频考点——**生成不相关内容/说错数字 = 质量缺陷；被诱导输出违法内容、越权访问数据 = 安全问题**。

### 8.2 内容安全风险

> **导读**：内容安全风险就是“模型可能说出不该说的话”：要么自己“学坏”（违法、偏见），要么被坏人“带坏”（越狱、注入）。

| 风险类型 | 说明 |
|----------|------|
| **违法信息** | 生成涉及暴力、色情、诈骗等违法内容 |
| **虚假信息** | 生成看似合理但事实错误的内容（幻觉） |
| **偏见与歧视** | 模型训练数据中的偏见被放大 |
| **越狱攻击（Jailbreak）** | 用户通过特殊提示词绕过安全限制 |
| **提示注入（Prompt Injection）** | 在用户输入中嵌入恶意指令劫持模型行为 |

> ⚠️ “生成不相关内容”不属于内容安全风险，属于质量/相关性缺陷。

**【白话版】**：前两类是模型“自己出错”（能力/数据问题），后两类是“被人利用”（攻击问题）；“跑题、说错”只是能力缺陷，不是安全事故。

**【深入原理】**：

- **虚假信息（幻觉）的根源**：大模型是“概率续写器”，遇到没把握的内容会“一本正经地编”，编出来的内容语法通顺、逻辑自洽，人工难以察觉。
- **偏见从哪来**：训练数据本身存在分布偏差（某些群体样本少、刻板印象表达多），模型学到的“统计规律”就带着偏见——这是**数据问题**，不是模型“故意的”。

**【常见误区】**：① “模型说错一个数字 = 安全问题” → 属事实性/质量问题；② “幻觉 = 模型在撒谎” → 是概率生成的自然缺陷；③ “偏见只能靠审核解决” → 根本治理靠数据清洗与对齐。

### 8.3 安全防护措施

> **导读**：防护措施就是“在门口设两道安检”：进门的输入要查（有没有恶意指令），出门的输出也要查（有没有违规内容），中间再给模型戴上“行为护栏”。

| 措施 | 说明 |
|------|------|
| **内容审核** | 对输入和输出进行自动审核过滤 |
| **Guardrail（护栏）** | 设定模型行为边界，拦截不安全请求 |
| **非法查询识别** | 识别并拒绝回答非法/违规查询 |
| **插件安全设计** | 不安全的插件设计可能导致数据泄露或权限滥用 |
| **API Key 安全管理** | 将 API Key 配置在**环境变量**中，而非硬编码在代码里。可避免泄漏到版本库或被日志打印 |

**【白话版】**：内容审核像“安检机”扫进出的内容；Guardrail 像“行为守则”贴在墙上，越界就拦；API Key 像银行卡密码，必须放保险箱（环境变量/密钥服务），不能写在便利贴（代码）上。

**【深入原理】**：

- **内容审核怎么做**：“规则 + 模型”结合——关键词/正则先粗筛，再用审核模型（文本、图片、语音分类）细判，可对接阿里云内容安全等服务；**输入、输出双向审核**缺一不可。
- **Guardrail 与插件安全**：Guardrail 把“模型不该做什么”从“靠模型自觉”变成“应用层强制执行”（敏感话题黑名单、输出格式约束、工具调用白名单、敏感操作二次确认）；插件获得的能力 = 攻击者可利用的能力，工具权限越大、提示注入破坏越大，所以要**权限最小化 + 关键操作人工确认**。
- **API Key 泄漏路径**：硬编码进 Git 被自动化爬虫扫描、打印进日志、写进前端页面；正确做法是环境变量/配置中心/KMS 托管 + 定期轮换 + 最小权限 + 异常调用监控。

**【实战/考试要点】**：高频考点一句话——**API Key 放环境变量、输入输出双向审核、敏感操作人工确认、权限最小化**。

### 8.4 数据安全

> **导读**：数据安全就是保证“数据在传输、存储、使用三个环节都不泄露”：路上要加密（HTTPS）、仓库要上锁（加密存储）、进门要查证件（访问控制）、全程要留记录（审计）。

| 知识点 | 说明 |
|--------|------|
| **数据脱敏** | 训练/推理前对敏感信息进行脱敏处理 |
| **访问控制** | 通过 RAM/ACL 控制数据和模型的访问权限 |
| **传输加密** | 数据传输使用 HTTPS/TLS 加密 |
| **审计日志** | 记录所有 API 调用和数据访问行为，便于追溯 |

**【白话版】**：脱敏是“把身份证号打码再拿去用”；访问控制是“谁有什么权限一清二楚”；审计日志是“行车记录仪”，出事能追责。

**【深入原理】**：

- **脱敏（去标识化）**：对姓名、证件号、手机号、地址等敏感字段做替换/掩码/泛化；RAG 场景中，企业知识库的敏感文档也要在进入检索链路前做权限标记。
- **访问控制**：RAM（子账号、角色、策略）实现最小权限；ACL 控制对象级访问；**RAG 应用要防“越权检索”**——低权限用户通过检索接口读到高权限文档。
- **传输与存储加密**：传输层 HTTPS/TLS，存储层静态加密（如 KMS 托管密钥），**只做一半等于没做**；审计日志记录“谁、何时、从哪个 IP、调用了什么、返回了什么”，是追溯与合规检查的基础。

**【常见误区】**：① “传输加密就够了” → 存储加密同样必要；② “API Key 不写进代码就安全” → 还需防日志打印、前端暴露并定期轮换；③ “权限配好就不用管” → 权限要随人员/业务变动持续评审。

### 8.5 法规与合规

> **导读**：合规就是“法律规定的动作一个都不能少”：服务要备案、生成内容要打标识、收集个人信息要授权、数据出境要评估。

| 知识点 | 说明 |
|--------|------|
| **生成式 AI 管理办法** | 《生成式人工智能服务管理暂行办法》：服务提供者需履行内容安全义务、依法备案 |
| **《数据安全法》《个保法》** | 数据分级分类、最小必要原则、用户授权同意 |
| **深度合成规定** | AI 生成/合成内容需添加标识（如“AI 生成”水印），不得用于造假诈骗 |
| **企业落地要点** | 数据出境评估、训练数据合规审查、敏感数据脱敏、审计留痕 |

**【白话版】**：三部规定记成三句话——**给公众提供服务先备案；动用户的数据先授权、只拿必要的；AI 生成的东西要贴“AI 生成”标签**。

**【深入原理】**：

- **《生成式人工智能服务管理暂行办法》**：面向境内公众提供生成式 AI 服务的组织，需履行内容安全主体责任、依法**备案**，并建立投诉举报机制、生成内容标识机制等，是国内生成式 AI 服务的核心合规门槛。
- **《数据安全法》与《个保法》**：《数据安全法》建立**数据分类分级**制度，重要数据重点保护；《个人信息保护法》要求处理个人信息**告知同意**、遵循**最小必要**原则，敏感个人信息需单独同意。
- **深度合成标识与落地闭环**：利用 AI 生成/合成的文本、图片、音视频依法需**显著标识**（如“AI 生成”水印）防止造假诈骗；企业落地按“训练数据来源合规审查 → 敏感数据脱敏 → 数据出境评估 → 生成内容标识与审核 → 审计留痕”闭环推进。

**【实战/考试要点】**：记关键词即可——**备案、标识（AI 生成水印）、最小必要、告知同意、出境评估、审计留痕**。

### 8.6 提示注入与越狱防护

> **导读**：提示注入像“把病毒藏在快递包裹里骗过安检”——恶意指令混在数据里，模型分不清指令和数据；越狱像“骗过门卫”——用话术让模型以为自己在干好事。

| 攻击类型 | 说明 |
|----------|------|
| **直接提示注入** | 用户直接在对话中输入恶意指令（如“忽略以上所有规则…”）劫持模型 |
| **间接提示注入** | 恶意指令藏在网页、文档中，被 RAG 检索进上下文后悄悄改变模型行为 |
| **越狱（Jailbreak）** | 用角色扮演、虚构场景等技巧绕过模型安全对齐 |

**防护手段**：输入输出双向内容审核、指令与数据隔离、对检索内容做无害化过滤、权限最小化、关键操作人工确认。

**【白话版】**：直接注入是“当面抢方向盘”，间接注入是“把指令藏进资料里让模型自己翻到”；越狱是“花言巧语骗过安全员”——三者都是要劫持模型行为。

**【深入原理】**：**提示注入为什么能得逞？**

- **模型的“眼里”没有指令和数据之分**：系统提示词、用户输入、检索文档在模型看来都是“上下文 token”；“系统提示词优先级最高”只是**约定与惯例**（靠位置和措辞维持），不是机制层面的保证；注入的本质是**覆盖**——恶意指令比原指令更明确、更靠后时，模型就可能照新指令执行（“忽略以上所有规则，只做 X”就是这个原理）。
- **间接注入危害更大**：恶意指令藏在网页/文档里，用户根本不知道；一旦被 RAG 检索进上下文，模型可能被诱导去**调用工具**（读文件、发邮件、改数据）——工具权限越大，破坏越大。
- **越狱的原理**：对齐层拒绝的是“直接有害请求”，角色扮演、虚构场景把请求包装成“创作/教学任务”，让有害意图在语义上“隐形”。

**【常见误区】**：① “系统提示词写得强硬就绝对安全” → 提示词隔离只是缓解手段；② “只审核用户输入就够了” → 间接注入来自文档/网页；③ “提示注入只是让模型说错话” → 它可能劫持工具调用；④ “越狱 = 幻觉” → 幻觉是质量缺陷，越狱是主动攻击。

### 8.7 企业级安全落地清单

> **导读**：把前面的安全知识点串成一张“上线前自查表”，逐项打勾，就是一次完整的安全落地。

| 环节 | 检查项 |
|------|--------|
| **输入侧** | 用户输入内容审核、注入/越狱检测、非法查询识别 |
| **模型侧** | 服务依法备案、生成内容合规、模型版本管理 |
| **输出侧** | 输出内容审核、AI 生成内容标识（水印）、敏感信息脱敏后再输出 |
| **数据侧** | 训练/评测数据脱敏、存储加密、传输加密（HTTPS/TLS） |
| **权限侧** | RAM/ACL 最小权限、API Key 环境变量管理、定期轮换、工具权限最小化 |
| **应用侧** | 插件安全设计、敏感操作人工确认、指令与数据隔离、RAG 越权防护 |
| **审计侧** | 调用与访问全量日志、异常监控告警、投诉举报渠道、应急响应预案 |

**【实战/考试要点】**：场景题先判断它落在**哪个环节**（输入/输出/数据/权限/审计），再选对应措施；跨环节的题（如“文档被检索后诱导模型调用工具”）按**注入 → 工具 → 权限**链路整体作答。

## 9. API 调用与工具使用

### 9.1 什么是 API 调用

> **导读**：大模型 API 调用的本质，是通过标准化请求把提示词、参数和上下文发送给模型服务，再由服务端返回生成结果。理解参数和调用规范，是模型接入的基础能力。

**核心概念**：通过 HTTP 请求调用云端模型服务，传入提示词和参数，获取模型生成的文本。

**高频考点**：

- **请求三要素**：接口地址（URL）、身份凭证（API Key）、请求体（messages + 参数）；消息按角色组织——`system`（系统提示词）、`user`（用户输入）、`assistant`（模型回复），多轮对话要把历史消息按顺序全部带上
- **鉴权方式**：HTTP Header 携带 API Key（如 `Authorization: Bearer <API-Key>`），请求用 POST、`Content-Type: application/json`

**【白话版】**：API 调用就像“给云端模型发微信”：把要说的话（提示词）、聊天记录（上下文）和设置（参数）打包发过去，它把回复发回来；发消息要证明“是你发的”——这就是 API Key 的作用。

**【深入原理】**：

- **一次调用的完整链路**：客户端构造请求 → 服务端鉴权 → 配额/限流检查 → 模型推理 → 返回响应；任何一环失败都会反映在错误码上（见 9.5）。模型每次生成都重新计算完整 messages，**输入 + 输出 token 之和不能超过上下文窗口上限**，否则报错或被截断，输入越长越贵越慢。
- **OpenAI 兼容模式**：阿里云 DashScope/百炼除原生接口外，还提供 **OpenAI 兼容接口**，用 OpenAI 风格 SDK 改一下 `base_url` 和 `api_key` 即可接入。

**【实战/考试要点】**：记住 messages 三个角色与“多轮对话要带全历史”；鉴权失败（401）先查 Key；参数错误（400）先查 messages 格式。

### 9.2 核心参数

> **导读**：这些参数像“点菜的备注”：temperature 决定厨师敢不敢创新，top_p/top_k 决定候选菜谱范围，max_tokens 决定最多上几道菜，seed 决定能不能“复刻同一桌菜”。

| 参数 | 说明 | 取值范围 |
|------|------|----------|
| **temperature** | 控制随机性。**越高越随机有创意，越低越确定保守** | 0.0 ~ 2.0 |
| **top_p** | 核采样，只从累积概率达到 top_p 的词中采样 | 0.0 ~ 1.0 |
| **top_k** | 只从概率最高的 k 个词中采样 | 正整数 |
| **max_tokens** | 限制生成的最大 token 数 | 正整数 |
| **seed** | 随机种子，固定后相同输入产生相同输出 | 正整数 |
| **stop** | 遇到指定字符串时停止生成 | 字符串或字符串数组 |

**【白话版】**：temperature 管“胆量”（越高越敢天马行空）、top_p/top_k 管“候选圈有多大”、max_tokens 管“话最多说多长”、seed 管“能不能复制同一次输出”、stop 管“说到哪个词就闭嘴”。

**【深入原理】**：

- **temperature 的数学含义**：模型先算出每个候选 token 的得分（logits），除以 temperature 再做 softmax：T 越小分布越“尖锐”（最高分被放大），T→0 退化为贪婪解码（只选最高分）；T 越大分布越“平坦”（各 token 概率趋近相等），输出越发散；T=1 即原始分布。**temperature 只改变随机性，不改变模型“聪明程度”**。
- **top_p / top_k 的数学含义**：top_p（核采样，Nucleus Sampling）把候选按概率从高到低排序、从最高开始累加，直到累积概率 ≥ p，只在这个“核心集合”内按重归一化后的概率采样；top_k 只保留概率最高的 k 个 token 再重归一化采样（k=1 等价于贪婪解码）。二者都是“先截断、再采样”，p/k 越小越保守；与 temperature 叠加时一般先截断再缩放，实践中**固定一个、调另一个**即可。
- **seed 与 stop**：固定 seed 可大幅提高可复现性，但并发请求、服务端实现、模型版本升级都可能改变结果——**seed 相同 ≠ 输出绝对相同**；stop 是命中任一字符串即停止生成，可用于截断输出到指定格式（如生成 JSON 到 `}` 为止）。

**【常见误区】**：① “temperature 调高 = 模型变聪明” → 只影响随机性，与能力无关；② “temperature=0 输出必然完全一致” → 受并发/版本影响，不能绝对保证；③ “top_p 和 temperature 一起拉满效果更好” → 双高 = 输出完全失控；④ “max_tokens 越大越好” → 输入+输出受上下文窗口限制，过大会报错且成本高。

### 9.3 API Key 安全最佳实践

> **导读**：API Key 就是“模型的银行卡密码”——要放在保险箱（环境变量/密钥服务）里，不能写在便利贴（代码/Git）上，还要定期换密码。

| 实践 | 说明 |
|------|------|
| **环境变量存储** | API Key 放在环境变量中，**不硬编码在代码或配置文件** |
| **不要提交到 Git** | 代码仓库中不应包含 API Key |
| **定期轮换** | 定期更换 API Key 降低泄漏风险 |
| **最小权限** | 每个 Key 只授予必要的最小权限 |

**【白话版】**：Key 一旦泄露，别人就能“刷你的卡”调用模型、烧你的钱、读你的数据；所以：不写死在代码里、不进仓库、常换、权限最小。

**【深入原理】**：

- **主要泄漏途径**：① 硬编码后提交到 Git，被自动扫描 API Key 的爬虫发现 ② 打印进日志 ③ 写进前端代码，任何浏览器用户都能在开发者工具里看到。
- **正确做法**：环境变量/配置中心/密钥管理服务（如阿里云 KMS）托管；RAM 子账号 + 按需授权；定期轮换并清理旧 Key；对调用做**异常监控**；**前端一律不直接放 Key，走后端代理**；泄漏后立即禁用/轮换并检查近期调用记录。

**【实战/考试要点】**：高频考点——**API Key 放环境变量、不进 Git、定期轮换、最小权限、前端走代理**；“写死在代码里方便维护”是典型的错误选项。

### 9.4 Function Calling（工具调用）

> **导读**：Function Calling 是“让模型学会填表”：你给模型一张工具说明书（Schema），模型把用户的话翻译成规范的结构化参数，再由你的程序真正执行——模型负责“想”，程序负责“做”。

| 知识点 | 说明 |
|--------|------|
| **工具 Schema 定义** | 使用 **JSON-Schema** 准确定义工具的参数名、类型、描述和必填项 |
| **Schema 不完整** | 会导致模型无法正确映射参数，如“菜品名称”和“数量”无法区分 → 订单出错 |
| **多轮工具调用** | 复杂场景需要 Agent 多次调用不同工具，并在多轮对话中逐步提取参数 |

**【白话版】**：Schema 就是“工具说明书”，写得越清楚，模型填表越准；说明书缺参数、描述含糊，模型就会填错——“菜品名称”和“数量”混为一谈，订单就错了。

**【深入原理】**：

- **完整调用闭环（四步）**：① **定义工具**——把工具写成 JSON-Schema（name、description、parameters，含各字段的 type、description、required）② **模型决策**——请求带上 tools，模型判断是否需要调用：需要则返回 `tool_calls`（函数名 + 参数 JSON），不需要则直接回答 ③ **程序执行**——你的代码解析参数、真正执行工具 ④ **结果回传**——把工具结果以 `tool` 角色消息返回模型，模型基于结果生成最终回答。
- **为什么 Schema 的 description 至关重要**：模型靠字段名和 description 理解“这个参数是什么意思”，描述含糊、字段名歧义都会导致参数提取错误；常见失败还有 required 漏标必填字段、参数类型写错、工具描述太泛、多轮调用后上下文过长。

**【实战/考试要点】**：**模型返回 tool_calls ≠ 工具已执行**——真正执行的是你的程序，执行完必须把结果回传给模型，否则模型只能“盲猜”；“Schema 不完整导致参数映射错误”是高频考点。

### 9.5 流式输出与调用实践

> **导读**：流式输出像“看直播”而不是“等录播”——第一个字几乎立刻出现，后面的字一个个蹦出来，用户感知到的“速度”完全不同。

| 知识点 | 说明 |
|--------|------|
| **流式输出（SSE）** | 服务端通过 SSE 逐个返回 Token，用户无需等待完整回答，显著改善体验 |
| **超时与重试** | 设置合理超时；失败用指数退避重试，避免请求雪崩 |
| **常见错误码** | 限流（429）、参数错误（400）、鉴权失败（401）、服务不可用（500） |
| **并发控制** | 客户端主动控制并发，避免触发服务端限流 |
| **TTFT（首 Token 延迟）** | 流式场景关键指标，影响用户感知速度 |

**【白话版】**：非流式像“等整集电视剧下载完再看”，流式像“边下边看”；出错时不能立刻傻乎乎重试（会挤爆服务），要“越等越久地重试”（指数退避）。

**【深入原理】**：

- **SSE 长什么样**：服务端通过 HTTP 长连接逐条推送事件帧，格式形如 `data: {"choices":[...]}\n\n`；每条帧是**增量（delta）**，最后一条带 `finish_reason` 表示结束。**流式响应不能当完整 JSON 解析**，要按帧逐条解析、增量渲染。
- **超时与重试**：连接超时与读取超时分开设置（流式读取超时要宽松，否则“模型思考稍长就被误判超时”）；失败按 1s → 2s → 4s… 指数退避并加随机抖动（Jitter），避免重试雪崩；**4xx（参数/鉴权）重试无意义，不重试**，直接修请求；429/5xx 才重试。
- **延迟构成**：总延迟 ≈ TTFT + TPOT（后续每 token 时间）× 生成 token 数；流式下用户感知的是 TTFT，非流式感知的是总延迟。

**【常见误区】**：① 把流式返回当完整 JSON 解析 → 应按帧解析增量；② 对 400/401 无限重试 → 重试无意义，应修请求；③ 重试不加退避 → 大量并发重试会打爆服务端；④ 流式接口用短读取超时 → 应放宽。

### 9.6 计费与配额

> **导读**：计费像“按字数付钱”——读进去的字（输入）和吐出来的字（输出）分开计价，且输出更贵；同一段“开场白”反复用（缓存命中）可以打折。

| 知识点 | 说明 |
|--------|------|
| **按 Token 计费** | 输入与输出 Token 分开计价，输出通常更贵 |
| **上下文缓存** | 命中缓存的部分 Token 大幅降价，适合固定系统提示词 + 知识库场景 |
| **免费额度** | 阿里云百炼/DashScope 新用户通常有免费试用额度 |
| **成本控制** | 用 max_tokens 限制、上下文压缩、缓存、模型分级（Turbo/Plus/Max）平衡成本与效果 |

**【白话版】**：你发的消息（输入）和模型的回复（输出）都按 token 收费，回复更贵；如果每次都用同一段固定开场白（系统提示词 + 知识库前缀），命中缓存的部分能便宜一大截。

**【深入原理】**：

- **计费规则与配额**：输入 token、输出 token **分开计价，输出单价通常高于输入**；系统提示词、历史消息、检索文档都计入输入 token——**上下文越长，单次调用越贵**；平台还按 RPM（每分钟请求数）、TPM（每分钟 token 数）、并发数等维度设配额，超额返回 **429**，配额不够可提工单申请调整。
- **上下文缓存与成本优化**：服务端按“请求前缀”缓存，相同前缀（固定 system prompt、固定知识库切片）无需重复计算，命中部分大幅降价，代价是**保持前缀稳定**（把易变内容放在请求靠后位置）；整体优化组合拳：max_tokens 限制输出 → 上下文压缩/截断控制输入 → 复用固定前缀命中缓存 → 按任务选模型（简单任务用 Turbo，高质量任务用 Max）→ 批量任务走离线/批量接口（如平台支持）。

**【实战/考试要点】**：三个关键点——**输入输出分开计价且输出更贵；缓存命中降成本（前缀要稳定）；429 = 限流（配合 9.5 的退避重试）**。
